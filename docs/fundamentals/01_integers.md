# 01. 整数の表現とオーバーフロー

```bash
cargo run -p fundamentals --example integers
cargo run -p fundamentals --example integers --release
```

## 1. コンピュータは数を「ビットの並び」で持っている

メモリの最小単位は**ビット**（0 か 1）で、8 ビットをまとめて **1 バイト**と呼びます。
整数は2進数としてビットに格納されます。

```
  0 = 00000000
  1 = 00000001
  5 = 00000101    (4 + 1)
127 = 01111111
255 = 11111111    (128+64+32+16+8+4+2+1)
```

n ビットで表せるパターンは 2ⁿ 通りです。8 ビットなら 256 通りなので、`u8` は 0〜255 しか表せません。
**型の名前の数字は、ビット数**です。

| 型 | ビット数 | 範囲 |
|---|---|---|
| `u8` | 8 | 0 〜 255 |
| `u32` | 32 | 0 〜 約43億 |
| `u64` | 64 | 0 〜 約1844京 |
| `i8` | 8 | -128 〜 127 |
| `i32` | 32 | 約-21億 〜 約21億 |
| `usize` | CPU による（64bit 環境なら 64） | 配列のインデックスやサイズに使う |

`u` は unsigned（符号なし、0以上だけ）、`i` は integer（符号付き、負の数も表す）の略です。

## 2. 負の数の表し方: 2の補数

符号付き整数は、ビットのパターンの半分を負の数に割り当てます。その割り当て方が **2の補数**です。

```
 127 = 01111111
   1 = 00000001
   0 = 00000000
  -1 = 11111111
  -2 = 11111110
-128 = 10000000
```

規則: **全ビットを反転して 1 を足すと、符号が逆になります**。
例えば 1 = `00000001` を反転すると `11111110`、1 を足すと `11111111` = -1 です。

この方式が使われるのは、**足し算の回路を符号なしと共通にできる**からです。`11111111` に 1 を足すと `00000000` になり（溢れた9ビット目は捨てられます）、確かに -1 + 1 = 0 になっています。

最上位ビットが 1 なら負の数なので、`i8` の範囲は -128〜127 になります（0 を正の側に含めるので、正の数が1つ少なくなります）。

## 3. オーバーフローとは何か

**オーバーフロー**とは、計算結果がその型で表せる範囲を超えることです。

```
  11111111  (255)
+ 00000001  (  1)
----------
 100000000  ← 9ビット必要。でも u8 は8ビットしか持てない
  ^
  この桁は入りきらずに捨てられる → 結果は 00000000 (0)
```

CPU は溢れた桁を捨てます。そのため **255 + 1 が 0 になり**ます。これを**ラップアラウンド**と呼びます。時計の針が 12 の次に 1 に戻るのと同じです。

符号付きの場合、`127i8 + 1` は `01111111 + 1 = 10000000` になり、これは **-128** です。正の数を足したのに負の数になります。

### なぜこれが危ないのか

オーバーフローしても、CPU はエラーを出しません。間違った値のまま、黙って処理が続きます。

- 銀行の残高が上限を超えて、マイナスになる
- `確保するバッファの大きさ = 個数 × 要素のサイズ` の掛け算が溢れて、小さなバッファしか確保されず、その範囲外に書き込んでしまう。C 言語では実際にこれが深刻なセキュリティ脆弱性の原因になってきました
- 1996年、アリアン5ロケットは、64ビットの浮動小数点数を16ビットの整数に変換した際に値が範囲を超え、打ち上げに失敗しました

### Rust の対応

| ビルド | `255u8 + 1` の結果 |
|---|---|
| debug（`cargo run`） | **panic**: `attempt to add with overflow` |
| release（`cargo run --release`） | **0**（ラップアラウンド） |

実験で両方を確かめてください。debug ビルドで検出するのはバグを見つけるためで、release ビルドで検出しないのは、毎回チェックすると遅くなるからです。
（`Cargo.toml` に `[profile.release] overflow-checks = true` と書けば、release ビルドでも検出するようにできます。）

本当に溢れる可能性がある場所では、**どう振る舞うべきかをメソッドで明示します**。

| メソッド | `250u8 + 10` の結果 | 使う場面 |
|---|---|---|
| `checked_add` | `None` | 溢れたらエラーとして扱う（お金の計算など） |
| `saturating_add` | `255` | 上限で止める（音量、ゲームの HP など） |
| `wrapping_add` | `4` | 意図的にラップさせる（ハッシュ値、乱数など） |
| `overflowing_add` | `(4, true)` | 結果と、溢れたかどうかの両方が欲しい |

## 4. `as` による型変換の落とし穴

```
300i32 as u8   = 44           ← 300 = 1_0010_1100 の下位8ビットだけが残る
-1i32 as u32   = 4294967295   ← ビット列は全部 1 のまま、解釈だけが変わる
3.99f64 as i32 = 3            ← 小数点以下は切り捨て
```

`as` は**黙って値を変えてしまいます**。値が変わったときにエラーにしたい場合は `try_from` を使います。

```rust
u8::try_from(300i32)  // Err(TryFromIntError(()))
```

## 5. 整数の割り算

- `7 / 2 = 3`（整数の割り算は 0 の方向に切り捨て）、`-7 / 2 = -3`
- `0` で割ると、debug ビルドでも release ビルドでも **panic** します。ゼロ除算には意味のある結果がないためです
- 余り `%` は左辺と同じ符号になります: `-7 % 3 = -1`。常に 0 以上の余りが欲しい場合は `(-7i32).rem_euclid(3) = 2` を使います
