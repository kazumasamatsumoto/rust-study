# 03. メモリ: スタックとヒープ

```bash
cargo run -p fundamentals --example memory_layout
```

## 1. メモリは巨大なバイトの配列

プログラムから見ると、メモリは**番号（アドレス）の付いた巨大なバイトの配列**です。
`0x16b8e1df8` のような16進数が、アドレスです。変数はメモリのどこかに置かれ、そこを指す番号を持っています。

プログラムが使うメモリには、性質の違う2つの領域があります。

## 2. スタック

関数を呼ぶたびに、その関数のローカル変数を置く領域（**スタックフレーム**）が積まれ、関数から戻ると取り除かれます。

```
main() が foo() を呼び、foo() が bar() を呼んだとき:

  ┌──────────────┐ ← 一番上（今実行中）
  │ bar の変数   │
  ├──────────────┤
  │ foo の変数   │
  ├──────────────┤
  │ main の変数  │
  └──────────────┘
```

- **確保も解放も一瞬**です。上に積んで、取り除くだけです
- ただし、**コンパイル時にサイズが決まっている値しか置けません**
- 大きさに上限があり、数MB程度です。再帰が深すぎると溢れます（**スタックオーバーフロー**）
- 関数から戻ると消えるので、**関数の外に持ち出せません**

## 3. ヒープ

**実行時にサイズが決まるデータ**や、**関数より長く生きるデータ**を置く領域です。

- 「何バイト欲しい」とアロケータ（メモリ管理の仕組み）に頼んで確保し、使い終わったら返却します
- スタックより遅いです。空いている場所を探す必要があり、確保したデータもメモリ上で散らばりがちになります
- サイズは自由で、いつ解放するかも自由です。**だからこそ、誰がいつ解放するのかという問題が生まれます**

## 4. ⭐ `String` と `Vec` はスタックとヒープにまたがっている

```
String        : 24 バイト  ← ポインタ + 長さ + 容量
Vec<i32>      : 24 バイト
Vec<[u8;1000]>: 24 バイト  ← 要素がどれだけ大きくても同じ
```

`String` 本体はスタック上の 24 バイトで、その中に**ヒープ上の文字データを指すポインタ**が入っています。

```
       スタック                        ヒープ
  ┌─────────────────┐          ┌───┬───┬───┬───┐
s │ ptr ────────────┼────────→ │ h │ i │   │   │
  │ len = 2         │          └───┴───┴───┴───┘
  │ capacity = 4    │           使用中   空き
  └─────────────────┘
```

- `len`: 使っているバイト数
- `capacity`: 確保済みのバイト数。`len` が `capacity` を超えるときに、より大きな領域を確保し直します（06 で扱います）

実験では、スタックのアドレス（`0x16b...`）とヒープのアドレス（`0x104...`）が、離れた場所にあることを確認できます。

## 5. ⭐ ムーブの正体

```rust
let t = s; // ムーブ
```

実験の出力を見てください。

```
ムーブ前のヒープアドレス: 0x104da1d50
ムーブ後のヒープアドレス: 0x104da1d50  ← 同じ。中身はコピーされていない
```

ムーブで実際に起きているのは、**スタック上の 24 バイト（ポインタ・長さ・容量）のコピー**だけです。ヒープ上のデータはそのままです。

ここで問題になるのが、`s` と `t` の**両方が同じヒープを指している**ことです。

- 両方がスコープの終わりで解放しようとすると、**二重解放**になります
- `s` を通してデータを書き換えると、`t` から見たデータも勝手に変わります

そのため Rust は、ムーブした後の `s` を**使えなくします**。これが所有権のルールの正体です。
**「ヒープ上のデータを解放する責任を持つのは、常に1つの変数だけ」**にするためのルールなのです。

一方 `clone()` は、ヒープ上に新しい領域を確保して中身をコピーします（実験でアドレスが変わることを確認できます）。だから `clone()` はコストが高いのです。

## 6. `Copy` 型と、そうでない型

`i32` や `bool` は、ヒープを指していません。値の全てがスタック上にあります。コピーしても困ることは何もないので、`Copy` になっています。

**ヒープを指している型（`String`, `Vec`, `Box`）は `Copy` になれません**。勝手にコピーされると、上で説明した二重解放が起きるからです。

## 7. おまけ: アラインメントとニッチ最適化

```
(u8, u32) : 8 バイト  ← 1 + 4 = 5 のはずなのに 8
```

CPU は、`u32` を4の倍数のアドレスから読むのが得意です。そのため、間に詰め物（パディング）が入ります。これを**アラインメント**と呼びます。

```
Option<&i32> : 8 バイト  ← &i32 と同じ
Option<u32>  : 8 バイト  ← u32 (4バイト) より大きい
```

参照は決してヌル（アドレス 0）になりません。そこで Rust は、**`None` をアドレス 0 で表します**。そのため `Option<&T>` は、余分なメモリを使いません（**ニッチ最適化**）。
`Option` は便利なだけでなく、C の「ヌルになりうるポインタ」と全く同じコストで、安全さだけを付け足したものになっています。これが「**ゼロコスト抽象化**」の具体例です。
