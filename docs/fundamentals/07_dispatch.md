# 07. 静的ディスパッチと動的ディスパッチ

```bash
cargo run -p fundamentals --example dispatch --release
```

## 1. ディスパッチとは

**ディスパッチ**とは、「`shape.area()` と書いたときに、**実際にどの関数を呼ぶのか**を決めること」です。
`Circle` の `area` と `Square` の `area` は、別々の機械語の関数としてメモリ上の別の場所に置かれています。呼び出すには、そのアドレスを知る必要があります。

それを**いつ**決めるかで、方式が2つに分かれます。

| 方式 | 決めるタイミング | Rust での書き方 |
|---|---|---|
| **静的ディスパッチ** | コンパイル時 | ジェネリクス `fn f<T: Shape>(s: &T)` / `impl Shape` |
| **動的ディスパッチ** | 実行時 | トレイトオブジェクト `&dyn Shape` / `Box<dyn Shape>` |

## 2. 静的ディスパッチと単相化

```rust
fn total_static<T: Shape>(shapes: &[T]) -> f64 { ... }
```

ジェネリック関数はそのままでは機械語にできません。`T` の大きさも、`T::area` のアドレスも分からないからです。
そこでコンパイラは、**使われた型ごとに関数をコピーして作ります**。`total_static::<Circle>` と `total_static::<Square>` は、別々の関数になります。これを**単相化**（monomorphization）と呼びます。

実験では、同じ `describe` 関数が型ごとに別のアドレスに存在していることを確認できます。

```
describe::<u8>     のアドレス: 0x1020e526c
describe::<u64>    のアドレス: 0x1020e523c
describe::<String> のアドレス: 0x1020e5244
```

（アドレスの値は実行のたびに変わります。見てほしいのは、3つが**別々のアドレス**だという点です。）

**得られるもの**
- 呼び出す関数がコンパイル時に分かるので、**インライン化**（関数の中身を呼び出し元に埋め込むこと）ができます。最適化が最大限に効きます
- 実行時のコストはゼロです

**払うもの**
- 型の数だけ関数が増えるので、**バイナリが大きくなり**、**コンパイルが遅く**なります。Rust のコンパイルが遅い大きな理由の1つが、これです
- 1つの `Vec<T>` には、1種類の型しか入れられません

## 3. 動的ディスパッチと vtable

```rust
fn total_dyn(shapes: &[Box<dyn Shape>]) -> f64 { ... }
```

`dyn Shape` は「`Shape` を実装している、何かの型」です。どの型なのかは実行時にしか分かりません。
そこで Rust は、**vtable**（仮想関数テーブル）という「その型の関数のアドレスの一覧表」を、型ごとに1つ作っておきます。

```
 &dyn Shape (16バイト)                 vtable for Circle (型ごとに1つ)
┌──────────────────┐                 ┌──────────────────────┐
│ data ptr ────────┼─→ Circle { r }  │ drop のアドレス      │
│ vtable ptr ──────┼───────────────→ │ size, align          │
└──────────────────┘                 │ area のアドレス ─────┼─→ Circle::area の機械語
                                     └──────────────────────┘
```

`&dyn Shape` は、**データへのポインタ**と **vtable へのポインタ**を組にしたファットポインタです（[04](04_pointers.md) の `&str` が「アドレス + 長さ」だったのと同じ仕組みです）。

```
&Circle          : 8   ← アドレスだけ
&dyn Shape       : 16  ← アドレス + vtable へのポインタ
Box<dyn Shape>   : 16
```

実験で、中身を覗いてみると:

```
circle(r=1)  data=0x16b016038 vtable=0x104e34040
square       data=0x16b016040 vtable=0x104e34060
circle(r=3)  data=0x16b016048 vtable=0x104e34040   ← 1つ目の circle と同じ vtable
```

**同じ型の値は、同じ vtable を共有しています**。vtable は値ごとではなく、型ごとに1つだけです。

`s.area()` の呼び出しは、実行時に次の手順になります。
1. vtable ポインタを読む
2. vtable の中から `area` のアドレスを読む
3. そのアドレスにジャンプする

**得られるもの**
- 違う型を1つの `Vec<Box<dyn Shape>>` に混ぜて入れられます
- 関数のコピーが作られないので、バイナリが小さく、コンパイルも速くなります
- プラグインのように、コンパイル時には分からない型も扱えます

**払うもの**
- 呼び出しのたびに、ポインタを2回たどります
- 呼び出す関数がコンパイル時に分からないので、**インライン化ができず**、最適化が効きにくくなります
- `Box<dyn Shape>` は1つずつヒープに確保されるので、要素がメモリ上に散らばります（[06](06_complexity.md) のキャッシュの話）

## 4. 速度の比較

100万個の円の面積を合計した結果（release ビルド、2回目の計測）:

```
static (Vec<Circle>)        : 976.583µs
dyn    (Vec<Box<dyn Shape>>): 1.28275ms
```

この環境では、動的ディスパッチは**約1.3倍**遅いという結果でした。
この差には、vtable を引くコストだけでなく、`Box` による**メモリの散らばり**も含まれています。

**大事なのは、「dyn は遅いから使わない」と結論しないこと**です。
- 1回の呼び出しの差は、ナノ秒の単位です
- 1回の呼び出しで重い処理（I/O、ネットワーク）をしているなら、この差は誤差になります
- 何百万回も回るループの中で、軽い処理を呼ぶ場合にだけ、差が目に見えるようになります

結論は同じです。**推測するより計測**しましょう。

## 5. 他の言語では

| 言語 | デフォルト | 補足 |
|---|---|---|
| Java, C# | 動的（仮想メソッド） | JIT コンパイラが実行時に、よく使われる型に特化した最適化をする |
| Go | interface は動的 | ジェネリクス（1.18〜）は、型によって単相化と辞書渡しを組み合わせた実装 |
| C++ | `virtual` は動的、template は静的 | Rust と最も近い。Rust の設計は C++ をお手本にしている |
| Python, JS | 全て動的 | 実行時に、メソッドを名前で探す |
| **Rust** | **静的**。`dyn` と書いたときだけ動的 | コストのかかる方は、コードに `dyn` として現れる |

Rust は、**速い方をデフォルトにして、コストのある方は明示させる**という方針です。Stage 02 で `.clone()` を明示させていたのと同じ考え方です。

## 6. どちらを選ぶか

| 状況 | 選ぶもの |
|---|---|
| 型がコンパイル時に決まっていて、性能が重要 | ジェネリクス / `impl Trait` |
| 違う型を1つのコレクションに混ぜたい | `dyn Trait` |
| 型の種類が閉じていて、全部を自分で把握している | **enum**（Stage 03）。ヒープ確保がなく、match もインライン化できる |
| ライブラリの利用者が型を追加する（プラグイン） | `dyn Trait` |
| コンパイル時間やバイナリのサイズを抑えたい | `dyn Trait` |

**混ぜたいけれど、種類が決まっている**場合は、enum が最も速いことが多いです。`dyn` と enum の両方を思い浮かべられるようになりましょう。

## 7. おまけ: dyn にできないトレイト

全てのトレイトを `dyn` にできるわけではありません（**dyn 互換性**、以前の呼び名は object safety）。
例えば、ジェネリックなメソッド `fn f<U>(&self, u: U)` を持つトレイトは `dyn` にできません。`U` が何になるか分からないので、vtable に載せる関数を事前に作れないからです。
vtable の仕組みを知っていると、この制約は「当然そうなる」と理解できます。
