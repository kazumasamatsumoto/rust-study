# 08. プロセス・スレッド・データ競合

```bash
cargo run -p fundamentals --example threads --release
```

## 1. プロセスとスレッド

**プロセス**とは、実行中のプログラムのことです。`cargo run` するたびに、新しいプロセスが1つ作られます。
OS はプロセスごとに**専用のメモリ空間**を割り当てます。そのため、あるプロセスが別のプロセスのメモリを勝手に読み書きすることはできません。

**スレッド**とは、プロセスの中で動く「実行の流れ」です。1つのプロセスの中に、複数のスレッドを作れます。

```
 プロセス A                          プロセス B
┌─────────────────────────────┐   ┌──────────────┐
│ ヒープ・グローバル変数(共有)  │   │ 別のメモリ空間 │
│                             │   │ (A からは見えない)│
│ ┌────────┐ ┌────────┐       │   └──────────────┘
│ │スレッド1│ │スレッド2│       │
│ │ スタック│ │ スタック│       │
│ └────────┘ └────────┘       │
└─────────────────────────────┘
```

- 各スレッドは**自分専用のスタック**を持ちます（[03 スタックとヒープ](03_memory.md)）
- **ヒープは同じプロセスのスレッド全員で共有**します

この「ヒープを共有している」ことが、スレッドの便利さ（データを渡すのにコピーが要らない）の源であり、同時に危険さの源でもあります。

| | プロセスを分ける | スレッドを分ける |
|---|---|---|
| メモリ | 別々（安全） | 共有（速いが危険） |
| 作るコスト | 大きい | 小さい |
| データのやりとり | パイプやソケットを使う（コピーが必要） | 同じメモリを直接読み書きする |
| 片方がクラッシュしたら | もう片方は生き残る | プロセスごと全部落ちる |

## 2. OS のスケジューリング: いつ実行されるかは分からない

実験の出力を見てください。4つのスレッドがそれぞれ自分の番号を 1000 回書き込み、書き込まれた順番を記録しています。

```
1回目: 切り替わり   27 回, 先頭: 0x161 3x206 1x146 0x114 1x1 0x1 ...
2回目: 切り替わり   21 回, 先頭: 0x727 2x46 3x22 1x230 0x244 1x170 ...
3回目: 切り替わり   11 回, 先頭: 0x1000 1x260 3x62 2x222 3x296 1x319 ...
```

`0x161` は「スレッド 0 が 161 回続けて書き込んだ」という意味です。もう一度実行したときは、次のようになりました。

```
1回目: 切り替わり  146 回, 先頭: 0x6 2x3 1x149 2x2 0x13 3x1 ...
3回目: 切り替わり 1023 回, 先頭: 0x555 1x47 0x8 1x1 0x1 1x1 ...
```

**同じプログラムなのに、毎回結果が違います。**

CPU のコア数には限りがあります（このマシンでは `available_parallelism = 10`）。OS の**スケジューラ**が、どのスレッドをどのコアでいつ動かすかを決めます。実行中のスレッドを途中で止めて別のスレッドに切り替えることもあります（**プリエンプション**）。
その判断は、他のプロセスの状況やタイミングで毎回変わります。

**教訓**: スレッドがどの順番で、どこまで進んでいるかについて、**何も仮定してはいけません**。「たぶんこっちが先に終わる」は、いつか必ず外れます。

## 3. 並行と並列

- **並行**（concurrency）: 複数の処理を「同時に進行中」にすること。1コアでも、細かく切り替えれば並行になります
- **並列**（parallelism）: 複数の処理を「物理的に同時に」実行すること。複数のコアが必要です

Web サーバが1万の接続を同時に扱うのは主に**並行**の問題で（CS基礎 09「I/O モデルと非同期処理」で扱います）、画像処理を8コアで分担して速くするのは**並列**の問題です。

## 4. ⭐ 競合状態とデータ競合

### カウンタが壊れる理由

`count += 1` は1つの操作に見えますが、CPU の中では3つの手順に分かれています。

```
1. メモリから count を読む     (レジスタ ← メモリ)
2. 1 を足す                    (レジスタ + 1)
3. メモリに書き戻す            (メモリ ← レジスタ)
```

2つのスレッドがこれを同時に行うと、次のようなことが起こり得ます。

```
count = 5
スレッドA: 読む (5)
                        スレッドB: 読む (5)
スレッドA: 足す (6)
                        スレッドB: 足す (6)
スレッドA: 書く (6)
                        スレッドB: 書く (6)   ← 2回足したのに 6。1回分が消えた
```

実験では、「読む」と「書く」を別々の操作に分けて同じ状況を再現しています。

```
load + store : 結果 = 1008383  ← 期待値 4000000 より少ない（競合状態）
```

400万回足したはずが、約100万になりました。**4分の3の更新が消えています**。そして実行するたびに数字が変わります（別の回では 1279189 でした）。

### 2つの用語を区別する

| 用語 | 意味 | Rust で防げるか |
|---|---|---|
| **データ競合**（data race） | 複数のスレッドが同じメモリに同時にアクセスし、少なくとも1つが書き込みで、同期の仕組みを使っていない | **コンパイル時に防ぐ**（safe Rust では書けない） |
| **競合状態**（race condition） | 実行のタイミングによって、結果が変わってしまうこと（ロジックのバグ） | 防げない。設計で避ける必要がある |

データ競合は、C/C++ では**未定義動作**です。値がおかしくなるだけでなく、何が起きても文句が言えません。
Rust では、普通の変数をスレッド間で共有して書き換えようとすると**コンパイルエラー**になります。そのため、上の実験も `AtomicUsize`（後述）を使わなければ書けませんでした。

ただし、アトミックな「読む」と「書く」を別々に行えば、データ競合ではありませんが、**競合状態**にはなります。実験の `load + store` がまさにそれです。
**Rust はデータ競合は防ぎますが、競合状態は防ぎません**。この区別はとても大事です。

## 5. 解決策1: アトミック操作

**アトミック**（atomic、不可分）な操作とは、途中で他のスレッドが割り込めない操作のことです。
CPU には「読んで、足して、書く」を1つの命令で行う専用の命令があり、`AtomicUsize::fetch_add` はそれを使います。

```rust
counter.fetch_add(1, Ordering::Relaxed); // 読む・足す・書く を不可分に行う
```

```
AtomicUsize  : 結果 = 4000000, 時間 = 34.305709ms
```

正しく 400万になりました。

使えるのは整数や bool のような単純な値だけで、「2つの値をまとめて更新する」といったことはできません。

## 6. 解決策2: ミューテックス（Mutex）

**ミューテックス**（mutual exclusion、相互排除）とは「**鍵**」です。鍵を持っているスレッドだけがデータに触れられ、他のスレッドは鍵が返されるまで待ちます。

```rust
let mut guard = counter.lock().unwrap(); // 鍵を取る（取れるまで待つ）
*guard += 1;                             // データを触る
// guard がスコープを抜けると、自動で鍵を返す
```

```
Mutex        : 結果 = 4000000, 時間 = 603.39125ms
```

正しい結果になりましたが、アトミックより**約18倍遅く**なっています。4つのスレッドが1つの鍵を奪い合い、ほとんどの時間を「待つこと」に使っているからです（**ロック競合**）。

### Rust の Mutex は「データを包む」

C++ や Java では、ミューテックスとそれが守るデータは別々の変数です。そのため「鍵を取らずにデータを触る」ことができてしまいます。
Rust の `Mutex<T>` は**データそのものを中に包んでいます**。`lock()` しない限り、中のデータにアクセスする方法がありません。鍵を取り忘れるバグが、型の仕組みで起こり得なくなっています。

## 7. 解決策3: そもそも共有しない

```
共有しない   : 結果 = 4000000, 時間 = 985.583µs
```

各スレッドが**自分のローカル変数で数え、最後に1回だけ合算**しました。Mutex より約600倍速くなっています。

**一番速くて安全な同期は、同期しないことです**。共有を最小限にする設計を最初に考え、アトミックやロックは、どうしても共有が必要な場所にだけ使います。

| 方法 | 結果 | 時間（実験） |
|---|---|---|
| 共有しない | 正しい | 約 1ms |
| AtomicUsize | 正しい | 約 34ms |
| Mutex | 正しい | 約 600ms |
| load + store（間違い） | **壊れる** | — |

## 8. デッドロック

ミューテックスを2つ以上使うと、**デッドロック**が起こり得ます。

```
スレッドA: 鍵1 を取る → 鍵2 を待つ
スレッドB: 鍵2 を取る → 鍵1 を待つ
→ お互いが相手の鍵を待ち続け、永遠に進まない
```

Rust の型システムは、**デッドロックを防げません**。設計で避けます。
- 複数の鍵を取るときは、**全てのスレッドで同じ順番で**取る
- 鍵を持ったまま、時間のかかる処理（I/O や別の鍵の取得）をしない
- 鍵を持つ範囲（スコープ）をできるだけ短くする

## 9. スレッドを作るコスト

```
spawn + join x10000: 128.193334ms  (1回あたり 12.819µs)
```

スレッドを1つ作って終わるまでに、約 13µs かかりました。OS にスタック用のメモリを確保してもらい、スケジューラに登録する必要があるからです。
- 1回あたりの処理が数µs しかないなら、スレッドを作るコストのほうが大きくなります
- そのため実務では、スレッドを使い回す**スレッドプール**を使います（`rayon` や、Part 3 の HTTP サーバで作ります）
- 1万の接続にそれぞれスレッドを1つずつ割り当てると、メモリもスケジューリングも重くなります。これが**非同期処理**（Stage 11）が必要になる理由です

## 10. 概要だけ: CPU キャッシュとメモリ順序

ここは深入りしませんが、存在だけは知っておいてください。

- 各 CPU コアは自分専用の**キャッシュ**を持っています。あるコアが書き込んだ値が、別のコアから**すぐに見えるとは限りません**
- コンパイラや CPU は、速くするために**命令の順番を入れ替える**ことがあります。1つのスレッドから見て結果が同じなら許されますが、他のスレッドからは順番が違って見えることがあります

`Ordering::Relaxed` などの引数は、この「他のスレッドからどの順番で見えることを保証するか」を指定するものです。
- カウンタのように、値が正しく足されさえすればよいなら `Relaxed` で十分です
- 「データを書いてから、フラグを立てる」のように順番に意味がある場合は、`Release` / `Acquire` が必要になります
- 迷ったら、アトミックを直接使うのではなく `Mutex` かチャネルを使いましょう。メモリ順序を正しく扱うのは、専門家でも難しいことです
