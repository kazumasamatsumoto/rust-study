# 09. I/O モデルと非同期処理

```bash
cargo run -p fundamentals --example io_latency --release
cargo run -p s11_async --example blocking_demo
```

> 前提: [08 プロセス・スレッド・データ競合](08_concurrency.md) を先に読んでおくと理解しやすくなります。

## 1. I/O とは何か、なぜ遅いのか

**I/O**（Input/Output、入出力）は、CPU とメモリの外側とのデータのやりとりのことです。ファイルの読み書き、ネットワーク通信、データベースへの問い合わせなどが当てはまります。

I/O は、CPU の計算と比べて**桁違いに遅い**です。実験の結果（release ビルド、手元の Mac で計測）:

```
メモリから u64 を1個読む      : 0.164ns (連続した読み込み)
ファイルを開いて読む (1回)    : 10.305µs
ファイルを開いて書く (1回)    : 29.64µs
10ms 待つ (ネットワークの代役): 15.020041ms
```

単位に注目してください。ns（ナノ秒）→ µs（マイクロ秒、1000 ns）→ ms（ミリ秒、1000 µs）です。

| 処理 | だいたいの時間 | 人間の時間に置き換えると（1ns = 1秒） |
|---|---|---|
| メモリの連続読み込み（実験） | 1ns 未満 | 1秒 |
| ファイルを開いて読む（実験。OS のキャッシュに載っている） | 約10µs | 約3時間 |
| 同じデータセンター内の通信 | 約0.5ms（一般によく引用される目安） | 約6日 |
| 東京↔アメリカ西海岸の通信 | 約100ms（目安） | 約3年 |

メモリの読み込みが 1ns 未満なのは、データが連続して並んでいて、CPU のキャッシュと先読みがよく効いているからです（06 を参照）。
ファイルの実験は、OS がファイルをメモリ上にキャッシュしているので、実際のディスクを読むよりずっと速く出ています。それでも、メモリの読み込みとは**数万倍**の差があります。

**つまり、Web サーバのようなプログラムは、ほとんどの時間を「待つこと」に使っています。** DB からの返事を待ち、クライアントからのデータを待ち、外部 API からの応答を待っています。
その待ち時間のあいだに CPU に何をさせるか、が I/O モデルの問題です。

（ちなみに `sleep(10ms)` が 15ms かかっているのは、`sleep` が「**少なくとも**指定した時間は待つ」という約束でしかないからです。OS は、待っていたスレッドをすぐに起こすとは限りません。）

## 2. ブロッキング I/O

一番素直なやり方は、**I/O が終わるまでスレッドを止めて待つ**ことです。これを**ブロッキング I/O**と呼びます。

```rust
let n = socket.read(&mut buf)?; // データが届くまで、このスレッドはここで止まる
```

スレッドが止まっている間、CPU は OS によって他のスレッドに割り当てられます。そのため CPU が無駄になるわけではありませんが、**止まっているスレッド自体**は何もできません。

1つのスレッドで、10人のクライアントに順番に対応すると、こうなります。

```
スレッド: [客1を待つ.......][客2を待つ.......][客3を待つ.......] ...
```

前の客を待っている間、後ろの客は放置されてしまいます。

## 3. 解決策1: 接続ごとにスレッドを作る

「客1人につきスレッドを1本」にすれば、それぞれが勝手に待てます。

```
スレッド1: [客1を待つ.......]
スレッド2: [客2を待つ.......]
スレッド3: [客3を待つ.......]
```

実験の結果:

```
1000スレッド × 50ms 待ち: 64.936041ms
(1つずつ順番に待つと 50ms × 1000 = 50秒かかる)
```

1000 本のスレッドがそれぞれ同時に待つので、50ms 強で終わりました。分かりやすく、とても強力な方法です。

### でも、スレッドはタダではない

```
   10 個のスレッドを作って待つ: 169.666µs (1個あたり 16.966µs)
  100 個のスレッドを作って待つ: 830.709µs (1個あたり 8.307µs)
 1000 個のスレッドを作って待つ: 10.956667ms (1個あたり 10.956µs)
```

スレッドを1本作るのに、約10µs かかっています。これは、ファイルを開いて読むのと同じくらいの時間です。それに加えて、次のようなコストがかかります。

- **メモリ**: スレッドは1本ごとに専用のスタックを持ちます。Rust の `std::thread::spawn` で作るスレッドのスタックは、標準では 2MiB です（実際に物理メモリが使われるのは、触った部分だけです）
- **コンテキストスイッチ**: OS がスレッドを切り替えるたびに、レジスタの退避や復元などの処理が必要です。スレッドが数万本になると、この切り替えのコストが無視できなくなります
- **OS の上限**: 作れるスレッドの数には上限があります

### C10K 問題

1999年に Dan Kegel が「**1台のサーバで1万（10K）の同時接続をさばくにはどうすればよいか**」という問題を提起しました。これを **C10K 問題**と呼びます。
接続ごとにスレッドを作る方式では、1万本のスレッドが必要になり、メモリとコンテキストスイッチのコストが壁になりました。
今のサーバは、10万〜100万の同時接続（チャットや WebSocket など、ほとんどの時間はアイドル状態の接続）を求められることがあります。

## 4. 解決策2: ノンブロッキング I/O とイベントループ

発想を変えます。**少ないスレッドで、たくさんの接続を見張る**のです。

1. ソケットを**ノンブロッキング**モードにする。データがまだ届いていなければ、`read` は待たずに「まだ無い」（`WouldBlock`）とすぐに返す
2. OS に「**この1万個のソケットのうち、どれかが読めるようになったら教えて**」と頼む
3. 教えてもらったソケットだけを処理する。処理が終わったら、また 2 に戻る

この「待つ → 準備ができたものを処理する → また待つ」のループを、**イベントループ**と呼びます。

```
                 ┌───────────────────────────────┐
                 │         イベントループ         │
  ソケット1 ─┐    │                               │
  ソケット2 ─┼──→ │ 1. OS に「どれか準備できた？」 │
  ...       │    │ 2. 準備できたものだけ処理する  │
  ソケット1万┘    │ 3. 1 に戻る                   │
                 └───────────────────────────────┘
```

手順 2 のための OS の仕組みが、OS ごとに用意されています。

| OS | 仕組み |
|---|---|
| Linux | `epoll`（新しいものとして `io_uring` もある） |
| macOS / BSD | `kqueue` |
| Windows | IOCP |

これらを使うと、1本のスレッドで何万もの接続を見張れます。nginx、Node.js、Redis は、この方式で高い性能を出しています。

### その代わりに払うもの: コードが書きにくくなる

イベントループ方式では、「待つ」たびに処理を中断して、イベントループに制御を返さなければなりません。
「どこまで処理したか」を自分で覚えておく必要があり、素直に書くとコールバックが入れ子になっていきます（JavaScript の「コールバック地獄」）。

```js
// 昔の JavaScript
readFile("a.txt", (err, a) => {
  readFile("b.txt", (err, b) => {
    writeFile("c.txt", a + b, (err) => {
      // ...
    });
  });
});
```

## 5. async/await: イベントループを、普通のコードのように書く

**async/await** は、イベントループ方式の性能を保ったまま、**ブロッキング I/O と同じ見た目でコードを書ける**ようにする仕組みです。

```rust
async fn copy() -> io::Result<()> {
    let a = read_file("a.txt").await?; // 待つ間、スレッドは他のタスクを処理する
    let b = read_file("b.txt").await?;
    write_file("c.txt", a + b).await
}
```

`.await` は「ここで待つかもしれない。待つ間は、スレッドを他のタスクに譲る」という印です。

### 協調的マルチタスク

OS のスレッドは、OS が**強制的に**切り替えます（**プリエンプティブ**、横取り型のマルチタスク）。
async のタスクは、**自分から** `.await` で制御を譲ったときにしか切り替わりません（**協調的**マルチタスク）。

これには、次のような結果がついてきます。

- 長所: 切り替えるのは `.await` の場所だけなので、OS のスレッド切り替えよりずっと軽い
- **短所**: タスクが `.await` せずに CPU を使い続けると、同じスレッドの**他のタスクが全部止まります**

この短所は、実験で見られます。

```
== B: std::thread::sleep (async の中でやってはいけない) ==
  [B] tick at    0ms
  [B] tick at  501ms   ← 100ms ごとのはずが、500ms 止まった
  [B] tick at  604ms
```

`std::thread::sleep` は `.await` しないので、スレッドを譲りません。そのためスレッドごと止まり、100ms ごとに動くはずの ticker タスクも止まってしまいました。
`tokio::time::sleep(...).await`（A）や `spawn_blocking`（C）を使えば、ticker は 100ms ごとに動き続けます。

**教訓**: async のコードの中で、ブロッキング I/O（`std::fs`、`std::net`、`std::thread::sleep`）や、長い計算を直接やってはいけません。

## 6. ⭐ Rust の async の正体: ステートマシン

Rust のコンパイラは、`async fn` を**ステートマシン**（状態機械）に変換します。Stage 03 で作った自販機と同じものです。

```rust
async fn copy() {
    let a = read("a").await;
    let b = read("b").await;
    write(a, b).await;
}
```

このコードは、おおよそ次のような enum に変換されます（概念的な図です）。

```rust
enum CopyFuture {
    Start,
    WaitingA { fut: ReadFuture },
    WaitingB { a: String, fut: ReadFuture },        // a を覚えておく必要がある
    WaitingWrite { fut: WriteFuture },
    Done,
}
```

**`.await` の場所が、状態の区切り**になります。中断するときに必要な変数（ここでは `a`）は、状態の中に保存されます。
これはまさに、イベントループ方式で「どこまで処理したか」を人間が手で管理していた部分です。それを**コンパイラが自動で作ってくれる**のです。

この方式には、次のような性質があります。

- **タスクごとのスタックが要らない**: 必要な変数だけを持つ enum なので、タスク1つのサイズは、多くの場合、数百バイトから数KB 程度です。スレッドのスタック（2MiB）と比べて、ずっと小さくなります
- **ヒープ確保も必須ではない**: ステートマシンはただの値なので、スタックに置くこともできます。そのため、組み込み機器でも async が使えます
- これが「**ゼロコスト**の async」と呼ばれる理由です

## 7. Future と poll

ステートマシンを動かすためのインターフェースが、`Future` トレイトです。

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),  // 完了した。結果はこれ
    Pending,   // まだ。準備ができたら知らせる
}
```

ランタイム（tokio など）と Future は、次のようにやりとりします。

```
ランタイム                       Future
    │   poll() ─────────────────→ │ 状態を1つ進める
    │ ←───────────────── Pending  │ 「まだ。準備ができたら起こして」
    │                             │  (Waker を OS の通知に登録しておく)
    │  ... 他のタスクを処理 ...      │
    │                             │
    │ ←────── waker.wake() ────── │ OS「ソケットにデータが届いた」
    │   poll() ─────────────────→ │ 状態をまた進める
    │ ←──────────────── Ready(v)  │ 完了
```

ここで大事なのが、**Waker**（起こし役）です。
ランタイムは、`Pending` を返したタスクを何度も poll したりはしません（それでは CPU の無駄遣いになります）。**Waker が呼ばれたタスクだけ**を、もう一度 poll します。
そのため、自分で Future を実装するときに Waker を登録し忘れると、そのタスクは**二度と起こされず、永遠に止まります**（課題 03 で体験します）。

### Rust の Future は「怠惰」

Rust の Future は、**poll されるまで何もしません**。

```rust
let fut = fetch_price("apple"); // まだ何も起きていない
let price = fut.await;          // ここで初めて実行される
```

JavaScript の Promise は、作った瞬間に実行が始まります（**先行評価**）。Rust の Future は、`.await` するか、`tokio::spawn` でランタイムに渡すまで、動きません（**遅延評価**）。
「`async fn` を呼んだのに何も起きない」というのは、Rust の async を学び始めた人がよくはまるポイントです。コンパイラも、`.await` されていない Future には警告を出します。

### `Pin` について（概要だけ）

ステートマシンは、自分の中の変数への参照を持つことがあります（例: `let b = &a; something.await; use(b);`）。
この値がメモリ上で移動すると、その参照は古い場所を指したままになり、壊れてしまいます（04 のダングリングポインタです）。
`Pin` は「**この値は、もうメモリ上で移動しない**」と約束するための型です。普段のコードで意識することはほとんどありませんが、Future を自分で実装するときに `self: Pin<&mut Self>` として現れます。
