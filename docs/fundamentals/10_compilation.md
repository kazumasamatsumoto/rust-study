# 10. コンパイルとリンク、最適化

```bash
cargo run -p fundamentals --example optimization
cargo run -p fundamentals --example optimization --release
```

## 1. コンパイルとは何か

CPU が実行できるのは**機械語**（CPU の命令を表すバイト列）だけです。
**コンパイラ**は、人間が書いたソースコードを機械語に翻訳するプログラムです。

Python や JavaScript は、実行するときに翻訳します（インタプリタや JIT コンパイラ）。
Rust は**実行する前に、全部を機械語に翻訳しておきます**（AOT: ahead-of-time コンパイル）。その分、実行時には翻訳のコストがかかりません。

## 2. rustc の中で起きていること

```
 ソースコード (.rs)
     │ ① 字句解析・構文解析 … 文字の並びを、木構造 (AST) にする
     ▼
 AST
     │ ② 名前解決・マクロ展開・型検査・トレイトの解決
     ▼
 HIR / MIR  (Rust 専用の中間表現)
     │ ③ 借用検査 … 所有権と借用のルールをチェックする（MIR の上で行う）
     ▼
 LLVM IR  (言語に依存しない中間表現)
     │ ④ LLVM による最適化
     ▼
 機械語 (.o オブジェクトファイル)
     │ ⑤ リンク … 複数のオブジェクトファイルとライブラリを1つにまとめる
     ▼
 実行ファイル
```

- ①〜③ が **Rust 独自の部分**です。所有権のチェックは③で行われ、実行ファイルには一切残りません。だから実行時のコストがゼロなのです
- ④⑤ は **LLVM** に任せています。LLVM は C/C++ のコンパイラ clang や、Swift でも使われている共通の基盤です。Rust が C と同じくらい速いのは、同じ最適化エンジンを使っているからでもあります

### 実際に見てみる

次の関数を、最適化ありでコンパイルしてみます。

```rust
pub fn square(x: u32) -> u32 {
    x * x
}
```

**LLVM IR**（`rustc --emit=llvm-ir -C opt-level=3`）

```llvm
define noundef i32 @_ZN3add6square17h76456300ea77fdc9E(i32 noundef %x) unnamed_addr #1 {
start:
  %_0 = mul i32 %x, %x
  ret i32 %_0
}
```

型（`i32`）と命令（`mul` は掛け算、`ret` は戻る）だけの、アセンブリに近い言語です。Rust の `u32` も、LLVM の中では符号を区別しない `i32` になっています（符号の違いは、使う命令の側で区別します）。

**機械語**（`--emit=asm`、Apple Silicon = ARM64 の場合）

```asm
__ZN3add6square17h76456300ea77fdc9E:
	mul	w0, w0, w0      ; w0 = w0 * w0   (引数も戻り値も w0 レジスタ)
	ret                     ; 呼び出し元に戻る
```

**2命令**になりました。関数名が `_ZN3add6square17h...E` のように変形されているのは、**名前修飾**（mangling）です。別のモジュールにある同じ名前の関数を区別するために、パスとハッシュ値を埋め込んでいます。

## 3. ⭐ debug ビルドと release ビルド

| | `cargo build`（debug） | `cargo build --release` |
|---|---|---|
| 最適化 | なし（`opt-level = 0`） | あり（`opt-level = 3`） |
| オーバーフロー検査 | あり | なし |
| `debug_assert!` | 有効 | 無効 |
| コンパイル速度 | 速い | 遅い |
| 実行速度 | **遅い** | 速い |
| 目的 | 開発中、デバッグ | 本番、ベンチマーク |

同じ `square` を最適化なし（`opt-level=0`）でコンパイルすると、こうなります。

```asm
__ZN3add6square17h76456300ea77fdc9E:
	sub	sp, sp, #32         ; スタックフレームを作る
	stp	x29, x30, [sp, #16]
	add	x29, sp, #16
	umull	x8, w0, w0          ; 64ビットで掛け算して…
	lsr	x8, x8, #32         ; 上位32ビットを取り出し…
	mul	w9, w0, w0
	stur	w9, [x29, #-4]      ; 結果を一度メモリに置く
	cbnz	w8, LBB5_2          ; 上位ビットが 0 でなければ → オーバーフロー → panic へ
	...
```

2命令だったものが10命令以上になりました。**オーバーフローの検査**（[01 整数](01_integers.md)）と、値をいちいちメモリに置く処理が入っているからです。

### 実験: 速度の違い

```
== debug ビルド ==
fib(32)                     :  17.362334ms
iterator_chain(100_000_000) : 1.319128834s
hand_loop(100_000_000)      : 143.082083ms
== release ビルド ==
fib(32)                     :   9.932292ms
iterator_chain(100_000_000) :  18.432625ms
hand_loop(100_000_000)      :  13.197333ms
```

注目してほしいのは `iterator_chain` です。

```rust
(0..n).map(|x| x * 3).filter(|x| x % 2 == 0).map(|x| x / 2).sum()
```

- debug ビルドでは **1.3秒**。手書きのループ（0.14秒）より **約9倍遅い**です
- release ビルドでは **18ms**。手書きのループとほぼ同じ速さになり、debug ビルドより **約70倍速く**なりました

**教訓**
- **速度を測るときは、必ず `--release` で測る**。debug ビルドの速度は、本番の速度とは別物です
- イテレータのような抽象化は、release ビルドではコストがほぼゼロになります。これが**ゼロコスト抽象化**です。debug ビルドで遅いからといって、イテレータを避ける必要はありません

## 4. インライン化: 最適化の起点

イテレータが速くなる仕組みの中心が**インライン化**です。関数の呼び出しを、関数の中身で置き換える最適化です。

最適化なしの `sum_of_squares` には、こんな関数呼び出しが残っていました。

```rust
pub fn sum_of_squares(n: u32) -> u32 {
    (1..=n).map(|x| x * x).sum()
}
```

```asm
	bl	...RangeInclusive...new...    ; bl = 関数呼び出し
	bl	...Iterator...map...
	bl	...Iterator...sum...
```

`map` や `sum` は、それぞれ別の関数です。最適化を有効にすると、LLVM はこれらを全てインライン化して、1つのループにまとめます。
すると関数の境界がなくなり、その先の最適化が可能になります。この例では、さらにその先まで進みました。

```asm
; opt-level=3 の sum_of_squares（抜粋）
	sub	w8, w0, #2
	sub	w9, w0, #3
	umull	x9, w8, w9
	...
	madd	w0, w0, w0, w8
	ret
```

**ループ命令がありません**。LLVM は「1² + 2² + ... + n² を足すループ」だと見抜いて、**n から直接答えを計算する式**（n(n+1)(2n+1)/6 に相当する計算）に書き換えてしまいました。n が 10 でも 10億でも、同じ一瞬で終わります。

インライン化は万能ではありません。インライン化しすぎるとコードが大きくなり、CPU の命令キャッシュに収まらなくなります。`#[inline]` という属性もありますが、基本はコンパイラの判断に任せてください。

## 5. ⭐ なぜ Rust のコンパイルは遅いのか

Rust のコンパイルが遅いのは、Rust の大きな弱点の1つです。主な理由は3つあります。

### (1) 単相化（monomorphization）

ジェネリック関数は、**使われた型ごとに、別々の機械語が作られます**。

```rust
pub fn largest<T: PartialOrd + Copy>(v: &[T]) -> T { ... }

largest(&[1, 5, 3]);      // i32 版
largest(&[1.0, 0.5]);     // f64 版
largest(&[9u8, 2]);       // u8 版
```

コンパイルした結果を見ると、`largest` が**3つ**できていました。

```
__ZN7generic7largest17h0421c63b9fbcd69fE:
__ZN7generic7largest17h1de32961e73285efE:
__ZN7generic7largest17hf29e88ff4265af53E:
```

- **長所**: それぞれの型に特化した機械語になるので、実行が速い。インライン化もしやすい
- **短所**: 生成するコードの量が増え、**コンパイルが遅くなり、バイナリも大きくなる**

Java のジェネリクスは、型の情報を消して1つのコードを共有します（型消去）。コンパイルは速いですが、実行時に型を確認するコストがかかります。
どちらを選ぶかは、まさにトレードオフです。Rust でも `dyn Trait` を使えば、1つのコードを共有する方式を選べます（CS基礎 07 と Stage 06 で扱います）。

### (2) 借用検査と型推論

所有権、ライフタイム、トレイトの解決など、他の言語にはないチェックをコンパイル時に行っています。**実行時のバグを減らすために、コンパイル時間を払っている**のです。

### (3) LLVM の最適化

上で見たような強力な最適化には、時間がかかります。debug ビルドが速いのは、主にこれを省略しているからです。

### 対策

- **インクリメンタルビルド**: 変更されていない部分のコンパイル結果は、`target/` に保存して再利用されます。2回目以降のビルドが速いのはこのためです
- **クレート単位で並列にコンパイル**: 依存しているクレートは、別々に並列でコンパイルされます。大きなプロジェクトを複数のクレートに分けると速くなることがあります
- **`cargo check`**: 型検査と借用検査だけを行い、機械語を作りません。エディタでエラーを確認するだけなら、これで十分です
- **`cargo build --timings`**: どのクレートに時間がかかっているかを、グラフで確認できます

## 6. リンク: 1つの実行ファイルにまとめる

自分のコード、依存しているクレート、標準ライブラリは、それぞれ別々にコンパイルされます。それらをつなぎ合わせて1つの実行ファイルにするのが**リンカ**です。

| | 静的リンク | 動的リンク |
|---|---|---|
| 方法 | ライブラリのコードを実行ファイルに**埋め込む** | 実行時に、OS にあるライブラリ（`.so`, `.dylib`, `.dll`）を**読み込む** |
| 配布 | ファイル1つで動く | ライブラリが入っていないと動かない |
| サイズ | 大きい | 小さい |
| ライブラリの更新 | 再コンパイルが必要 | ライブラリを差し替えるだけで済む |

Rust は、**クレートを全て静的にリンクします**。実験の実行ファイルが何に依存しているかを調べると、次のようになりました（macOS の `otool -L`）。

```
target/release/examples/optimization:
	/usr/lib/libSystem.B.dylib
```

依存しているのは OS の基本ライブラリ（C の標準ライブラリを含む）だけです。そのため、Rust で作った CLI ツールは**ファイルを1つコピーするだけで配布できます**。
Python のツールを配るときに「Python のバージョン」や「pip install」を気にする必要があるのと比べると、大きな違いです。これが、[選球眼トラック](../judgment/01_when_to_use_rust.md) で挙げた「配布が楽」という強みの正体です。
