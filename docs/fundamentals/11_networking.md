# 11. ネットワーク: TCP と HTTP

```bash
cargo run -p fundamentals --example tcp_echo
```

この実験は全て `127.0.0.1`（自分自身のマシン）の中で完結します。外部のネットワークには出ません。

## 1. 階層（レイヤー）で考える

ネットワーク通信は、役割ごとに**層**に分けて考えます。下の層は、上の層に「機能」を提供します。

```
 ┌──────────────────────┐
 │ アプリケーション層   │ HTTP, DNS, SSH ...   「何を話すか」
 ├──────────────────────┤
 │ トランスポート層     │ TCP, UDP             「どのプログラムに、どう届けるか」
 ├──────────────────────┤
 │ インターネット層     │ IP                   「どのマシンに届けるか」
 ├──────────────────────┤
 │ リンク層             │ Ethernet, Wi-Fi      「隣の機械まで届けるか」
 └──────────────────────┘
```

これは TCP/IP モデルと呼ばれる4層の分け方です（より細かく7層に分けた OSI 参照モデルもあり、「L4 ロードバランサ」「L7 ロードバランサ」のような言い方はこちらの番号に由来します）。

各層は、下の層の詳細を知らなくて済みます。HTTP を書く人は Wi-Fi の電波のことを知らなくてよく、TCP は「バイト列を確実に届ける」ことだけに責任を持ちます。
Rust のモジュール設計（s09）と同じく、**責務を分けて、境界をはっきりさせる**ことで、巨大な仕組みを扱えるようにしています。

## 2. IP アドレスとポート

- **IP アドレス**: マシン（正確にはネットワークインターフェース）を表す番号
  - IPv4 は **32 ビット**の整数です（CS基礎 01）。`192.168.0.1` は、8 ビットずつ 10 進数で書いたものです。約43億個しかなく、足りなくなりました
  - IPv6 は **128 ビット**です（`::1` など）
  - `127.0.0.1` は**ループバックアドレス**で、「自分自身」を表します。実験ではこれを使っています
- **ポート**: マシンの中の「どのプログラム宛てか」を表す番号です。**16 ビット**（0〜65535）なので、Rust では `u16` で表されます
  - 80 は HTTP、443 は HTTPS というように、慣習で決まっている番号があります
  - Unix 系の OS では伝統的に、1024 未満のポートで待ち受けるには特権が必要です

「IP アドレス + ポート」の組で、通信の相手を特定します。

```
サーバの待ち受けアドレス: 127.0.0.1:60157
[client] 自分のアドレス: 127.0.0.1:60158  ← ポートは OS が自動で割り当てた (エフェメラルポート)
```

- サーバは、**ポート 0 を指定して bind する**と、OS が空いているポートを選んでくれます。テストでポートの衝突を避けたいときに便利です
- クライアント側にもポートがあります。`connect` したときに OS が自動で割り当てる、一時的なポート（**エフェメラルポート**）です

## 3. TCP: 確実に、順番どおりに届ける

IP は「ベストエフォート」です。パケット（データの小さな塊）は、**途中で失われることも、順番が入れ替わることも、重複することも**あります。
**TCP** はその上で、「**送ったバイト列が、欠けず・順番どおりに・重複なく届く**」ことを保証します。

### 3ウェイハンドシェイク（接続の確立）

```
クライアント                          サーバ
    │ ──── SYN (seq=x) ──────────────→ │  「接続したい。私の番号は x から」
    │ ←─── SYN-ACK (seq=y, ack=x+1) ── │  「了解。私の番号は y から」
    │ ──── ACK (ack=y+1) ────────────→ │  「了解」
    │        ここから通信できる        │
```

- `TcpStream::connect` を呼ぶと、OS がこのやり取りをします。`TcpListener::accept` は、ハンドシェイクを終えた接続を1つ取り出します
- 通信を始めるまでに1往復かかります。遠くのサーバ（往復 100ms など）では、この時間が無視できません。これが、1つの接続を使い回す **keep-alive** が重要な理由です（後述）

### 信頼性と順序の仕組み

- 送るバイトには**シーケンス番号**が付いています。受信側は番号を見て、順番を並べ直し、重複を捨てます
- 受信側は「ここまで受け取った」という **ACK** を返します。ACK が来なければ、送信側は**再送**します
- **フロー制御**: 受信側は「あと何バイト受け取れるか」（ウィンドウ）を伝えます。送信側は、受信側のバッファが溢れないように送る量を調整します
- **輻輳制御**: ネットワーク全体が混雑しているときに、送る速度を落とします

これらは全て OS（カーネル）の中で行われます。アプリケーションからは、ただ「確実に届くバイト列」に見えます。

### ⭐ TCP はバイトの「流れ」で、区切りがない

```
送信側: write を3回 ("first|", "second|", "third|")
受信側: read の結果 = ["first|s", "econd|t", "hird|"]
```

これは TCP を使うときに、最も誤解されやすい点です。**TCP は「メッセージ」を運ぶのではなく、「バイトの流れ（ストリーム）」を運びます**。
1回の `write` が1回の `read` に対応する保証はありません。実験では受信側のバッファを7バイトにしたので7バイトずつ読まれましたが、ネットワークの状況によって、まとめて届くことも、細切れに届くこともあります。

そのため、**どこからどこまでが1つのメッセージなのかは、アプリケーションが自分で決める必要があります**（**フレーミング**）。代表的な方法は2つです。

| 方法 | 例 |
|---|---|
| 区切り文字 | HTTP のヘッダは `\r\n\r\n`（空行）で終わる。1行ずつのプロトコル |
| 長さを先に送る | HTTP の `Content-Length`、CS基礎 14 のログのレコード（先頭にキーと値の長さを書く） |

p03 で HTTP サーバを書くとき、「1回の `read` でリクエスト全体が読める」と仮定すると、たまたま動いて本番で壊れるバグになります。

## 4. UDP: 区切りはあるが、保証はない

```
recv_from: "first|" (送信元 127.0.0.1:62882)
recv_from: "second|" (送信元 127.0.0.1:62882)
recv_from: "third|" (送信元 127.0.0.1:62882)
```

**UDP** は接続を作らず、**データグラム**（1つの独立した塊）を送ります。

| | TCP | UDP |
|---|---|---|
| 接続 | あり（ハンドシェイクが必要） | なし |
| 届く保証 | あり（再送する） | **なし** |
| 順序の保証 | あり | **なし** |
| 区切り | なし（バイトの流れ） | **あり**（1回の send = 1回の recv） |
| 遅延 | 失われたデータの再送を待つ間、後続のデータも止まる | 待たない |

**UDP を選ぶ場面**: 遅れて届いたデータには価値がないとき（ビデオ通話、オンラインゲーム）や、1往復で済む小さな問い合わせ（DNS）。
HTTP/3 は、UDP の上に **QUIC** という独自の信頼性の仕組みを載せています。TCP の「1つのパケットが失われると、その後ろのデータが全て待たされる」問題（Head-of-Line Blocking）を避けるためです。

ここにも選球眼の題材があります。**「保証」にはコスト（遅延）がかかり、全ての用途にその保証が必要なわけではない**のです。

## 5. ソケット

**ソケット**は、OS がアプリケーションに提供する「通信の出入り口」です。Unix 系の OS では、ソケットも**ファイルディスクリプタ**（CS基礎 13）の一種で、ファイルと同じように `read` / `write` できます。

| Rust | 裏で OS に頼んでいること |
|---|---|
| `TcpListener::bind(addr)` | ソケットを作り（socket）、アドレスに結び付け（bind）、待ち受けを始める（listen） |
| `listener.accept()` | ハンドシェイクを終えた接続を1つ取り出す。なければ来るまで待つ（**ブロック**する） |
| `TcpStream::connect(addr)` | ソケットを作り、ハンドシェイクをする |
| `stream.read` / `write` | カーネルの受信バッファ / 送信バッファとのコピー |
| `drop(stream)` | 接続を閉じる。相手の `read` は 0 を返す（実験の2つ目で使っています） |

`TcpStream` は `File` と同じく、`std::io::Read` と `std::io::Write` を実装しています。そのため、`BufReader` などのファイル用の道具がそのまま使えます（実験でも `BufReader::read_until` を使っています）。
トレイトで「読める」「書ける」を抽象化しているおかげで、**ファイルでもネットワークでもメモリ上のバイト列でも、同じコードで扱えます**。p01 のヒントで「入力を `impl BufRead` で受け取るとテストしやすい」と書いたのは、この性質を使うためです。

`std::net` の操作は全て**ブロッキング**です。データが来るまで、そのスレッドは止まります。1つのスレッドで多数の接続を扱いたい場合の話が、CS基礎 09 の非同期 I/O です。

## 6. HTTP/1.1: TCP の上で話すテキスト

```
---- [server] 受け取った生のリクエスト (62 バイト) ----
  GET /hello HTTP/1.1\r\n
  Host: localhost\r\n
  User-Agent: tcp_echo\r\n
  \r\n
```

HTTP/1.1 は、**TCP の上で送る、決まった形式のテキスト**にすぎません。実験では、ただの文字列を `write_all` しただけで、HTTP のリクエストになっています。

### リクエストの形式

```
GET /hello HTTP/1.1\r\n        ← リクエストライン: メソッド パス バージョン
Host: localhost\r\n            ← ヘッダ: 名前: 値
User-Agent: tcp_echo\r\n
\r\n                           ← 空行 = ヘッダの終わり
(ボディ)                       ← POST などで使う。長さは Content-Length で示す
```

- 改行は `\n` ではなく **`\r\n`（CRLF）**です
- `Host` ヘッダは HTTP/1.1 では必須です。1つの IP アドレスで複数のサイトを運用できるのは、このヘッダでどのサイト宛てかを判別しているからです

### レスポンスの形式

```
HTTP/1.1 200 OK\r\n            ← ステータスライン: バージョン ステータスコード 理由
Content-Type: text/plain\r\n
Content-Length: 19\r\n         ← ボディが何バイトか
Connection: close\r\n
\r\n
hello from raw TCP\n           ← ボディ (19 バイト)
```

### keep-alive（持続的接続）

HTTP/1.1 では、**1つの TCP 接続で複数のリクエストを順番に送る**のがデフォルトです。毎回ハンドシェイクをする時間を節約するためです。
そのため受信側は、「ボディがどこで終わるか」を `Content-Length`（または `Transfer-Encoding: chunked`）で知る必要があります。接続が閉じるのを待つだけでは、次のリクエストとの境目が分からないからです。
実験では、`Connection: close` を付けて「このレスポンスの後に接続を閉じる」と宣言し、クライアントは接続が閉じるまで（`read_to_end`）読んでいます。

HTTP/2 はテキストではなくバイナリの形式になり、1つの接続で複数のリクエストを同時に流せるようになりました（多重化）。

## 7. TLS: 暗号化と相手の確認

ここまでの通信は全て**平文**です。途中の経路にいる人は、内容を読むことも書き換えることもできます。
**TLS** は、TCP と HTTP の間に入って、次のことを提供します。

- **暗号化**: 途中の経路にいる人が内容を読めない
- **改ざんの検出**: 途中で書き換えられたら分かる
- **サーバの認証**: 証明書によって、接続した相手が本物の `example.com` であることを確認できる

HTTPS は「HTTP over TLS」、つまり TLS で保護された接続の上で、同じ HTTP のテキストを送っているものです。
Rust では TLS の実装として、Rust で書かれた `rustls` と、OS の TLS ライブラリを使う `native-tls` のどちらかを選ぶのが一般的です（選球眼の題材として、p04 で調べてみてください）。

## 8. DNS: 名前から IP アドレスへ

`example.com` のような名前を、IP アドレスに変換する仕組みが **DNS** です。
通信の前に「この名前の IP アドレスは？」と DNS サーバに問い合わせます（伝統的には UDP の 53 番ポートを使います）。結果はしばらくの間キャッシュされます。

Rust では、`TcpStream::connect("example.com:80")` のように名前を渡すと、標準ライブラリが名前解決をしてから接続します（`ToSocketAddrs` トレイト）。
名前解決には時間がかかることがあり、しかも**ブロッキング**の処理です。非同期のコードの中では注意が必要です（CS基礎 09、s11 の `spawn_blocking`）。
