# 12. メモリ階層とキャッシュ

```bash
cargo run -p fundamentals --example cache --release
```

> **必ず `--release` で実行してください。** debug ビルドでは命令の実行そのものが遅く、メモリの待ち時間の差が埋もれてしまいます（[10 コンパイル](10_compilation.md)）。

前提知識: [03 スタックとヒープ](03_memory.md)、[06 計算量](06_complexity.md)、[08 並行処理](08_concurrency.md)

06 の最後で「計算量だけでは決まらない。`Vec` は CPU キャッシュが効くので速い」と書きました。この章では、その「キャッシュ」が何なのかを、実験で確かめながら説明します。
性能を考えるときに一番効いてくるのは、多くの場合「計算の回数」ではなく「**メモリを待つ時間**」です。

---

## 1. CPU はメモリを待っている

CPU は 1 秒に数十億回の命令を実行できます。1命令あたり 0.2〜0.3ns 程度です。
一方、メインメモリ（DRAM）からデータを1つ読んでくるには、**約 100ns** かかります。

つまり、何も工夫しなければ、CPU はメモリから1つデータが届くまでの間に、**数百命令ぶんの時間をただ待つ**ことになります。

この差を埋めるために、CPU とメモリの間には、小さくて速い記憶装置が何段も置かれています。これを**メモリ階層**と呼びます。

```
   速い・小さい・高い
   ┌──────────────┐
   │ レジスタ      │  数百バイト      CPU の中。計算はここで行う
   ├──────────────┤
   │ L1 キャッシュ │  数十〜百数十 KB  コアごと
   ├──────────────┤
   │ L2 キャッシュ │  数〜十数 MB
   ├──────────────┤
   │ L3 キャッシュ │  数十 MB         (CPU によってはない)
   ├──────────────┤
   │ メインメモリ  │  数〜数十 GB
   ├──────────────┤
   │ SSD          │  数百 GB〜数 TB
   └──────────────┘
   遅い・大きい・安い
```

上の段ほど速いのですが、作るのが高く、CPU の近くに置ける量も限られるので、小さくなります。

### 待ち時間の桁（目安）

| 場所 | 待ち時間の目安 | 1ns を 1 秒に拡大すると |
|---|---|---|
| レジスタ | 1ns 未満 | 1秒未満 |
| L1 キャッシュ | 約 1ns | 1 秒 |
| L2 キャッシュ | 約 3〜10ns | 数秒 |
| L3 キャッシュ | 約 10〜40ns | 十数秒〜数十秒 |
| メインメモリ | 約 100ns | 1〜2 分 |
| SSD (NVMe) の読み込み | 約 10〜100µs | 3 時間〜1 日 |
| 同じデータセンター内の通信 | 約 500µs | 6 日 |

数値は CPU や機器によって大きく変わるので、**桁だけ**覚えてください。L1 とメモリで約 100 倍、メモリと SSD でさらに約 1000 倍の差があります。
（SSD とネットワークの話は [09 I/O と非同期処理](09_io_async.md) で扱いました。）

### 実験: メモリ階層のはしごを自分で測る

実験 3 は、データの大きさを変えながら「1回の読み込みにかかる時間」を測ります。この PC（Apple M4、L1 データキャッシュ 128KB、L2 16MB、キャッシュライン 128 バイト。`sysctl hw` で調べられます）での結果です。

```
データ      16 KB:    0.91 ns/回   ← L1 に収まる
データ      64 KB:    0.91 ns/回   ← L1 に収まる
データ     256 KB:    3.01 ns/回   ← L1 からあふれて L2 へ
データ    1024 KB:    5.02 ns/回
データ    4096 KB:    5.95 ns/回
データ   16384 KB:   10.83 ns/回   ← L2 (16MB) のぎりぎり
データ   65536 KB:   74.01 ns/回   ← L2 からもあふれて、メインメモリへ
データ  262144 KB:   93.34 ns/回
```

データが**キャッシュの大きさを超えた瞬間に、段差のように遅くなる**ことが分かります。上の表の「桁」が、自分の PC で実際に見えました。

この実験では、`next[p]` に「次に読む位置」を入れておき、`p = next[p]` を繰り返しています。次の位置は今の読み込みが終わるまで分からないので、CPU は先回りして読むことができません。そのため、純粋な待ち時間が見えます。
これは連結リストをたどるときと全く同じ状況です（実験 4 でもう一度出てきます）。

## 2. キャッシュライン: メモリはまとめて運ばれる

CPU がメモリから 1 バイトだけ欲しいときでも、実際には**周りのデータもまとめて**キャッシュに運ばれます。この運ばれる単位を**キャッシュライン**と呼びます。

- 多くの x86 CPU では 64 バイト
- Apple M シリーズでは 128 バイト

```
メモリ:  ... [ 0〜127 バイト目 ][ 128〜255 バイト目 ][ ... ]
                    ↑
         ここの 1 バイトを読むと、この 128 バイトが丸ごとキャッシュに来る
```

`u32` なら、1 回の読み込みで 32 個ぶんがまとめて運ばれてくるわけです。**隣のデータを次に使うなら、それはもうキャッシュにあるのでタダ同然**です。

## 3. 局所性: キャッシュが効くプログラムの条件

キャッシュが効くかどうかは、データの使い方で決まります。

| 種類 | 意味 | 例 |
|---|---|---|
| **空間的局所性** | 今使ったデータの**近く**を、すぐに使う | 配列を先頭から順に読む |
| **時間的局所性** | 今使ったデータを、**またすぐに**使う | ループの中で同じ変数を何度も使う |

CPU はさらに、「順番に読んでいるな」というパターンを見つけると、**次のキャッシュラインを先回りして読み込みます**（ハードウェアプリフェッチ）。連続したアクセスはこれでさらに速くなります。

### 実験 1: 行優先 vs 列優先

4096×4096 の行列を、1 本の `Vec<u32>` に**行ごとに**並べて持っています（行優先 / row-major）。

```
メモリ上の並び:  [行0の全要素][行1の全要素][行2の全要素] ...
```

これを「行ごと」に足すか、「列ごと」に足すかで比べます。足す要素も回数も全く同じです。

```
行優先 (連続アクセス)       : 2.048791ms
列優先 (16KB 飛ばしアクセス): 49.900792ms
列優先は 24.4 倍遅い
```

列ごとに読むと、1 つ下の要素は 4096 × 4 = 16KB 先にあります。運んできたキャッシュラインのうち 4 バイトしか使わずに次へ飛ぶので、キャッシュがほとんど役に立ちません。
**計算量はどちらも O(n²) で同じなのに、20 倍以上違います。**（実行するたびに 20〜50 倍程度の間でばらつきました。）

### 実験 2: 連続アクセス vs ランダムアクセス

同じ要素を同じ回数読みますが、順番だけを変えます。

```
データ      32 KB: 連続   0.26 ns/要素, ランダム   0.27 ns/要素 (1.0 倍)
データ     512 KB: 連続   0.28 ns/要素, ランダム   0.48 ns/要素 (1.7 倍)
データ    8192 KB: 連続   0.29 ns/要素, ランダム   0.58 ns/要素 (2.0 倍)
データ  131072 KB: 連続   0.28 ns/要素, ランダム   3.12 ns/要素 (11.0 倍)
```

- データが L1 に収まるうち（32KB）は、順番はどうでもよい
- データが大きくなるほど、ランダムアクセスだけが遅くなる
- 連続アクセスは、データが 128MB になっても速いまま。プリフェッチが効いているから

ランダムアクセスの値が実験 3 の値（約 90ns）より小さいのは、次に読む位置があらかじめ配列に入っていて、CPU が**複数の読み込みを同時に**発行できるからです。実験 3 では次の位置が前の読み込みの結果に依存しているので、1 つずつしか読めません。

### 実験 4: Vec vs LinkedList

```
Vec        : 81.708µs
LinkedList : 1.370583ms  (16.8 倍)
```

どちらも 100 万個の要素を 1 回ずつ読むだけで、計算量は同じ O(n) です。
連結リストのノードはヒープのあちこちに散らばっていて、次のノードの場所は今のノードを読むまで分かりません。実験 3 と同じ「1 つずつ待つ」状態です。
**これが、Rust の標準ライブラリに `LinkedList` があってもほとんど使われない理由**です（06 を参照）。

## 4. AoS と SoA: データの並べ方を設計する

ゲームの粒子や、データベースの行のように、同じ形のデータが大量にあるとき、並べ方は 2 通りあります。

```rust
// AoS (Array of Structs): 構造体の配列。普通の書き方
struct Particle { x: u32, y: u32, z: u32, vx: u32, /* ... */ id: u64, flags: u64 }
let particles: Vec<Particle>;

// SoA (Struct of Arrays): 配列の構造体。フィールドごとに Vec を持つ
struct Particles { x: Vec<u32>, y: Vec<u32>, z: Vec<u32>, /* ... */ }
```

```
AoS のメモリ:  [x y z vx vy vz mass charge id flags][x y z ...][x y z ...] ...
SoA のメモリ:  x: [x x x x x x x x x x x x ...]
               y: [y y y y y y y y y y y y ...]
```

### 実験 5: x だけを合計する

```
ParticleAoS 1個のサイズ: 48 バイト (そのうち x は 4 バイト)
AoS で x の合計: 2.69575ms
SoA で x の合計: 255.708µs  (AoS は 10.5 倍遅い)
```

AoS では、x を 1 つ読むたびに、使わない 44 バイトも一緒にキャッシュへ運んでいます。運んだデータの 1/12 しか使っていません。
SoA では、運んだデータが全部 x なので無駄がありません。さらに、同じ型の値が連続しているので、コンパイラが **SIMD 命令**（1 命令で複数の値をまとめて計算する命令）を使いやすくなります。

**どちらを選ぶか**

| | AoS | SoA |
|---|---|---|
| 1 つの要素の全フィールドを使う処理 | ◎ | △（あちこちの Vec を読む） |
| 全要素の一部のフィールドだけを使う処理 | △ | ◎ |
| 書きやすさ・読みやすさ | ◎ | △ |

ゲームエンジンの ECS（Entity Component System、Rust では `bevy` が有名）や、列指向データベース（Apache Arrow、DuckDB など）は、SoA の考え方で作られています。
ただし、普段のアプリケーションでは AoS で十分なことがほとんどです。**計測して、ここがボトルネックだと分かってから**検討しましょう（Stage 15）。

## 5. 分岐予測: CPU は if の結果を「賭けて」いる

最近の CPU は、命令を 1 つずつ順番に実行しているわけではありません。何十個もの命令を、流れ作業（**パイプライン**）で同時に進めています。

ここで困るのが `if` です。条件の結果が出るまで、次にどちらの命令を実行すべきか分かりません。待っていると流れ作業が止まってしまいます。
そこで CPU は、**過去の傾向から結果を予想して、先に実行してしまいます**（分岐予測）。

- 予想が当たれば、待ち時間はゼロ
- 外れたら、先に進めた作業を全部捨ててやり直す。10〜20 サイクル程度の損になる

### 実験 6: ソート済みのデータ vs 未ソートのデータ

0〜255 のランダムな値 100 万個から、128 以上のものだけを足します。

```
分岐あり  / 未ソート: 2.660625ms
分岐あり  / ソート済: 261.542µs  (未ソートは 10.2 倍遅い)
分岐なし  / 未ソート: 17.042µs
分岐なし  / ソート済: 17µs
```

- **未ソート**: 128 以上かどうかが毎回ランダムなので、予想は半分くらい外れる
- **ソート済み**: 前半はずっと「いいえ」、後半はずっと「はい」なので、予想はほぼ当たる

**データの並び順が変わっただけで、同じコードの速さが 10 倍変わりました。**

「分岐なし」は、条件を `(x >= 128) as u64` という 0 か 1 の値にして、掛け算で書いたものです。分岐がないので予想の当たり外れが関係なく、SIMD も使えるので、さらに 100 倍以上速くなっています。

> **注意: この実験は、コンパイラと戦っています。**
> 普通に `if x >= 128 { sum += x }` と書くと、コンパイラは賢いので、自動で分岐のない命令（条件付き選択命令や SIMD）に変換してしまいます。そうなると、ソートしてもしなくても速さは変わりません。実際に試すと、未ソートが 33µs、ソート済みが 46µs で、どちらも「分岐あり」よりずっと速く、ソートによる改善もありませんでした。
> 実験コードでは、`black_box` を使ってこの変換をわざと防いでいます。
> つまり、**普段のコードでは、こうした最適化はコンパイラに任せればよい**ということです。分岐予測を意識する必要があるのは、計測してそこが遅いと分かったときだけです。

## 6. フォルスシェアリング: 別々の変数なのに、取り合いになる

[08 並行処理](08_concurrency.md) で、複数のスレッドが同じデータを書き換えると遅くなることを見ました。
実は、**別々の変数であっても、同じキャッシュラインに乗っていると**同じことが起きます。

```rust
struct Adjacent { a: AtomicU64, b: AtomicU64 }  // a と b は 8 バイトしか離れていない
```

スレッド 1 は `a` だけを、スレッド 2 は `b` だけを書き換えます。論理的には何も共有していません。
しかし、キャッシュは**キャッシュライン単位**で管理されています。スレッド 1 が `a` を書き換えると、`b` も含んだキャッシュライン全体が「書き換わった」扱いになり、スレッド 2 のコアにあるコピーは無効になります。
結果として、2 つのコアの間でキャッシュラインが行ったり来たりします。これを**フォルスシェアリング**（偽りの共有）と呼びます。

### 実験 7

```
a と b のアドレスの差: 8 バイト (同じキャッシュライン)
隣り合ったカウンタ    : 110.175667ms
128 バイト離したカウンタ: 31.950333ms  (隣り合うと 3.4 倍遅い)
```

対策は、`#[repr(align(128))]` を付けて、変数をキャッシュラインの境界に揃えることです。こうすると、それぞれの変数が別のキャッシュラインに乗ります。
`crossbeam` クレートの `CachePadded<T>` は、まさにこれをするための型です。tokio などの並行処理ライブラリの内部でも使われています。

## 7. まとめ: Rust はこの知識とどうつながるのか

| CS の事実 | Rust での現れ方 |
|---|---|
| 連続したデータはキャッシュが効く | `Vec` がデフォルトの選択肢。`Vec<T>` は要素を（ポインタではなく）値そのものとして連続して並べる |
| 散らばったデータは遅い | Java の `ArrayList<Integer>` は各要素が別々のオブジェクトへのポインタになるが、Rust の `Vec<i32>` は値そのものが並ぶ。`Box` を多用すると散らばる |
| データの並べ方が性能を決める | 構造体のレイアウトを自分で決められる（`#[repr(C)]`、`#[repr(align)]`）。SoA も書ける |
| コンパイラは分岐を消すなどの最適化をする | ゼロコスト抽象化。イテレータで書いても、最適化されて同じ機械語になる（Stage 15） |
| フォルスシェアリング | `#[repr(align(N))]`、`crossbeam::utils::CachePadded` |

GC のある言語では、オブジェクトがどこに置かれるかを自分で決めにくく、GC がオブジェクトを移動させることもあります。
Rust（や C/C++）では、**データがメモリ上にどう並ぶかを、プログラマが把握して決められます**。性能が必要な場面で Rust が選ばれる理由の一つです。

ただし、ここに書いたことの大半は、**計測して問題が見つかったときに初めて使う知識**です。最初から気にしすぎて読みにくいコードを書くのは本末転倒です。その判断の仕方は Stage 15 で扱います。

## 確認問題（`answers/fundamentals.md` へ）

1. 実験 3 の結果から、この PC の L1 キャッシュと L2 キャッシュの大きさを推測してください。`sysctl hw.l1dcachesize hw.l2cachesize`（macOS）や `lscpu`（Linux）で調べた実際の値と比べてみましょう。
2. 2 次元の画像（幅 1920 × 高さ 1080 のピクセル）を `Vec<u32>` に行優先で持っています。全ピクセルの明るさを変える処理を書くとき、ループの外側を「行」と「列」のどちらにしますか？ 理由も答えてください。
3. ユーザーのデータ `struct User { id: u64, name: String, age: u32, bio: String }` が 100 万件あり、「平均年齢」を何度も計算します。AoS と SoA のどちらが速いと予想しますか？ `String` が持っているのはヒープへのポインタであること（[03](03_memory.md)）も考えて答えてください。
4. 実験 7 で、`Padded` の `#[repr(align(128))]` を `#[repr(align(8))]` に変えると、結果はどうなると予想しますか？ 実際に試して確かめてください。
5. Java の `ArrayList<Integer>` と Rust の `Vec<i32>` で、100 万個の合計を求める速さに差が出るとしたら、その理由をキャッシュの観点から説明してください。
