# 13. OS とシステムコール

```bash
cargo run -p fundamentals --example syscalls --release
```

一時ファイルを OS の一時ディレクトリに作り、最後に削除します。

## 1. OS は何をしているのか

**OS（オペレーティングシステム）のカーネル**は、ハードウェア（CPU、メモリ、ディスク、ネットワーク）を管理し、複数のプログラムに安全に分け与えるソフトウェアです。

もし全てのプログラムがディスクを直接操作できたら、あるプログラムのバグが、他のプログラムのファイルやファイルシステム全体を壊してしまうかもしれません。
そこで CPU には**特権レベル**があり、プログラムは2つの世界に分けられています。

```
 ┌───────────────────────────────────────────┐
 │ ユーザー空間                              │
 │   あなたのプログラム、ブラウザ、エディタ  │  ← ハードウェアを直接触れない
 ├───────────── システムコール ──────────────┤
 │ カーネル空間                              │
 │   ファイルシステム、ネットワーク、        │  ← 何でもできる
 │   メモリ管理、プロセスの管理              │
 └───────────────────────────────────────────┘
          ↓
     ハードウェア
```

ユーザー空間のプログラムがファイルを読んだり、ネットワークで通信したり、メモリを確保したりしたいときは、**システムコール**でカーネルに頼みます。

## 2. システムコール

**システムコール**は、ユーザー空間のプログラムがカーネルに処理を頼むための入り口です。呼ぶと CPU の特権レベルが切り替わり、カーネルのコードが実行されて、また戻ってきます。

代表的なシステムコール（Unix 系）:

| システムコール | 内容 | Rust で呼ばれる場面 |
|---|---|---|
| `open` | ファイルを開き、ファイルディスクリプタを返す | `File::open`, `File::create` |
| `read` / `write` | ファイルディスクリプタから読む / に書く | `Read::read`, `Write::write` |
| `close` | ファイルディスクリプタを閉じる | `File` が drop されたとき |
| `fsync` | ファイルの内容をディスクに書き出すまで待つ | `File::sync_all` |
| `socket` / `connect` / `accept` | ネットワーク通信 | `TcpStream`, `TcpListener`（CS基礎 11） |
| `mmap` など | メモリを確保する | アロケータが大きなメモリを確保するとき（CS基礎 03） |

**システムコールにはコストがかかります**。特権レベルの切り替えや、カーネル内での処理が発生するからです。普通の関数呼び出しに比べると、桁違いに遅くなります。

## 3. ファイルディスクリプタ

```
開いたファイルの fd = 3
(0 = 標準入力, 1 = 標準出力, 2 = 標準エラー出力 は最初から開いている)
```

**ファイルディスクリプタ**（fd）は、カーネルがプロセスごとに持っている「開いているファイルの表」の**番号**です。プログラムは、ファイルそのものではなく、この番号を使ってカーネルに「3番に書いて」と頼みます。

```
 プロセスの fd 表（カーネルが管理）
 ┌────┬───────────────────────┐
 │ 0  │ 標準入力 (キーボード) │
 │ 1  │ 標準出力 (画面)       │
 │ 2  │ 標準エラー出力        │
 │ 3  │ /tmp/xxx.txt          │ ← 実験で開いたファイル
 │ 4  │ TCP 接続 (ソケット)   │ ← ソケットも fd になる
 └────┴───────────────────────┘
```

- Unix 系の OS では「**全てはファイル**」という考え方で、ファイル、ソケット、パイプ、端末などが全て fd として同じように扱われます
- fd には上限があります（プロセスごとの上限は `ulimit -n` で確認できます）。**閉じ忘れると、いつか新しいファイルが開けなくなります**（fd のリーク）

### Rust は fd の閉じ忘れを防ぐ

Rust の `File` は fd を**所有**していて、drop されたときに自動で `close` します。s02 の所有権と、s08 の `Drop` の実例です。
C では `close` を自分で呼ぶ必要があり、エラー処理の途中で `return` したときに閉じ忘れるバグがよく起きます。Java には `try-with-resources`、Python には `with` 文がありますが、書き忘れることができます。
Rust では、**所有者がスコープを抜ければ必ず閉じられる**ので、書き忘れることができません。このように「資源の解放を、値の寿命に結び付ける」設計を **RAII** と呼びます。

## 4. ⭐ バッファリング: システムコールの回数を減らす

```
== 11 バイトの write を 100000 回 ==
File に直接       : write システムコール 100000 回, 125.849916ms
BufWriter 経由    : write システムコール    135 回, 685.834µs
→ 約 183 倍速い
```

（実行時間は、マシンの状態によって大きく変わります。同じ環境でもう一度実行したときは、412ms と 738µs で約558倍でした。）

- `File` に直接 `write` すると、**呼ぶたびにシステムコールが発生**します。11 バイトを書くたびにカーネルとの行き来が起きるので、1回あたり数µs かかっています
- `BufWriter` は、データをまず**ユーザー空間のメモリ（バッファ）に溜めて**おき、溜まったらまとめて1回のシステムコールで書き出します
  - バッファの大きさは、標準ライブラリの現在の実装では 8 KiB です
  - 1,100,000 バイト ÷ 8,192 バイト ≒ 134.3 なので、約135回になります。計算どおりです

実験で回数を数えられているのは、`File` を包んだラッパー（`CountingWriter`）で `write` の呼び出しを数えているからです。`File::write` は1回呼ぶごとに `write` システムコールを1回発行するので、これがシステムコールの回数になります。
（Linux では `strace -c` を使うと、プログラムが発行したシステムコールを直接数えられます。macOS の同等のツール `dtruss` は、システム保護機能（SIP）によって制限されています。）

### 実務での注意点

- **ファイルに小さな書き込みを繰り返すなら、`BufWriter` で包む**。`BufReader` も同じです
- **`println!` にも注意**。Rust の標準出力は**行ごとにバッファリング**されるので、`println!` を1行ごとに呼ぶと、そのたびにシステムコールが発生します。大量に出力するときは、`stdout().lock()` を `BufWriter` で包みます
- **`BufWriter` は `flush` を明示的に呼ぶ**。`BufWriter` は drop されるときにも書き出しを試みますが、**そのときに起きたエラーは無視されます**（`Drop` は `Result` を返せないからです）。書き込みの失敗を確実に知りたいなら、自分で `flush()` を呼んで、結果を確認します

## 5. ⭐ ページキャッシュ: write が返っても、まだディスクには書かれていない

```
8 MiB の write_all: 721.916µs  ← メモリ (ページキャッシュ) にコピーしただけ
sync_all          : 6.165667ms  ← 実際にディスクへ書き出すのを待った
```

（2回目の実行では、772µs と 13.46ms でした。）

ディスクは、メモリよりはるかに遅い装置です（CS基礎 09）。そのためカーネルは、ファイルのデータを**メモリ上にキャッシュ**しています。これを**ページキャッシュ**と呼びます。

```
 あなたのプログラム
     │ write
     ▼
 ┌──────────────────┐
 │ ページキャッシュ │ ← write はここにコピーした時点で返ってくる
 │ (カーネルのメモリ) │
 └──────────────────┘
     │ 後でカーネルがまとめて書き出す (数秒〜数十秒後のこともある)
     ▼
 ┌──────────────────┐
 │ ディスク          │
 └──────────────────┘
```

- **write**: データをページキャッシュにコピーした時点で、成功として返ってきます。ディスクへの書き出しは後回しです
- **read**: データがページキャッシュにあれば、ディスクを読まずにメモリから返します。同じファイルを2回目に読むと速いのはこのためです
- **fsync**（Rust では `File::sync_all`）: ページキャッシュにある、そのファイルの内容がディスクに書き出されるまで待ちます。実験では、write の約10倍の時間がかかっています

### 何が起きたら、データが失われるのか

| 起きたこと | write した直後のデータ | fsync した後のデータ |
|---|---|---|
| プロセスが panic した、kill された | **残る**（データはカーネルが持っている） | 残る |
| OS がクラッシュした、電源が落ちた | **失われることがある** | 残る（※） |

※ ディスク装置自体のキャッシュの扱いなど、細かい条件はあります。

これが p02（KV ストア）の非機能要件「プロセスが kill されても、完了を返した書き込みは失われない（OS のクラッシュは考慮しなくてよい）」の意味です。
プロセスが kill されるだけなら、write でカーネルに渡しておけば十分です。電源断にまで耐えたいなら、fsync が必要です。そして fsync は遅いので、**どこまでの耐久性が必要かは、性能とのトレードオフ**になります。データベースの設定に「コミットのたびに fsync するか」という項目があるのは、このためです（CS基礎 14）。

### 厳密な話: rename と fsync

ファイルを書き換えるときの定番の手順は、「一時ファイルに書く → fsync → rename で置き換える」です。`rename` は、同じファイルシステムの中ではアトミックに（中途半端な状態を見せずに）置き換わります。
ただし Linux では、rename したという事実（ディレクトリの内容の変更）を電源断に耐えさせるには、**ディレクトリそのものも fsync する**必要があります。ここまで気にするのが、データベースを作る人の仕事です。

## 6. プロセスと仮想メモリ

**プロセス**とは、実行中のプログラムのことです。カーネルは、プロセスごとに次のものを用意します。

- **独立したメモリ空間**: CS基礎 03 の実験で表示したアドレス（`0x16b8e1df8` など）は**仮想アドレス**です。各プロセスは、自分だけが巨大なメモリを持っているように見えますが、実際の物理メモリのどこに対応するかは、カーネルと CPU が管理しています。そのため、あるプロセスのバグが、他のプロセスのメモリを壊すことはありません
- **fd 表**: 上で説明したとおりです
- **1つ以上のスレッド**: CS基礎 08 で扱いました。同じプロセスのスレッドは、メモリ空間を共有します

「プロセスは互いに隔離されている。スレッドはメモリを共有している」。だからスレッド間では、データ競合を防ぐ仕組み（Rust では `Send` / `Sync`）が必要になるのです。
