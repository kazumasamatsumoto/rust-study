# 14. ストレージエンジン: データベースはどうやって保存しているのか

```bash
cargo run -p fundamentals --example append_log
```

一時ファイルを OS の一時ディレクトリに作り、最後に削除します。
このドキュメントは、p02（KV ストア）の設計の土台です。**p02 を始める前に読んでください。**

## 1. 何が難しいのか

データベースの中で、データをディスクに保存して読み出す部分を**ストレージエンジン**と呼びます。求められることは、互いに矛盾しがちです。

- **書き込みが速い**
- **読み出しが速い**
- **ディスクを無駄に使わない**
- **クラッシュしても壊れない**: 書き込みの途中でプロセスや OS が落ちても、データが矛盾した状態にならない

ディスクには、性能上の重要な性質があります。**ランダムな位置への書き込みより、末尾への連続した書き込み（シーケンシャル書き込み）のほうが速い**ことです。HDD では桁違いに、SSD でも差があります。
この性質と上の4つの要求の折り合いの付け方によって、いくつかの方式に分かれます。

## 2. 追記型ログ: 一番単純な方式

**全ての書き込みを、ファイルの末尾に追記するだけ**の方式です。上書きも削除も、「新しいレコードを追記する」ことで表します。

### ディスク上のフォーマット

実験では、1つのレコードを次の形式で書いています。

```
[キーの長さ u32][値の長さ u32][キーのバイト列][値のバイト列]
```

```
set lang=rust, level=1 → ファイルの中身:
  0000: 04 00 00 00 04 00 00 00 6C 61 6E 67 72 75 73 74  ........langrust
  0010: 05 00 00 00 01 00 00 00 6C 65 76 65 6C 31        ........level1
```

- `04 00 00 00` は、キー `lang` の長さ 4 を、u32 のリトルエンディアン（下位のバイトが先）で書いたものです（CS基礎 01）
- `6C 61 6E 67` は `lang` の UTF-8 のバイト列です（CS基礎 05）
- **長さを先に書いておく**ことで、読むときにどこまでが1つのレコードかが分かります。CS基礎 11 で学んだ、TCP のフレーミングと同じ考え方です

削除は、値の長さに特別な値（`u32::MAX`）を書いたレコードで表します。これを**トゥームストーン**（墓石）と呼びます。

### 長所と短所

- ✅ 書き込みは末尾への追記だけなので、**とても速い**
- ✅ 既存のデータを書き換えないので、**クラッシュに強い**（後述）
- ❌ 読み出すには、ファイルを先頭から全部読んで、そのキーの最後のレコードを探す必要がある。**O(n)** です
- ❌ 上書きや削除をしても古いレコードは残るので、**ファイルが膨らみ続ける**

```
level を 2〜5 に上書きし、lang を削除した
ファイルサイズ: 98 バイト (生きている値は level=5 の1件だけなのに)
```

## 3. ハッシュインデックス: 読み出しを速くする

読み出しを速くするには、「キー → そのキーの最新のレコードが、ファイルのどの位置にあるか」を**メモリ上の `HashMap`** に持っておきます。これを**インデックス**と呼びます。

```
インデックス: {"level": 72}
```

`get` のときは、インデックスで位置を引き、その位置だけをディスクから読みます（`seek` してから `read`）。読み出しは、**平均 O(1) のハッシュ検索 + ディスクの読み出し1回**になります。

これは **Bitcask**（分散データベース Riak のストレージエンジン）が使っている方式です。実験は、その最小版です。

### 起動時の復旧

インデックスはメモリ上にしかないので、プロセスが終了すると消えます。そのため**起動時にログを先頭から読み直して、インデックスを作り直します**。

```
== 3. 再起動: ログを読み直してインデックスを復元する ==
  インデックスを再構築: レコード 7 件を読み、生きているキーは 1 件
```

**ログが「正」で、インデックスはそこから作り直せる「キャッシュ」にすぎない**、という関係が大事です。

### この方式の限界

- **全てのキーがメモリに収まる必要がある**
- **範囲検索ができない**。「`user:100` から `user:200` までのキー」のような検索は、ハッシュでは効率よくできません（CS基礎 06 の `HashMap` と `BTreeMap` の違いと同じです）
- 起動時にログ全体を読むので、ログが大きいと起動が遅い（Bitcask は、インデックスの内容を別ファイルに保存しておく「ヒントファイル」でこれを解決しています）

## 4. ⭐ クラッシュへの耐性: 書き込みの途中で落ちたら？

レコードの書き込みの途中でプロセスが落ちると、ファイルの末尾に**不完全なレコード**が残ります（torn write）。実験では、ヘッダだけを書いて本体の途中で止まった状況を再現しています。

```
== 4. 書き込み途中でクラッシュした場合 ==
  位置 98 に不完全なレコードがあったので、そこで打ち切った
  インデックスを再構築: レコード 7 件を読み、生きているキーは 1 件
  末尾のゴミ 10 バイトを切り詰めた
get(level) = Some("5")  ← 完了していたデータは無事
```

追記型ログでは、壊れる可能性があるのは**最後のレコードだけ**です。既存のデータは決して書き換えないからです。そのため、復旧は「最後の完全なレコードまでを信じる」だけで済みます。

### 実験を作る途中で、実際に踏んだバグ

最初の版の実験では、不完全なレコードを読み飛ばすだけで、**ファイルから取り除いていませんでした**。すると次のことが起きます。

```
[正常なレコード...][ゴミ][新しいレコード 1000 件]
                    ↑
           次の起動時、ここで読み込みが止まる → 後ろの 1000 件が全て失われる
```

新しいレコードがゴミの後ろに追記されてしまい、**次に再起動したときに、ゴミより後ろのデータが全て読めなくなる**のです。
今の実験では、起動時にゴミを切り詰めて（`File::set_len`）から追記を再開しています。クラッシュからの復旧は、「1回落ちる」だけでなく「**落ちて、復旧して、また書いて、また落ちる**」まで考える必要があります。p02 でも、この種のテストを書いてください。

### 壊れ方は途切れるだけではない

実験は、レコードが**途中で途切れた**場合しか検出できません。ディスクの故障などでデータの中身が**化けた**場合は、長さが正しく見えてしまうので気付けません。
実際のシステムは、レコードごとに **CRC**（データから計算する短い検査用の値）を書いておき、読むときに計算し直して一致するかを確かめます。Bitcask のレコードにも CRC が含まれています。

## 5. コンパクション: ファイルの膨張を止める

```
counter を 1000 回上書きした後: 17988 バイト
コンパクション後             : 32 バイト
```

**コンパクション**は、生きているキーの最新の値だけを新しいファイルに書き出して、古いファイルと置き換える処理です。

安全に置き換えるための手順:

1. 新しい一時ファイルに、生きているデータを書く
2. 一時ファイルを `fsync` する（CS基礎 13）
3. `rename` で、古いファイルと置き換える。同じファイルシステムの中では、rename はアトミックです

途中で落ちても、古いファイルか新しいファイルのどちらか一方が、完全な形で残ります。**中途半端なファイルが「正」になる瞬間がない**ことがポイントです。

考えるべきこと（p02 の ADR の題材です）:
- **いつ**コンパクションするか（ファイルサイズ？ ゴミの割合？）
- コンパクションの最中に来た書き込みをどうするか
- コンパクションは、ディスクに大量の書き込みをする。その間、通常の処理が遅くなってもよいか

## 6. B-tree: 最も広く使われている方式

**B-tree** は、データを**キーの順に並べた木構造**で、ディスク上に置かれます。SQLite、PostgreSQL のインデックス、MySQL の InnoDB など、多くの関係データベースが使っています（多くの実装は、葉にだけデータを置く派生形の B+tree です）。

```
                  ┌─────────────────┐
                  │   [ 100 | 200 ] │  ← ルートページ
                  └─────────────────┘
          ┌────────────┼─────────────┐
          ▼            ▼             ▼
   ┌────────────┐┌────────────┐┌────────────┐
   │ 1..99      ││ 100..199   ││ 200..      │  ← 葉のページ（ここにデータ）
   └────────────┘└────────────┘└────────────┘
```

- ディスクを、**ページ**と呼ばれる固定サイズのブロックに分けて管理します（デフォルトのページサイズは、SQLite が 4 KiB、PostgreSQL が 8 KiB、InnoDB が 16 KiB）
- 1つのページに数百個のキーが入るので、木の**分岐の数**がとても多くなります。そのため、何百万件のデータでも、木の深さは数段で済みます。検索は O(log n) です
- キーが順番に並んでいるので、**範囲検索が得意**です
- 書き込みは、該当するページを**その場で書き換えます**（in-place update）

### その場で書き換えることの危険と、WAL

ページを書き換えている途中でクラッシュすると、**ページが中途半端な状態で残る**可能性があります。追記型ログと違い、既存のデータを壊してしまいます。
そこで B-tree のデータベースは、**WAL**（Write-Ahead Log、先行書き込みログ）を併用します。

1. 変更内容を、まず**ログに追記**して fsync する
2. その後で、ページを書き換える
3. クラッシュしたら、起動時にログを読んで、変更をやり直す（または取り消す）

**「まずログに書く」**ことで、追記型ログの「クラッシュに強い」性質を借りているのです。PostgreSQL は WAL を使っています。SQLite はデフォルトではロールバックジャーナルという別の方式を使い、設定（`journal_mode=WAL`）で WAL に切り替えられます。

## 7. LSM-tree: 書き込みに強い方式

**LSM-tree**（Log-Structured Merge-tree）は、追記型ログのアイデアを発展させて、範囲検索もできるようにしたものです。RocksDB、LevelDB、Cassandra などが使っています。

```
  書き込み → [WAL に追記] + [memtable (メモリ上のソート済みの表)]
                                   │ 一杯になったら
                                   ▼
             [SSTable] [SSTable] [SSTable] ...  ← ディスク上のソート済みファイル（書き換えない）
                                   │ 裏で
                                   ▼
                          コンパクション（マージして古い値を捨てる）
```

- 書き込みは、メモリ上の **memtable**（キーの順に並んだ表）に入れるだけです。クラッシュに備えて、WAL にも追記します
- memtable が一杯になったら、ソート済みのファイル（**SSTable**）としてディスクにまとめて書き出します。**シーケンシャル書き込み**だけで済みます
- 読み出しは、memtable → 新しい SSTable → 古い SSTable の順に探します。そのままだと遅いので、「このファイルにはそのキーが確実に無い」ことを高速に判定できる**ブルームフィルタ**を使って、無駄な読み込みを減らします
- 裏でコンパクションをして、SSTable をマージし、古い値やトゥームストーンを捨てます

## 8. ⭐ 3つの「増幅」: ストレージエンジンを比べる物差し

| 増幅 | 意味 |
|---|---|
| **書き込み増幅** | アプリが書いたデータ量に対して、実際にディスクに書いた量が何倍か（コンパクションや WAL の分だけ増える） |
| **読み出し増幅** | 1回の読み出しで、ディスクを何回（何バイト）読むか |
| **空間増幅** | 生きているデータの量に対して、ディスクを何倍使っているか（古い値やゴミの分だけ増える） |

この3つを同時に最小にすることはできない、というのが経験則です（研究では RUM 予想と呼ばれます）。

| 方式 | 書き込み | 読み出し | 範囲検索 | 空間 | 代表例 |
|---|---|---|---|---|---|
| 追記型ログ + ハッシュ | ◎ | ◎ | ✕ | △（コンパクションまでゴミが残る） | Bitcask |
| B-tree + WAL | ○ | ◎ | ◎ | ○ | SQLite, PostgreSQL, InnoDB |
| LSM-tree | ◎ | ○ | ◎ | ○ | RocksDB, LevelDB, Cassandra |

**選球眼の題材**: 「書き込みが圧倒的に多いログ収集」と「読み出しが中心の商品カタログ」では、向いている方式が違います。
Rust のエコシステムにも、B-tree 系（`redb` など）と LSM-tree 系（`fjall` など）の組み込みデータベースがあります。選ぶときは、まず自分のワークロードが「書き込み中心か、読み出し中心か、範囲検索が必要か」を考えましょう。

## 9. p02 との対応

| p02 のマイルストーン | このドキュメントの節 |
|---|---|
| M2: 永続化（追記型ログ） | 2. 追記型ログ |
| M3: インデックス | 3. ハッシュインデックス |
| M4: コンパクション（途中で落ちても壊れない） | 4. クラッシュへの耐性、5. コンパクション |
| M5: フォーマットの比較 | 2. のフォーマット（自作のバイナリ形式 vs serde の各形式） |

実験の `append_log.rs` は、p02 の答えそのものではありません。エラー処理は最小限で、CRC もなく、並行アクセスも考えていません。**実験のコードを写すのではなく、ここに書いた理由を理解してから、自分で設計してください。**
