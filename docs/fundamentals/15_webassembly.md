# 15. WebAssembly の仕組み

```bash
node stages/s17_wasm/host/handmade.mjs                    # WASM をバイト列から手で組み立てる
cargo build -p s17_wasm --target wasm32-unknown-unknown --release
cargo run -p fundamentals --example wasm_inspect           # .wasm の中身を読む
```

最初のコマンドには Node.js が、2つ目には `rustup target add wasm32-unknown-unknown` が必要です。
この章は [Stage 17](../../stages/s17_wasm/README.md) の土台です。

## 1. WebAssembly とは何か

**WebAssembly**（略して WASM）は、**どの CPU でも動く、機械語に近い命令の形式**です。

普通、Rust のプログラムはその CPU 専用の機械語にコンパイルされます（CS基礎 10）。
Apple M4 向けにコンパイルしたバイナリは、Intel の CPU では動きません。OS が違っても動きません。

WASM は、特定の CPU の機械語ではなく、**架空の CPU の機械語**のようなものです。
実際に動かすときは、ブラウザや Node.js などの**ランタイム**が、WASM の命令を自分の CPU の機械語に変換して実行します。

```
  Rust / C / C++ / Go ...
          │ コンパイル
          ▼
   .wasm ファイル（どの CPU でも同じファイル）
          │ ランタイムが、その場で自分の CPU の機械語に変換する
          ▼
  ┌──────────────┬──────────────┬──────────────┬──────────────┐
  │ ブラウザ     │ Node.js      │ wasmtime     │ エッジの     │
  │ (Chrome など)│              │ (単体のランタイム) │ サーバ       │
  └──────────────┴──────────────┴──────────────┴──────────────┘
```

名前に Web と付いていますが、ブラウザ専用ではありません。
2017年に主要なブラウザで使えるようになり、2019年には W3C（Web の標準を決める団体）の正式な勧告になりました。

**Java のバイトコードと何が違うのか**: 考え方は似ていますが、WASM は GC やクラスの仕組みを最初は持たず、**とても小さく、低レベルに**作られています。
「メモリはただのバイト配列」「型は数値だけ」という割り切りのおかげで、C や Rust のような言語をそのまま載せられます。

## 2. ⭐ 一番小さな WASM を、手で組み立てる

`handmade.mjs` は、コンパイラを使わずに、バイト列を直接書いて WASM のモジュールを作ります。作るのは、2つの `i32` を足す関数1つだけです。

```
モジュールの大きさ: 41 バイト
WebAssembly.validate: true
add(2, 3) = 5
add(2147483647, 1) = -2147483648
0x6a → 0x6c に書き換えると: add(6, 7) = 42  ← 掛け算になった
```

41 バイトの中身はこうなっています。

```
00 61 73 6d  01 00 00 00              ヘッダ: "\0asm" とバージョン 1
01 07  01 60 02 7f 7f 01 7f           type セクション:     (i32, i32) -> i32 という型が 1 つ
03 02  01 00                          function セクション: 関数が 1 つ。その型は 0 番
07 07  01 03 61 64 64 00 00           export セクション:   "add" という名前で、0 番の関数を公開する
0a 09  01 07 00 20 00 20 01 6a 0b     code セクション:     関数の本体
                       │     │  │  │
                       │     │  │  └ 0b = end
                       │     │  └ 6a = i32.add
                       │     └ 20 01 = local.get 1（引数 1 を積む）
                       └ 20 00 = local.get 0（引数 0 を積む）
```

WASM のファイルは、**ヘッダの後に「セクション」が並んでいるだけ**です。
各セクションは `[セクションの番号][中身のバイト数][中身]` という形をしています。

最後の行に注目してください。**`i32.add` という命令は、`0x6a` という 1 バイト**です。
これを `0x6c`（`i32.mul`）に書き換えると、足し算が掛け算になりました。命令は本当にただのバイトなのです。

同じ内容を、人間が読みやすいテキストで書いたものが **WAT**（WebAssembly Text format）です。

```wat
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))
```

### Rust でビルドした WASM と比べる

Rust で同じ関数を書いて、release ビルドと strip（§10 で説明します）をすると、116 バイトになりました。

```rust
#[unsafe(no_mangle)]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    a.wrapping_add(b)
}
```

```
00000000: 0061 736d 0100 0000 0107 0160 027f 7f01  .asm.......`....
00000010: 7f03 0201 0004 0501 7001 0101 0503 0100  ........p.......
00000020: 1006 1903 7f01 4180 80c0 000b 7f00 4180  ......A.......A.
00000030: 80c0 000b 7f00 4180 80c0 000b 072b 0406  ......A......+..
00000040: 6d65 6d6f 7279 0200 0361 6464 0000 0a5f  memory...add..._
00000050: 5f64 6174 615f 656e 6403 010b 5f5f 6865  _data_end...__he
00000060: 6170 5f62 6173 6503 020a 0901 0700 2001  ap_base....... .
00000070: 2000 6a0b                                 .j.
```

最後の行に `20 01 20 00 6a 0b` があります。手で書いたものとほとんど同じです（足す順番が逆なのは、足し算はどちらから足しても同じなので、コンパイラが自由に選んだためです）。
手で書いたものより 75 バイト多いのは、Rust がメモリ（`memory`）と、メモリの配置を表す変数（`__data_end`, `__heap_base`）も用意して export しているからです。

`wasm_inspect` で見ると、セクションの一覧が分かります。

```
  番号 名前             バイト数  中身
   1 type              7  1 個
   3 function          2  1 個
   4 table             5
   5 memory            3
   6 global           25
   7 export           43  memory (メモリ), add (関数), __data_end (グローバル変数), __heap_base (グローバル変数)
  10 code              9  1 個
```

**セクションの大きさを表す数値は LEB128 という形式**で書かれています。1 バイトのうち下位 7 ビットが値で、最上位ビットが「次のバイトに続くか」を表します。
小さい数は 1 バイトで済むので、ファイルが小さくなります。UTF-8 と同じように、**よく使う小さい値ほど短く表す**という発想です（CS基礎 05）。

## 3. スタックマシン

`local.get 0; local.get 1; i32.add` という命令の並びを見て、「足す相手を指定していない」と思ったかもしれません。
WASM は**スタックマシン**です。命令は、値を**スタック**に積んだり、スタックから取り出したりして計算します。

`add(2, 3)` を実行するときの様子です。

```
命令              スタック（右が一番上）
                  [ ]
local.get 0       [ 2 ]          ← 引数 0 を積む
local.get 1       [ 2, 3 ]       ← 引数 1 を積む
i32.add           [ 5 ]          ← 2 つ取り出して足し、結果を積む
end               → 5 を返す     ← 最後にスタックに残った値が戻り値
```

（ここでいうスタックは、命令が計算に使う作業場所のことです。CS基礎 03 の、関数のローカル変数を置くスタックとは別物です。）

**本物の CPU はスタックマシンではありません。** CPU は**レジスタ**（CPU の中にある、ごく少数の高速な記憶場所）を名前で指定して計算します。

```
Apple M4 (arm64) の場合:  add w0, w0, w1     ← 「w0 と w1 を足して w0 に入れる」とレジスタを名前で指定する
WASM の場合:              i32.add            ← 相手はスタックの上 2 つ、と決まっているので指定しない
```

**なぜ WASM はスタックマシンなのか**

- **命令が短くなる**: 足す相手を書かなくてよいので、`i32.add` は 1 バイトで済みます。ネットワークで送るファイルなので、小さいことが重要です
- **CPU の種類に依存しない**: CPU によってレジスタの数は違います。スタックマシンなら、レジスタが何個あるかを気にせずに書けます
- **検証しやすい**: 「この命令の時点でスタックに `i32` が 2 つあるか」を、実行する前に機械的に確かめられます。`WebAssembly.validate` がやっているのがこれです

ランタイムは、実行する前に、スタックの操作をレジスタの操作に変換します。だから、実際に動くときはスタックマシンとしての遅さはありません。

## 4. 型は 4 つしかない

WASM の値の基本的な型は、次の 4 つです。

| 型 | 中身 |
|---|---|
| `i32` | 32 ビットの整数 |
| `i64` | 64 ビットの整数 |
| `f32` | 32 ビットの浮動小数点数（CS基礎 02） |
| `f64` | 64 ビットの浮動小数点数 |

（後から拡張として、SIMD 用の `v128` や、関数や外部のオブジェクトを指す参照型が追加されています。）

文字列も、構造体も、配列も、`bool` もありません。Rust の型は、全てこの 4 つのどれかで表されます。

| Rust | WASM |
|---|---|
| `i32`, `u32`, `bool`, `char`, ポインタ, `usize` | `i32` |
| `i64`, `u64` | `i64` |
| `f32` / `f64` | `f32` / `f64` |
| `&str`, `String`, `Vec`, 構造体 | **メモリに置いて、ポインタ（`i32`）で指す** |

### 符号は、型ではなく命令が持っている

`i32` には、符号付き・符号なしの区別がありません。区別が必要な計算では、**命令の側**が2種類あります。

| 計算 | 符号付きとして | 符号なしとして |
|---|---|---|
| 割り算 | `i32.div_s` | `i32.div_u` |
| 大小の比較 | `i32.lt_s` | `i32.lt_u` |
| 右シフト | `i32.shr_s` | `i32.shr_u` |
| **足し算** | `i32.add`（1つだけ） | |

足し算が1つしかないのは、CS基礎 01 で学んだとおり、**2の補数では、符号付きでも符号なしでも、足し算のビット操作は同じ**だからです。
Rust の `u32` の割り算は `i32.div_u` に、`i32` の割り算は `i32.div_s` にコンパイルされます。

## 5. ⭐ 線形メモリ — ただのバイト配列

WASM のモジュールは、**線形メモリ**という1つの大きなバイト配列を持っています。

```
線形メモリ（Stage 17 のモジュールの場合）
0                    約 1 MiB                                          1114112
├────────────────────┼──────────────┼───────────────────────────────────┤
│ スタック           │ データ       │ ヒープ（alloc で確保する場所）    │
│ (関数のローカル変数) │ (文字列定数など) │                                   │
└────────────────────┴──────────────┴───────────────────────────────────┘
                     ↑__data_end = 1050277      足りなくなったら、後ろに伸ばす →
```

（この配置は、Stage 17 のモジュールが export している `__data_end` と `__heap_base` の値から読み取ったものです。）

- **大きさはページ単位**です。1 ページは 64 KiB（65536 バイト）。Stage 17 のモジュールは 17 ページ（1114112 バイト）で始まりました
- **伸ばすことはできますが、縮めることはできません**（`memory.grow` という命令）
- **範囲外にアクセスすると、トラップ**（即座に実行が止まる）になります。線形メモリの外を読み書きすることは、決してできません
- **ポインタは、この配列の先頭からのオフセット（何バイト目か）にすぎません**。wasm32 では 32 ビットなので、最大 4 GiB まで扱えます

CS基礎 03 で「メモリは番号の付いた巨大なバイトの配列」と説明しました。WASM の線形メモリは、**それをそのまま、小さく区切って渡したもの**です。
ネイティブのプログラムは OS が管理する仮想メモリ（CS基礎 13）の上で動きますが、WASM のプログラムは、この1つのバイト配列の中だけで動きます。

JavaScript からは、このバイト配列をそのまま読み書きできます。

```js
const bytes = new Uint8Array(wasm.memory.buffer);  // 線形メモリ全体を、バイト配列として見る
bytes[1114120] = 0x68;                             // 1114120 バイト目に 'h' を書く
```

WASM の関数に文字列を渡すには、「メモリに書いておいて、場所と長さを数値で渡す」しかありません。これを Stage 17 の ex02 で実際にやります。

## 6. ⭐ サンドボックスと import / export

普通のプログラムは、システムコール（CS基礎 13）で OS に頼めば、ファイルもネットワークも時刻も使えます。
**WASM のモジュールは、何もできません。** できるのは、

- 自分の線形メモリの中で計算すること
- ホスト（WASM を動かしている側）が **import として渡してくれた関数**を呼ぶこと

だけです。ファイルを読む命令も、画面に出力する命令も、時刻を得る命令も、WASM の命令の中には**存在しません**。

```
          ホスト（ブラウザ / Node.js / wasmtime）
     ┌──────────────────────────────────────────────┐
     │  渡すと決めたものだけを、import として渡す       │
     │     env.host_log  ─────┐                      │
     │     env.host_random ───┤                      │
     │                        ▼                      │
     │   ┌──────────────────────────────┐            │
     │   │ WASM モジュール                │            │
     │   │  ・線形メモリの中だけで計算する   │            │
     │   │  ・import されたもの以外は、     │            │
     │   │    呼ぶ手段がない              │ ──→ export  │
     │   └──────────────────────────────┘    (add, ...) │
     └──────────────────────────────────────────────┘
```

Stage 17 を解き終えたモジュールを `wasm_inspect` で見ると、import は2つだけです。

```
   2 import           34  env.host_log (関数), env.host_random (関数)
```

このモジュールが外の世界に影響を与えられるのは、ホストが渡したこの2つの関数を通してだけだと、**ファイルを見るだけで確かめられます**。

このように「**持っている権限を、明示的に渡されたものだけに限る**」設計を、**ケイパビリティ**（capability。能力・権限）ベースのセキュリティと呼びます。
ネイティブのプログラムは「禁止されていないことは何でもできる」のに対して、WASM は「**渡されたこと以外は何もできない**」のです。
これが、信頼できないコード（他人の書いたプラグインなど）を WASM で動かす理由です。

**ただし**: サンドボックスが守るのは**ホスト**です。WASM の中で二重解放などのバグがあれば、その線形メモリの中のデータは普通に壊れます（Stage 17 の README §5）。

## 7. JavaScript と WASM の境界のコスト

JavaScript から WASM の関数を呼ぶとき、そして WASM から JavaScript の関数を呼ぶときには、**境界を越えるコスト**がかかります。

Stage 17 の `bench.mjs` で測った結果です（Apple M4、Node.js v24。2回実行して、傾向は同じでした）。

| 実験 | JavaScript | WASM | |
|---|---|---|---|
| 中身がほぼ空の `add` を 1000 万回呼ぶ | 3.2 ms | 15.5 ms | **WASM が約5倍遅い** |
| `is_prime` を 1〜300 万で呼ぶ | 305.4 ms | 192.6 ms | WASM が約1.6倍速い |
| 約 10MB の文字列の文字数を数える | 24.3 ms | 15.7 ms（うちコピー 9.7 ms） | 速いが、**時間の6割はコピー** |

**1つ目**: JavaScript の JIT コンパイラは、小さな JavaScript の関数を呼び出し元に埋め込み（インライン化。CS基礎 10）、呼び出しのコストを消せます。
WASM の関数の呼び出しは境界を越えるので、それができません。

**3つ目**: JavaScript の文字列は、内部では UTF-8 ではありません（CS基礎 05）。WASM に渡すには、UTF-8 に変換して、線形メモリにコピーする必要があります。
**データを渡すたびにコピーが起きる**ことは、WASM を使う設計で一番効いてくるコストです。

## 8. ⭐「WASM は JavaScript より速い」の正しい理解

「WASM は速い」は、半分だけ正しい言い方です。

| WASM が有利になりやすい | WASM が不利になりやすい |
|---|---|
| 1回の呼び出しの中で、大量に計算する | 小さな関数を何度も呼ぶ |
| データを一度渡したら、中で何度も使う | 大きなデータを、毎回コピーして渡す |
| 速さが**安定していてほしい** | DOM を操作する（JavaScript からしか触れない） |

**速さが安定する理由**: JavaScript の JIT は、実行しながら「この変数はいつも数値だ」と推測して最適化します。推測が外れると、最適化をやり直します。GC による一時停止もあります。
WASM は型が最初から決まっていて、GC もない（Rust の場合）ので、こうした揺れが起きにくいのです。ゲームや音声処理のように、**たまに遅くなることが許されない**用途では、平均の速さよりこちらが重要です。

**JavaScript は遅くない**: 実験 2 でも、差は 1.6 倍でした。現代の JavaScript エンジンはとても速いです。
「WASM にすれば何倍も速くなる」と期待する前に、選球眼 05 のとおり、**ボトルネックを計測すること**が先です。

## 9. ブラウザの外の WASM: WASI とコンポーネントモデル

ブラウザの外（サーバ、エッジ、コマンドライン）で WASM を動かすときも、ファイルや時刻は必要です。
しかし、ランタイムごとに import する関数の名前や形がバラバラだと、同じ .wasm を別のランタイムで動かせません。

**WASI**（WebAssembly System Interface）は、「ファイルを開く」「時刻を得る」「乱数を得る」といった機能を、**標準の import として決めたもの**です。
OS のシステムコール（CS基礎 13）に相当するものを、WASM 向けに標準化したと考えてください。ただし、ケイパビリティの考え方は変わりません。
例えば wasmtime で動かすときは、「このディレクトリだけ読んでよい」とランタイムに指定しない限り、ファイルには一切触れません。

**コンポーネントモデル**は、WASM のモジュール同士を、**数値だけでなく文字列や構造体などの型でつなぐ**ための仕組みです。
WIT という言語でインターフェース（どんな関数が、どんな型を受け取るか）を書くと、言語の違うモジュール同士でも、文字列のコピーなどを自動で行ってつなげます。
Stage 17 で手でやる「メモリに書いてポインタを渡す」作業を、標準のやり方として決めたもの、と言えます。2024年には、コンポーネントモデルの上に作られた WASI 0.2 が公開されました。

Rust のターゲット名にも、これが表れています。

| ターゲット | 意味 |
|---|---|
| `wasm32-unknown-unknown` | OS も WASI もない。必要なものは全部ホストが import で渡す（Stage 17） |
| `wasm32-wasip1` | WASI の初期の版（preview 1）を使う |
| `wasm32-wasip2` | WASI 0.2（コンポーネントモデル）を使う |

## 10. なぜ Rust は WASM でよく使われるのか

WASM は C、C++、Go、C#、Kotlin などからも作れます。その中で Rust がよく選ばれる理由は、**ランタイムを持たないこと**です。

- **GC がない**: GC のある言語は、GC そのものを .wasm の中に含めて送る必要があります。Rust は所有権でメモリを管理するので（Stage 02）、それが要りません
  （近年は、ブラウザの GC を WASM から使える WasmGC という拡張が主要なブラウザで使えるようになり、GC のある言語でも小さくしやすくなってきています）
- **大きなランタイムがない**: Go のように、スレッドのスケジューラなどの仕組みを含める必要もありません
- **使わない機能は入らない**: 最適化とリンクの段階で、使われていないコードは取り除かれます。`add` だけなら 116 バイトでした

### 何が .wasm を大きくしているのか

```
    670 バイト  _RNvMsa_NtCsgXGp5Oqx2Ny_4core3fmtNtB5_9Formatter3pad
    628 バイト  _RNvNtCsgXGp5Oqx2Ny_4core3fmt5write
    566 バイト  _RNvMs0_NtCsjqx8TIyZbP9_8dlmalloc8dlmallocINtB5_8DlmallocNtNtB7_3sys6SystemE13dispose_chun
    447 バイト  fizzbuzz_log
    421 バイト  _RNvNvNtCs5cOc02OMXlo_5alloc3fmt6format12format_inner
```

（`_RNv...` という読みにくい名前は、マングリングされた関数名です。Stage 17 の README §2 を参照してください。）

自分で書いた関数は十数個なのに、85 個の関数が入っています。大きいものは、

- **`dlmalloc`**: メモリアロケータ（`malloc` / `free`）。`Vec` や `String` を使うと、ヒープを管理する仕組みが必要になり、丸ごと含まれます
- **`core::fmt`**: `format!` や `to_string()` で使う、文字列の整形の仕組み
- **`from_utf8`, `count_chars`**: 標準ライブラリの UTF-8 の処理（コードリーディング 03 で読んだもの）

つまり、**ヒープと文字列の整形を使った瞬間に、数 KB が増える**のです。
小さな WASM が必要なときは、「`format!` を使わない」「アロケータを使わない」といった工夫をすることがあります。

### ビルドの設定と、ファイルの大きさ

Stage 17 の解答を、設定を変えてビルドした結果です。

| 設定 | 大きさ (バイト) |
|---|---|
| debug | 1,730,182 |
| release | 25,640 |
| release + `strip = true` | 19,599 |
| release + strip + `opt-level = "z"` | 20,255 |
| release + strip + `opt-level = "z"` + `lto = true` + `codegen-units = 1` + `panic = "abort"` | 20,205 |

- **debug が 1.7 MB もある理由**: `wasm_inspect` で見ると、`.debug_info`（約 44 万バイト）や `.debug_str`（約 85 万バイト）などのデバッグ情報のセクションがほとんどです。デバッガのための情報で、実行には使われません
- **strip** は、関数名（`name` セクション、5808 バイト）などの実行に要らない情報を取り除きます
- **`opt-level = "z"`（サイズ優先の最適化）にしたら、逆に大きくなりました**。どの最適化が効くかは、コードによって違います。「サイズ優先と書いてあるから小さくなるはず」と思い込まず、**計測して確かめること**（選球眼 05）

### WASM の先頭の 8 バイト

どの .wasm ファイルも、同じ 8 バイトで始まります。

```
00000000: 0061 736d 0100 0000 ...  .asm....
```

- `00 61 73 6d` = `\0asm`。**マジックナンバー**と呼ばれ、ファイルの種類を見分けるための印です（PNG なら `89 50 4E 47`、Mac の実行ファイルなら `CF FA ED FE` で始まります）
- `01 00 00 00` = バージョン 1。リトルエンディアン（小さい桁のバイトが先）の 32 ビット整数です（CS基礎 14）
