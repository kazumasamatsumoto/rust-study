# クレートの選び方

Rust の標準ライブラリは意図的に小さく作られています。非同期ランタイム、JSON、HTTP、CLI の引数解析などは**全て外部のクレート**です。
そのため、どのクレートを選ぶかを判断する力が、そのまま実力の一部になります。

## なぜ標準ライブラリが小さいのか

標準ライブラリに入ると、互換性を守るために API を永久に変えられなくなります。Python の `urllib` が `requests` に置き換えられたように、標準に入ったものが時代遅れになることはよくあります。
Rust は「標準は小さく安定させ、改良はエコシステムに任せる」という方針を選びました。**その代わり、利用者が選ぶ責任を負います。**

## 評価のチェックリスト

| 観点 | 確認方法 | 危険信号 |
|---|---|---|
| メンテナンス | GitHub の最終コミット、Issue への反応 | 1年以上更新がない、Issue が放置されている |
| 利用実績 | crates.io の Downloads、Dependents | 利用者が少なく、作者1人しか使っていない |
| ドキュメント | docs.rs、examples ディレクトリ | 例がない、API の説明がない |
| 依存の重さ | `cargo tree -p <crate>` | 小さな機能のために依存が数十個増える |
| `unsafe` の量 | ソースで `unsafe` を検索する、`cargo geiger` | 理由の説明がない `unsafe` が多い |
| セキュリティ | `cargo audit`（RustSec のデータベース） | 既知の脆弱性がある |
| ライセンス | `cargo deny check licenses` | GPL など、自分のプロジェクトと合わない |
| 安定性 | バージョンが 1.0 以上か、CHANGELOG | 0.x で破壊的変更が頻繁にある |

## 定番のクレートと、それが選ばれる理由

| 用途 | 定番 | 選ばれる理由 | 他の候補 |
|---|---|---|---|
| シリアライズ | `serde` | 事実上の標準。ほぼ全てのフォーマットが対応している | (ほぼない) |
| 非同期ランタイム | `tokio` | エコシステムの大半が tokio を前提にしている | `smol`（小さい） |
| CLI の引数 | `clap` | 機能が豊富で、derive で書ける | `argh`, `lexopt`（軽量） |
| エラー（アプリ） | `anyhow` | 文脈の付け足しが楽 | `eyre`（表示をカスタマイズできる） |
| エラー（ライブラリ） | `thiserror` | 独自エラー型を簡潔に書ける | 手で書く |
| HTTP クライアント | `reqwest` | 使いやすい | `ureq`（同期処理で軽量） |
| Web フレームワーク | `axum` | tokio 公式。tower のエコシステムを使える | `actix-web` |
| DB | `sqlx` | SQL をコンパイル時に検証できる | `diesel`（ORM）, `sea-orm` |
| ログ・トレース | `tracing` | 非同期処理でも文脈を追える | `log` + `env_logger` |
| 並列計算 | `rayon` | `.iter()` を `.par_iter()` に変えるだけで並列になる | 手でスレッドを書く |

**表を覚えることが目的ではありません。** 「なぜそれが定番なのか」を、上のチェックリストで自分で確かめられることが目的です。

## 依存を増やさないという選択肢

小さな関数1つのためにクレートを追加すると、ビルド時間、セキュリティのリスク、メンテナンスのコストが増えます。
「この依存は自分で書くと何行になるか？」と考えて、数十行で書けるなら自分で書くのも立派な判断です。
