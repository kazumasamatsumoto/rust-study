# ADR（Architecture Decision Record）の書き方

ADR は「**なぜその技術・設計を選んだのか**」を記録する短い文書です。
半年後の自分やチームメイトが「なぜこうなっているのか」と疑問に思ったときの答えになります。

Part 3 のプロジェクトでは、主要な判断ごとに ADR を書いてもらいます（`projects/<name>/docs/adr/` に置きます）。

## テンプレート

```markdown
# ADR-001: <決めたことを一文で>

- 日付: YYYY-MM-DD
- 状態: 提案 / 採用 / 廃止 / ADR-00X に置き換え

## 背景
何に困っているのか。どんな制約があるのか（性能、期限、チームのスキル）。

## 検討した選択肢
### 案A: ...
- 長所:
- 短所:
### 案B: ...
- 長所:
- 短所:

## 決定
案X を採用する。

## 理由
何を優先したのか。なぜ他の案を選ばなかったのか。

## 結果・影響
この決定によって何が楽になり、何が難しくなるのか。どうなったら見直すのか。
```

## 良い ADR のコツ

- **選択肢は最低2つ書く。** 1つしか書けないなら、それは判断ではなく思い込みです。
- **「見直す条件」を書く。** 例:「ユーザーが1万人を超えたら DB を見直す」
- **短く書く。** 1ページに収まらないなら、決めることを分けましょう。

## 例

```markdown
# ADR-001: CLI の引数解析に clap を使う

- 日付: 2026-11-01
- 状態: 採用

## 背景
logscope はサブコマンドが3つあり、オプションも10個以上ある。ヘルプの自動生成が欲しい。

## 検討した選択肢
### 案A: clap (derive)
- 長所: ヘルプや補完を自動で生成できる。定番なので情報が多い
- 短所: コンパイル時間が延び、バイナリが大きくなる
### 案B: lexopt
- 長所: 依存がなく軽量
- 短所: ヘルプやバリデーションを全て自分で書く必要がある
### 案C: std::env::args を手で解析
- 長所: 依存ゼロ
- 短所: サブコマンドが増えるとすぐに破綻する

## 決定
案A を採用する。

## 理由
バイナリのサイズよりも、ヘルプの品質と開発の速さを優先した。学習目的でも、実務で定番の構成に触れておく価値がある。

## 結果・影響
ビルド時間は数秒延びる。バイナリサイズが問題になったら lexopt を再検討する。
```
