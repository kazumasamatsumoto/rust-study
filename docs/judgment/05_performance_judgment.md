# 05. 性能の判断 — いつ、何を、どれだけ速くするか

> **前提**: CS基礎 06（計算量）、09（I/O と非同期）、10（コンパイルと最適化）を読んでいること。
> **関係するところ**: [01 Rust を選ぶべき時](01_when_to_use_rust.md)、p01〜p04 の非機能要件

「Rust は速い」とよく言われます。それは事実ですが、**速いプログラムを書けるかどうかは、言語よりも判断で決まります**。
このドキュメントでは、性能について「いつ気にするべきか」「何から手を付けるべきか」を判断するための考え方を学びます。

---

## 1. 「速い」とは何のことか

「速くしたい」と言うとき、実はいくつかの違うものを指しています。

| 指標 | 意味 | 例 |
|---|---|---|
| **レイテンシ**（latency） | 1つの処理が終わるまでの時間 | API が応答を返すまで 50ms |
| **スループット**（throughput） | 一定時間に処理できる量 | 1秒間に 1万リクエストを処理できる |
| **テールレイテンシ**（p99 など） | 遅い方から 1% の処理にかかる時間 | 99% のリクエストは 100ms 以内に返る |
| **リソースの使用量** | CPU、メモリ、ネットワークの使用量 | メモリ 200MB で動く。サーバ代が月 X 円 |

これらは、互いにトレードオフの関係にあることがよくあります。

- まとめて処理する（バッチ処理）と**スループットは上がる**が、1件ごとの**レイテンシは悪くなる**
- キャッシュを使うと**レイテンシは下がる**が、**メモリを多く使う**
- p03 の HTTP サーバでスレッド数を増やすと、ある程度までは**スループットが上がる**が、増やしすぎると切り替えのコストで逆に悪くなる（CS基礎 08）

**p99 が大事な理由**: 平均が 20ms でも、100回に1回 2秒かかるなら、ユーザーは「たまに固まるアプリ」だと感じます。そして1つの画面を表示するのに裏で API を 10 回呼ぶなら、どれか1つが遅い確率は 10 倍近くになります。
[01](01_when_to_use_rust.md) で紹介した Discord の事例は、平均ではなく **GC によるレイテンシのスパイク**（テールレイテンシ）が問題でした。

## 2. いつ最適化するべきか

### 「早すぎる最適化」

計算機科学者の Donald Knuth は、1974年の論文で次のように書いています。

> We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%.
>
> （小さな効率のことは、97% くらいの場面では忘れるべきだ。早すぎる最適化は諸悪の根源である。とはいえ、決定的に重要な残りの 3% の機会を逃してはならない。）

前半だけが有名ですが、**後半も大事**です。「最適化するな」ではなく、「**重要な 3% を見極めて、そこに集中せよ**」という意味です。

### 最適化を始める前に決めること

1. **目標を数字で決める**: 「速くしたい」ではなく、「1GB のログを 10 秒以内に処理する」（p01 の非機能要件）のように決めます。目標がなければ、どこでやめればよいか分かりません
2. **今の状態を計測する**: 目標をすでに満たしているなら、最適化は不要です
3. **目標に届かないときだけ、最適化する**

## 3. ⭐ 計測 → 仮説 → 検証

性能の改善は、**科学の実験と同じ手順**で進めます。

```
  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ 1. 計測  │ ──→ │ 2. 仮説  │ ──→ │ 3. 検証  │ ──┐
  └──────────┘     └──────────┘     └──────────┘   │
       ↑                                           │
       └───────────────────────────────────────────┘
       目標に届くまで繰り返す
```

1. **計測**: どこに時間がかかっているのかを、ツールで調べる
2. **仮説**: 「この関数で毎回 `clone` しているのが遅いのではないか」
3. **検証**: 変更して、もう一度計測する。**速くならなければ、変更を元に戻す**

人間の勘は、性能についてはよく外れます。「ここが遅いはず」と思って最適化した箇所が、実は全体の 1% しか時間を使っていなかった、ということはよくあります。

### Rust で計測するときの注意

| 注意点 | 理由 |
|---|---|
| **必ず `--release` で計測する** | CS基礎 10 で見た通り、debug ビルドは release より何十倍も遅いことがあります。debug ビルドで計測した結果は、ほとんど意味がありません |
| コンパイラに処理を消されないようにする | 結果を使わない計算は、最適化で丸ごと消されることがあります。`std::hint::black_box` を使います（CS基礎 01 の `integers` の実験で使っていました） |
| 何回か実行する | 1回目はファイルが OS のキャッシュに載っていないなど、条件が違います。ばらつきも見ましょう |
| 本番に近いデータで計測する | 10 件のデータでは、O(n) と O(n²) の差は見えません |

### 使う道具

| 道具 | 用途 |
|---|---|
| `std::time::Instant` | 手軽に処理の時間を測る（`fundamentals/examples/` の実験で使ってきたもの） |
| `criterion` クレート | 統計的に信頼できるベンチマークを取る（p02 で使います） |
| プロファイラ（`cargo flamegraph`, `samply`, macOS の Instruments, Linux の `perf` など） | プログラムのどの関数に時間がかかっているかを調べる |

**プロファイラ**は、実行中のプログラムを一定の間隔で覗き、「今どの関数を実行しているか」を記録する道具です。どの関数に時間を使っているかの割合が分かります。結果を図にした**フレームグラフ**では、横幅が広い関数ほど時間を使っています。

## 4. ⭐ Amdahl の法則: 全体のどこを速くするべきか

**Amdahl の法則**は、「プログラムの一部だけを速くしたとき、全体がどれだけ速くなるか」を表す式です。

```
全体の速さの向上 = 1 / ((1 - p) + p / s)

  p: 速くする部分が、全体の時間に占める割合
  s: その部分を何倍速くするか
```

数式より、例で考える方が分かりやすいでしょう。

ある API のリクエストに 100ms かかっていて、計測すると内訳はこうでした。

| 処理 | 時間 |
|---|---|
| DB への問い合わせ | 80ms |
| JSON への変換 | 15ms |
| ビジネスロジック | 5ms |

**案A**: ビジネスロジックを Rust で書き直して、10 倍速くする
→ 80 + 15 + 0.5 = **95.5ms**（4.5% しか速くならない）

**案B**: DB にインデックスを張って、問い合わせを 2 倍速くする
→ 40 + 15 + 5 = **60ms**（40% 速くなる）

案Aでは、ビジネスロジックを**無限に速くしても**、95ms より速くはなりません。
**全体に占める割合が小さい部分を、どれだけ頑張って速くしても、全体はほとんど速くならない**のです。だからこそ、3節の「計測」が最初に必要です。

この法則は並列化（Stage 10）にも当てはまります。処理の 90% を並列化できても、残りの 10% が並列化できないなら、CPU をいくら増やしても 10 倍より速くはなりません。

## 5. ⭐ ボトルネックは I/O か CPU か

CS基礎 09 で計測した数字を、もう一度見てみましょう。

| 処理 | 時間（CS基礎 09 の実験と目安） |
|---|---|
| メモリから連続して読む | 1ns 未満 |
| ファイルを開いて読む（OS のキャッシュに載っている） | 約 10µs |
| 同じデータセンター内の通信 | 約 0.5ms（目安） |
| 東京 ↔ アメリカ西海岸の通信 | 約 100ms（目安） |

ボトルネック（全体の速さを決めている、一番遅い部分）は、大きく2種類に分かれます。

| | **CPU バウンド** | **I/O バウンド** |
|---|---|---|
| 意味 | 計算に時間がかかっている | 待ち時間（ディスク、ネットワーク、DB）に時間がかかっている |
| 見分け方 | 遅いあいだ、CPU の使用率が 100% 近い | 遅いのに、CPU はほとんど使われていない |
| 例 | 画像処理、圧縮、大量のデータの集計、暗号 | Web API、DB を使うアプリ、ファイルのコピー |
| 効く対策 | アルゴリズムの改善、並列化、**言語の変更（Rust 化）** | 待つ回数を減らす（まとめる、キャッシュ）、待っているあいだに他のことをする（async） |

**典型的な Web アプリの多くは I/O バウンド**です。その場合、ロジックを Rust で書き直しても、4節の案Aのように、ほとんど速くなりません。
async（Stage 11）も、1つのリクエストのレイテンシを短くするわけではありません。**待っているあいだに他のリクエストを処理できるので、スループットが上がる**のです。

## 6. ⭐「Rust だから速い」の誤解

Rust で書いても、次のようなコードは遅くなります。以下の数値は、rustc 1.95.0、Apple Silicon（arm64）、release ビルドで計測したものです。

### 誤解1: 言語が速ければ、アルゴリズムは何でもよい

```
== 重複を探す (n = 20000) ==
二重ループ O(n^2)   : 13.135708ms
HashSet O(n)        : 435.209µs
```

n = 2万でも 30 倍の差です。n が 10 倍になれば、二重ループの時間は 100 倍になります（CS基礎 06）。
Python で O(n log n) で書いたプログラムが、Rust で O(n²) で書いたプログラムより速い、ということは普通に起こります。**言語の差は定数倍、アルゴリズムの差は桁違い**です。

### 誤解2: I/O の回数は気にしなくてよい

```
== ファイルに 100000 行書く ==
File に直接書く     : 317.473291ms
BufWriter を通して書く: 1.992584ms
```

約 160 倍の差です。`File` に直接書くと、`writeln!` のたびに OS へのシステムコール（OS に処理を頼む呼び出し）が起きます。`BufWriter` は、データをメモリ上のバッファにためておき、まとめて書き出します。
**「1回あたりのコストが大きい処理（I/O）の回数を減らす」**のは、どの言語でも効く基本的な最適化です。p01 のログ解析でも、読み込み側で同じことが言えます（`BufReader`）。

### 誤解3: `clone` は気にしなくてよい

```
== clone の有無 (100000 個の String の長さの合計) ==
毎回 clone する     : 1.964875ms
借用だけで済ませる  : 33.625µs
```

約 60 倍の差です。`String` の `clone` は、ヒープの確保とコピーを伴います（CS基礎 03）。
所有権のエラーを `.clone()` で黙らせる癖がつくと、コードのあちこちでこのコストを払うことになります。

### 誤解4: 並列化すれば必ず速くなる

CS基礎 08 の実験では、4スレッドで 400万回カウントアップするのに、**共有のカウンタを Mutex で守ると約 600ms**、**スレッドごとに別々に数えて最後に合計すると約 1ms** でした。
共有データの奪い合い（競合）が起きると、並列化しても速くならないどころか、遅くなることすらあります。

### 誤解5: debug ビルドでも十分速い

CS基礎 10 で見た通り、イテレータを使ったコードは、debug ビルドでは release ビルドより約 70 倍遅いことがありました。「Rust なのに遅い」と思ったら、まず `--release` を付けているかを確かめましょう。

## 7. 改善の順番

効果が大きく、コードを壊しにくいものから順に試します。

| 順番 | 対策 | 例 |
|---|---|---|
| 1 | **不要な処理をやめる** | 使っていない計算、二重に読み込んでいるファイル |
| 2 | **アルゴリズムとデータ構造を見直す** | 線形探索を `HashMap` にする、O(n²) を O(n log n) にする |
| 3 | **I/O の回数を減らす** | `BufReader` / `BufWriter`、DB への問い合わせをまとめる、キャッシュ |
| 4 | **メモリの確保を減らす** | 不要な `clone` をやめる、`with_capacity`、バッファを使い回す |
| 5 | **並列化・非同期化** | `rayon`、async（競合に注意） |
| 6 | **細かい最適化** | ビルド設定の調整（`lto` など）、`unsafe` による検査の省略（最後の手段） |

下に行くほど、コードが複雑になり、バグを生みやすくなります。**上から順に試して、目標に届いたらそこでやめる**のが原則です。

## 8. ⭐ コストは実行時間だけではない

最適化にもコストがかかります。

| コストの種類 | 例 |
|---|---|
| **開発時間** | 最適化に 3 日かかる |
| **保守性** | 速いが読みにくいコードは、次に変更する人の時間を奪う。バグも入りやすい |
| **実行時間** | ユーザーの待ち時間、バッチ処理の時間 |
| **インフラの費用** | サーバの台数、メモリ、クラウドの請求額 |

例えば、1日1回だけ動くバッチ処理を、3日かけて 10 分から 9 分に短縮しても、その価値はあまりありません。
一方で、1秒間に 1万回呼ばれる関数を 1ms 速くできれば、サーバの台数を減らせるかもしれません。

**「この最適化で、誰の、どのコストが、どれだけ減るのか？」**を説明できるようにしましょう。それが説明できる最適化だけが、やる価値のある最適化です。
これは [01](01_when_to_use_rust.md) の「Rust を選ぶべきか」と、全く同じ問いです。
