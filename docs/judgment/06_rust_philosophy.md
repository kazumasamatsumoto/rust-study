# 06. Rust の歴史と思想 — なぜ Rust はこういう言語なのか

> **前提**: Part 1 のステージをいくつか終えていること。全部終えた後に読み直すと、また違って見えるはずです。

これまで、所有権、`Option`、`Result`、トレイト、`unsafe` といった Rust の仕組みを1つずつ学んできました。
このドキュメントでは、少し引いた視点から「**Rust はなぜこういう言語になったのか**」を見ていきます。

言語の設計には、それを作った人たちの価値観が表れます。その価値観を知っておくと、

- 新しい機能を見たときに「なぜこうなっているのか」を推測できる
- Rust が得意なこと・不得意なことを、理由とセットで説明できる（[01](01_when_to_use_rust.md)）
- コミュニティの議論や、ライブラリの設計の方向性が読めるようになる

---

## 1. 誕生: Mozilla とブラウザ

| 年 | 出来事 |
|---|---|
| 2006年 | Mozilla の社員だった Graydon Hoare が、個人のプロジェクトとして Rust の開発を始める |
| 2009年 | Mozilla が公式にプロジェクトを支援し始める |
| 2010年 | Rust が一般に公開される |
| 2015年5月15日 | **Rust 1.0** がリリースされる |
| 2017年 | Firefox 57（"Quantum"）に、Rust で書かれた CSS エンジン（Servo プロジェクトから生まれた "Stylo"）が搭載される |

### なぜブラウザの会社が新しい言語を作ったのか

ブラウザは、次のような条件がそろった、とても難しいソフトウェアです。

- **巨大**: 数百万〜数千万行の C++ のコード
- **速さが必要**: Web ページの表示が遅いと、ユーザーは離れていく
- **安全性が必要**: インターネット上の誰が作ったか分からないデータ（HTML、画像、JavaScript）を、毎日読み込む
- **並列化したい**: CPU のコア数が増えていく中で、ページの描画を並列にしたい

C++ は速いのですが、メモリ安全性のバグ（CS基礎 04）が脆弱性の大きな原因になっていました。そして**並列化は、メモリ安全性のバグをさらに増やします**（データ競合、CS基礎 08）。
Mozilla は、Rust で新しいブラウザエンジン **Servo** を開発し、「C++ と同じくらい速く、しかも安全に並列化できるか」を試しました。その成果の一部が、Firefox の CSS エンジンとして実際に使われることになったのです。

Rust の「**速さと安全性を両立させる**」という目標は、この現実の問題から生まれました。

### 1.0 までに捨てたもの

1.0 より前の Rust は、今とはかなり違う言語でした。初期の Rust には**ガベージコレクタ付きのポインタ**や、言語に組み込まれた**グリーンスレッド**（OS のスレッドではなく、言語の実行環境が管理する軽量なスレッド）がありました。
Rust の開発者たちは、1.0 までにこれらを**取り除きました**。

- GC をやめて、**所有権と借用だけで**メモリを管理することにした
- 実行環境（ランタイム）を持たず、**C と同じように、何も上乗せせずに動く**言語にした

その結果、Rust は OS のカーネルや組み込み機器のような、GC やランタイムを置けない場所でも使える言語になりました。
Stage 11 で「Rust には標準の非同期ランタイムがなく、tokio などを選ぶ」と学んだのも、この「ランタイムを言語に入れない」という決断の延長線上にあります。

## 2. ⭐ Rust の3つの柱

Rust の公式サイト（rust-lang.org）には、こう掲げられています。

> A language empowering everyone to build reliable and efficient software.
> （誰もが、信頼性が高く効率的なソフトウェアを作れるようにする言語）

そして、その特徴として **Performance（性能）**、**Reliability（信頼性）**、**Productivity（生産性）** の3つを挙げています。
これまで学んできたことを、この3つの柱で整理してみましょう。

| 柱 | 意味 | これまでに学んだこと |
|---|---|---|
| **性能** | 速く、メモリを少なく使う | GC がない（s02）、ゼロコスト抽象化（ツアー04）、単相化（CS基礎 07） |
| **信頼性** | バグをコンパイル時に見つける | 所有権と借用（s02）、`Option` で null をなくす（s03）、`Result` でエラーを無視させない（s04）、`Send`/`Sync` でデータ競合を防ぐ（s10） |
| **生産性** | 書きやすく、道具が揃っている | `cargo`、`rustfmt`、`clippy`、分かりやすいエラーメッセージ、`docs.rs` |

この3つは、普通は互いにトレードオフの関係にあります。速さを取れば安全性が下がり（C/C++）、安全性と書きやすさを取れば速さが下がる（GC 言語）。
**Rust は、「学習コスト」と「コンパイル時間」を払うことで、3つを同時に取ろうとしている言語**だと言えます（[01](01_when_to_use_rust.md) の弱みの表）。

## 3. ⭐ ゼロコスト抽象化

**ゼロコスト抽象化**（zero-cost abstractions）という考え方は、Rust が C++ から受け継いだものです。C++ の作者 Bjarne Stroustrup は、こう述べています。

> What you don't use, you don't pay for. And further: What you do use, you couldn't hand code any better.
> （使わないものには、コストを払わない。そして、使うものについても、手で書いた方が良くなる、ということはない。）

この2つの約束は、これまでの学習で何度も確かめてきました。

- **使わないものには払わない**: Rust には GC もランタイムもないので、使わなければそのコストはゼロ。`Rc` や `Mutex` のようなコストのかかる仕組みも、自分で選んだときだけ使う（s08、s10）
- **手で書いた方が良くなることはない**: イテレータは、手書きのループと同じ機械語になった（ツアー04の実験）。`Option<&T>` は、null になりうるポインタと同じ 8 バイトだった（CS基礎 03）

ただし、「ゼロコスト」なのは**実行時**のコストです。コンパイル時間と、言語の複雑さというコストは払っています。

## 4. ⭐ Fearless Concurrency（恐れずに並行処理を書く）

1.0 の頃（2015年）、Rust の公式ブログで "Fearless Concurrency" という言葉が紹介されました。

多くの言語で、並行処理は「上級者だけが、細心の注意を払って書くもの」とされています。データ競合は、テストで再現しにくく、本番環境でたまにしか起きないからです。

Rust のアプローチは、**所有権と借用のルールを、そのまま並行処理の安全性に使う**ことでした。

- 「共有するなら書き換えない、書き換えるなら共有しない」（s02）は、そのまま「データ競合を起こさない」ためのルールになっている
- `Send`（別のスレッドに送ってよい）と `Sync`（複数のスレッドから共有してよい）というトレイトで、スレッドをまたいでよい型かどうかを、コンパイラが検査する（s10）

並行処理の安全性のために、新しい仕組みを付け足したのではありません。**メモリ安全性のために作った仕組みが、そのまま並行処理の安全性にもなっていた**のです。
（ただし、防げるのはデータ競合です。デッドロックや、処理の順番に依存するバグ（競合状態）は防げません。s10 の `Bank::transfer` で体験した通りです。）

## 5. その他の設計思想

これまでの学習に繰り返し出てきた考え方を、まとめておきます。

| 思想 | 現れていたところ |
|---|---|
| **明示的であること**（暗黙より明示） | `mut`、`.clone()`、`unsafe`、`?`。コストや危険がある処理は、コードの上に見えるようにする（s01、s02） |
| **安全をデフォルトにし、抜け道も用意する** | 普段は安全な Rust。どうしても必要なときだけ `unsafe`。そしてそれを小さな範囲に閉じ込める（CS基礎 04、ツアー02） |
| **ありえない状態を表現できなくする** | null の代わりに `Option`、状態を enum で表す、`String` は必ず UTF-8（s03、ツアー03） |
| **エラーは値である** | 例外ではなく `Result`。失敗の可能性を型に表す（s04） |
| **コンパイラは先生である** | 分かりやすいエラーメッセージ。何が問題で、どう直せばよいかを教えてくれる |

## 6. ⭐ 安定性の約束: "Stability without stagnation"

Rust の開発チームは、1.0 のリリースの前に「**停滞なき安定**」（stability without stagnation）という方針を示しました。

- **安定**: 一度安定版になった機能は、壊さない。Rust 1.0 で書いたコードは、今の Rust でもコンパイルできることを目指す
- **停滞しない**: それでも、言語は進化し続ける

この2つを両立させるために、いくつかの仕組みがあります。

### リリーストレイン

Rust は **6週間ごと**に新しい安定版をリリースしています。このリポジトリで使っている 1.95.0 も、その1つです。

| チャンネル | 内容 |
|---|---|
| **nightly** | 毎晩ビルドされる開発版。不安定な機能（ツアーで見た `#[unstable]` など）を試せる |
| **beta** | 次の安定版の候補。6週間かけて問題がないかを確かめる |
| **stable** | 安定版。普段使うもの |

新しい機能は、まず nightly で試され、十分に検証されてから安定版に入ります。決まった周期で出すので、「大きなリリースに向けて無理に機能を詰め込む」ということが起きにくくなっています。

### エディション

「停滞しない」ためには、ときどき互換性のない変更（新しいキーワードの追加など）も必要になります。そのための仕組みが **エディション**（edition）です。

| エディション | 安定化されたバージョン |
|---|---|
| 2015 | Rust 1.0（最初のエディション） |
| 2018 | Rust 1.31 |
| 2021 | Rust 1.56 |
| 2024 | Rust 1.85 |

このリポジトリの `Cargo.toml` には `edition = "2024"` と書かれていました。

エディションの最大の特徴は、**違うエディションのクレート同士を、組み合わせて使える**ことです。

- 2015 エディションで書かれた古いクレートを、2024 エディションのプロジェクトから使える
- そのため、エディションを上げるかどうかは、各クレートの作者が自分のペースで決められる
- `cargo fix --edition` で、コードを新しいエディションに自動で移行する手助けもしてくれる

Python 2 から Python 3 への移行では、言語の互換性のない変更によって、エコシステムが長い期間にわたって分断されました。エディションは、**互換性を壊す変更を入れつつ、エコシステムを分断しない**ための工夫です。

## 7. どうやって決めているのか: RFC とガバナンス

### RFC プロセス

Rust の言語や標準ライブラリへの大きな変更は、**RFC**（Request for Comments）という文書で提案され、公開の場で議論されてから決まります。RFC は GitHub の `rust-lang/rfcs` リポジトリで管理されていて、誰でも読むことも、議論に参加することもできます。

RFC には、提案の動機、詳しい設計、**欠点**、**検討した他の案**などを書きます。これは、[03](03_adr.md) で学んだ ADR とよく似ています。
「なぜこの機能はこういう形なのか」と疑問に思ったら、その機能の RFC を読めば、当時の議論と、選ばれなかった案を知ることができます。**選球眼を鍛えるための、最高の教材の1つ**です。

### 組織の変化

| 年 | 出来事 |
|---|---|
| 2020年8月 | Mozilla が大規模な人員削減を行い、Rust や Servo に関わっていた人たちも影響を受ける |
| 2021年2月 | **Rust Foundation**（Rust 財団）が設立される。設立時のメンバーは AWS、Google、Huawei、Microsoft、Mozilla |
| 2022年12月 | Linux 6.1 で、カーネルに Rust の初期サポートが入る |
| 2023年 | プロジェクト全体の運営を担う Leadership Council が発足する |

Rust は、1つの会社のものではなく、**複数の企業とコミュニティが支える言語**になりました。1つの会社の方針転換で言語の将来が左右されにくいことは、長く使う技術を選ぶときの判断材料の1つです（[02](02_choosing_crates.md) のクレート選びで「メンテナンスの状況」を確認したのと同じ視点です）。

## 8. 人気と、その理由

Stack Overflow の開発者調査では、Rust は 2016 年以降、長年にわたって「最も愛されている（most loved / admired）言語」の 1 位に選ばれています。
これは「最も使われている言語」という意味ではありません。「**使っている人が、また使いたいと思う割合が高い言語**」という意味です。

学習コストは高いものの、一度慣れると、

- コンパイラが多くのバグを先に見つけてくれる安心感
- 「コンパイルが通れば、だいたい動く」という感覚
- `cargo` を中心とした道具の使いやすさ

が評価されている、とよく言われます。このリポジトリで学んできたあなたにも、少しずつ実感が湧いてきているかもしれません。
