# コードリーディングトラック — 標準ライブラリを読む

これまでのステージでは、`Option::map`、`Vec::push`、`String::push`、`.iter().map().sum()` などを当たり前のように使ってきました。
このトラックでは、それらが**実際にどう書かれているのか**を、標準ライブラリのソースコードを開いて確かめます。

読んでみると、次の3つのことが分かるはずです。

1. **魔法はない**。`?` もイテレータも、普通の Rust のコードで書かれています。自分で書けるものばかりです。
2. **CS基礎で学んだことが、そのまま出てくる**。2倍に伸びる容量、UTF-8 のビット操作、ヌルにならないポインタなどです。
3. **良いコードの書き方が分かる**。`unsafe` をどう閉じ込めるか、なぜ関数を分けるのか、コメントに何を書くのか。

## 準備: ソースコードを手元に置く

標準ライブラリのソースは、`rustup` でインストールできます（エディタの「定義へジャンプ」も、これを使っています）。

```bash
rustup component add rust-src

# ソースの場所
ls "$(rustc --print sysroot)/lib/rustlib/src/rust/library"
# alloc  core  std  ...
```

| ディレクトリ | 中身 |
|---|---|
| `core/` | OS もヒープも使わない部分。`Option`, `Result`, `Iterator`, 整数, `char`, `str` |
| `alloc/` | ヒープを使う部分。`Vec`, `String`, `Box`, `Rc` |
| `std/` | OS の機能を使う部分。ファイル、スレッド、ネットワーク。`core` と `alloc` の中身も再公開している |

`std::vec::Vec` と書いても、本体は `alloc/src/vec/mod.rs` にあります。`std` は、`core` と `alloc` をまとめて見せる窓口です。
組み込み機器のように OS がない環境では、`#![no_std]` と書いて `core` だけを使います。この3層構造は、そのためのものです。

> **バージョンについて**: このトラックの引用は、すべて **rustc 1.95.0 (59807616e 2026-04-14)** の rust-src から、そのまま抜き出しています。
> バージョンが変わると、行番号や細部が変わります。そのため、場所は行番号ではなく「ファイル名と関数名」で示しています。エディタで関数名を検索してください。

## 読み方のコツ（全ツアー共通）

標準ライブラリのコードは、`#[...]` という**属性**（attribute）だらけで、初めて見ると面食らいます。でも、ほとんどは**読み飛ばしてよい**ものです。

### 読み飛ばしてよい属性

| 属性 | 意味 |
|---|---|
| `#[stable(feature = "...", since = "1.0.0")]` | 「Rust 1.0.0 から安定版で使える」という記録。中身には関係しない |
| `#[unstable(...)]`, `#[rustc_const_unstable(...)]` | まだ不安定な機能。nightly 版でしか使えない |
| `#[rustc_diagnostic_item = "..."]` | コンパイラや clippy がエラーメッセージを出すときの目印 |
| `#[rustc_confusables("push_back", ...)]` | 他の言語の名前で探したときに「もしかして `push`？」と教えるための目印 |
| `#[lang = "..."]` | コンパイラが特別扱いする項目の目印（`Option` や `?` などの構文とつながっている） |
| `/// ...` | ドキュメントコメント。docs.rs に表示される説明そのもの。**むしろ読む価値がある** |

### 意味を知っておくとよい属性

| 属性 | 意味 | なぜ付いているのか |
|---|---|---|
| `#[inline]` | 「呼び出し元に中身を展開してよい」というコンパイラへのヒント | 小さな関数の呼び出しコストを消すため（CS基礎 10） |
| `#[inline(never)]` | 「展開しないで」 | めったに通らない処理を展開すると、プログラムが無駄に大きくなるため |
| `#[cold]` | 「この関数はめったに呼ばれない」 | コンパイラが、よく通る道を優先して最適化できるようにするため |
| `#[track_caller]` | panic したときに、**呼び出し元**の行を表示する | `unwrap()` で panic したとき、標準ライブラリの中ではなく、あなたのコードの行が表示されるのはこれのおかげ |
| `#[must_use]` | 戻り値を使わないと警告が出る | 「イテレータは何もしていない」といった間違いに気付かせるため |
| `#[cfg(...)]` | 条件付きコンパイル。条件が成り立つときだけ、その行をコンパイルする | OS ごと、設定ごとにコードを切り替えるため |

`#[cfg(not(no_global_oom_handling))]` はよく出てきます。「メモリ不足のときに panic してよい環境でだけ、この関数を用意する」という意味で、OS のカーネルのような特殊な環境のためのものです。普段は読み飛ばして構いません。

### `unsafe` と `// SAFETY:` コメント

標準ライブラリには `unsafe` ブロックがたくさんあります。そして、その直前にはほぼ必ず `// SAFETY:` で始まるコメントがあります。

```rust
// SAFETY: Just reserved capacity for at least the length needed to encode `ch`.
unsafe { ... }
```

`unsafe` は「コンパイラが検証できないことを、プログラマが保証する」という宣言でした（CS基礎 04）。
`// SAFETY:` コメントには、**なぜそれが安全だと言えるのか**という、その保証の根拠を書きます。これは Rust のコミュニティ全体の慣習で、clippy にもこのコメントを強制する lint（`undocumented_unsafe_blocks`）があります。
**自分で `unsafe` を書くときも、必ず SAFETY コメントを書きましょう。** 書けないなら、その `unsafe` はおそらく間違っています。

### マクロで生成されているコード

`impl Sum for i32` を探しても、そのままの文字列では見つかりません。`macro_rules!` で、12種類の整数型の実装をまとめて生成しているからです（ツアー04で読みます）。

- `macro_rules! 名前 { ... }` でマクロを定義し、`名前! { i8 i16 i32 ... }` のように呼び出して使います
- マクロの中の `$a:ty` のような部分は「ここに型が入る」という意味です
- 実装が見つからないときは、**型の名前のリストを検索する**と、マクロの呼び出し箇所が見つかります

### `[const]` と `Destruct` という見慣れない記法

1.95 のソースでは、次のような記法がよく出てきます。

```rust
pub const fn map<U, F>(self, f: F) -> Option<U>
where
    F: [const] FnOnce(T) -> U + [const] Destruct,
```

これは、関数をコンパイル時（`const` の文脈）にも実行できるようにするための、**まだ不安定な機能**の記法です。
普段の Rust のコードとして読むときは、`F: FnOnce(T) -> U` と読み替えて構いません。`[const] Destruct` は「破棄できる」という意味で、普通の型はすべて満たしているので、無視してよい制約です。

## 次に読むと良い OSS

標準ライブラリに慣れたら、規模が小さく、よく書かれたクレートを読んでみましょう。

| クレート | 内容 | 読みどころ |
|---|---|---|
| [`anyhow`](https://github.com/dtolnay/anyhow) | アプリケーション向けのエラー型 | s04 で学んだ「エラーを捨てない」をどう実装しているか。`context()` の仕組み |
| [`thiserror`](https://github.com/dtolnay/thiserror) | エラー型の derive マクロ | s04 で手で書いた `Display` を、マクロがどう生成しているか。手続きマクロの入門にもなる |
| [`once_cell`](https://github.com/matklad/once_cell) | 一度だけ初期化される値 | 現在は標準ライブラリに `OnceLock` / `LazyLock` として取り込まれている。外部クレートが標準に入る流れも見られる |
| [`ripgrep`](https://github.com/BurntSushi/ripgrep) | 高速な grep | 規模は大きいが、実務品質の CLI の構成、エラー処理、テストの書き方の手本。p01 の前に眺めると参考になる |

いきなり全部を読む必要はありません。**自分が使ったことのある関数を1つ選び、その定義から読み始める**のがコツです。
