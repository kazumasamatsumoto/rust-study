# p02: kvstore — 永続化付きキーバリューストア

## 背景

Redis や RocksDB のような、キーと値を保存するデータベースを、小さく自作する。
「データベースはどうやってデータを壊さずにディスクに保存しているのか」を体験することが目的。

## 機能（マイルストーン）

### M1: メモリ上の KV ストア（ライブラリとして）
```rust
let mut store = KvStore::new();
store.set("name".to_string(), "kazu".to_string());
assert_eq!(store.get("name"), Some("kazu".to_string()));
store.remove("name");
```
- ライブラリクレートとして作り、CLI はその上に薄く乗せる

### M2: 永続化（追記型ログ）
- 全ての書き込み操作（set / remove）を、**ファイルの末尾に追記**していく（ログ構造化ストレージ）
- 起動時にログを先頭から読み込んで、状態を復元する
- `serde` を使って、操作をシリアライズする

```
kvs set name kazu
kvs get name      # → kazu
kvs rm name
```

### M3: インデックス
- 毎回ログを全部読むのは遅い。「キー → ログファイル内の位置」をメモリ上に持ち、`get` のときはその位置だけを読む

### M4: コンパクション
- 同じキーに何度も書き込むと、ログが古い値で膨らんでいく。ログが一定のサイズを超えたら、最新の値だけを新しいファイルに書き直す
- **書き直している途中でプロセスが落ちても、データが壊れないこと**

### M5: ベンチマーク
- `criterion` で set / get の性能を計測する
- シリアライズの形式（JSON / bincode など）を変えたときの、速度とファイルサイズを比較する

## 非機能要件

- プロセスが任意のタイミングで kill されても、それまでに完了を返した書き込みは失われないこと（ただし OS のクラッシュは考慮しなくてよい）
- 10万件のキーを扱えること

## 必須の ADR

1. ディスク上のフォーマット（JSON / bincode / 独自のバイナリ形式）— M5 の計測結果を根拠にする
2. コンパクションを始める条件と、その方法
3. `KvStore` の API で、値の型を `String` に固定するか、ジェネリクスにするか

## 学べること

- ファイル I/O、`Seek`、`BufWriter` と flush の意味
- serde の仕組み
- 「書き込みが完了した」とは何を意味するのか（`fsync` について調べる）
- ベンチマークの取り方
