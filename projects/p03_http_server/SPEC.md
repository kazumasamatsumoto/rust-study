# p03: HTTP サーバをフレームワークなしで作る

## 背景

普段は axum や Express のようなフレームワークを使うが、その下で何が起きているのかを知るために、TCP の上に HTTP/1.1 を自分で実装する。
**このプロジェクトでは HTTP 関連のクレートを使わない**（`std::net` だけを使う）。

## 機能（マイルストーン）

### M1: 1つずつ応答するサーバ
- `TcpListener` で接続を受け付け、リクエストラインとヘッダをパースし、静的ファイルを返す
- 対応するもの: `GET`、ステータスコード 200 / 404 / 400、`Content-Type` と `Content-Length`

### M2: スレッドプール
- 1つのリクエストの処理に時間がかかると、他のリクエストが待たされることを、実際に確かめる（`/sleep` というエンドポイントを作る）
- **スレッドプールを自分で実装する**（`std::sync::mpsc` と `Arc<Mutex<...>>` を使う）
- サーバを止めるときに、処理中のリクエストを終えてから終了する（グレースフルシャットダウン）

### M3: ルーティングと POST
- パスとメソッドの組み合わせで、ハンドラを登録できるようにする
- `POST` のボディを `Content-Length` に従って読み込む
- 考えること: ハンドラの型をどうするか（`fn` ポインタ / `Box<dyn Fn>` / ジェネリクス）

### M4: 負荷試験
- `oha` や `wrk` などのツールで負荷をかけ、スレッド数を変えたときのスループットとレイテンシを計測する
- 結果をグラフや表にまとめ、なぜそうなったのかを考察する

## 非機能要件

- 不正なリクエストを受けても、サーバ全体が落ちないこと（panic しない）
- 巨大なヘッダやボディを送りつけられても、メモリを使い果たさないこと（上限を設ける）
- パストラバーサル（`GET /../../etc/passwd`）を防ぐこと

## 必須の ADR

1. スレッドプールのサイズの決め方
2. ハンドラの型の設計
3. リクエストのサイズの上限と、上限を超えたときの振る舞い

## 学べること

- TCP と HTTP の関係（HTTP は TCP の上で動くテキストのプロトコルである）
- スレッドプールの仕組み、`Send` と `Sync` が実際にどこで必要になるのか
- セキュリティの基本（入力を信用しない）
- 「スレッド per 接続」の限界 → p04 の async への動機
