# p04: タスク管理の REST API

## 背景

実務でよくある構成（Web フレームワーク + DB + 認証）で、API サーバを作る。
p03 で自作したものを、今度はエコシステムのクレートで作る。**何を自作し、何をクレートに任せるかを判断すること**が、このプロジェクトのテーマ。

## 機能（マイルストーン）

### M1: CRUD
- `axum` + `tokio` で、タスクの作成・一覧・取得・更新・削除の API を作る
- 最初はメモリ上に保存する（`Arc<RwLock<HashMap<...>>>`）
- リクエストとレスポンスは JSON（`serde`）

```
POST   /tasks          { "title": "Rust を学ぶ" }
GET    /tasks?done=false
GET    /tasks/{id}
PATCH  /tasks/{id}     { "done": true }
DELETE /tasks/{id}
```

### M2: DB
- `sqlx` + SQLite（または PostgreSQL）で永続化する
- マイグレーションを管理する
- 保存先をトレイトで抽象化し、テストではメモリ上の実装に差し替えられるようにする（s09 で学んだ依存の注入）

### M3: エラーとバリデーション
- エラーを、適切なステータスコードと JSON のエラーレスポンスに変換する（`IntoResponse` を実装する）
- 入力のバリデーション（タイトルが空でないこと、長さの上限など）。長さの上限が「何の数」なのかに注意（CS基礎 05）

### M4: 認証と運用
- API キーまたは JWT による認証（axum のミドルウェアで実装する）
- `tracing` で、リクエストごとのログを出す
- 設定を環境変数から読む
- Docker イメージを作る（マルチステージビルドで、イメージを小さくする）

### M5: テスト
- ハンドラのテスト（実際にサーバを起動せずにリクエストを送る方法を調べる）
- DB を使った統合テスト

## 必須の ADR

1. Web フレームワークの選定（axum / actix-web / その他）
2. DB とアクセス方法の選定（sqlx / diesel / sea-orm、SQLite / PostgreSQL）
3. 認証の方式
4. エラーレスポンスの形式

## 学べること

- async Rust での実務的な構成
- トレイトによる抽象化と、そのコスト
- 「この API サーバを Rust で書いたことは、正しい判断だったか？」を振り返る（`docs/judgment/01_when_to_use_rust.md` に戻ること）
