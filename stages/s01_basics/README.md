## 1. 不変がデフォルト（`let` と `let mut`）

```rust
let x = 5;      // 変更できない
let mut y = 5;  // 変更できる
```

**なぜ不変がデフォルトなのか**

- 書き換わる変数は、読む人の頭に「どこで変わるのか」という負担をかけます。`mut` が付いている変数だけを気にすればよくなります。
- 並行処理で一番危ないのは「共有されていて、しかも書き換わる」データです。デフォルトを不変にしておくと、危険な箇所が目に見えるようになります（Stage 10 で効いてきます）。

**他の言語では**

| 言語 | 不変 | 可変 | デフォルト |
|---|---|---|---|
| JavaScript | `const` | `let` | どちらも書く必要がある |
| Kotlin | `val` | `var` | どちらも書く必要がある |
| Java | `final` | (なし) | 可変 |
| Rust | `let` | `let mut` | **不変** |

「短く書ける方を安全な方にする」という考え方です。Rust の設計ではこれが何度も出てきます。

## 2. 整数型を明示する理由とオーバーフロー

Python の整数はいくらでも大きくなれますが、Rust では `i32`, `u64` のようにサイズを決めます。

- **理由**: 固定サイズの整数は CPU がそのまま計算できるので速く、メモリ上のサイズも予測できます。
- **オーバーフローしたとき**: debug ビルドでは **panic**、release ビルドでは **ラップアラウンド**（最大値の次が 0 に戻る）します。
  開発中はバグを見つけやすく、本番では速度を優先する、という折衷です。
- 意図を明示したいときは、メソッドを使い分けます:
  - `checked_add` → `Option` を返す（溢れたら `None`）
  - `saturating_add` → 最大値で止まる
  - `wrapping_add` → 意図的にラップさせる

`sum_to` の戻り値を `u64` にしているのはこのためです。

## 3. 式指向（`if` は値を返す）

```rust
let label = if n % 2 == 0 { "even" } else { "odd" };
```

Rust には三項演算子 `a ? b : c` がありません。`if` そのものが値を返すので必要ないからです。`match` もブロック `{}` も値を返します。
「文（文を実行する）」より「式（値を作る）」で考えるようにすると、変数を途中で書き換える必要が減ります。

## 4. `String` と `&str` が分かれている理由

| | `String` | `&str` |
|---|---|---|
| 意味 | 所有している文字列 | 誰かの文字列を借りて見ている |
| 伸び縮み | できる | できない |
| メモリ | ヒープに確保する | 確保しない（指しているだけ） |

**なぜ2種類あるのか**: 「文字列の一部を見るだけ」の処理で毎回コピーを作ると遅くなるからです。`&str` を使えば、コピーせずに部分文字列を扱えます（ゼロコピー）。
Java や Python は文字列を1種類にしてこの区別を隠していますが、そのぶん裏でコピーやメモリ確保が起きています。Rust はそのコストをコードの上に見えるようにしています。

**`s[0]` で文字が取れない理由**: Rust の文字列は UTF-8 です。「あ」は3バイト、「a」は1バイトというように1文字のバイト数が違うので、n 番目の文字を O(1) で取り出すことができません。
`s[0]` と書けると速そうに見えてしまうので、Rust はあえて禁止して、`s.chars().nth(0)` と書かせます。こう書くと、先頭から順にたどる処理だということが分かります。

## 5. `match` の網羅性チェック

`match` は全てのケースを処理しないとコンパイルエラーになります。`grade` で `_ => '?'` を書かないとエラーになるのはこのためです。
「書き忘れ」をコンパイラが見つけてくれる、というのは Rust の安全性の中心にある考え方です。Stage 03 で本領を発揮します。
