Rust を選ぶ理由の多くは、この Stage の内容にあります。

## 1. メモリ管理の3つの流派

プログラムは使い終わったメモリを解放しなければなりません。その方法は大きく3つあります。

| 方式 | 代表的な言語 | 長所 | 短所 |
|---|---|---|---|
| 手動管理 | C, C++ | 速い。いつ解放されるか予測できる | 解放後の使用、二重解放、メモリリークが起きやすい |
| ガベージコレクション (GC) | Java, Go, Python, JS | 安全で、書くのが楽 | GC による一時停止、メモリを多めに使う、解放のタイミングを制御できない |
| **所有権** | **Rust** | 速く、しかも安全。解放のタイミングも予測できる | **学習コストが高い**。一部のデータ構造が書きにくい |

所有権は「どの値をいつ解放するかをコンパイル時に決めてしまう」方式です。実行時のコストはゼロで、C と同じ速さで動き、GC 言語と同じように安全です。

**その代わりに払うもの**

- 覚えることが多い（今まさに払っているコストです）
- グラフや双方向リストのように「お互いを指し合う」構造が素直に書けない（Stage 08 の `Rc`/`RefCell` で対処します）
- プロトタイプを素早く書く用途では、GC 言語のほうが速く書けることが多い

**実例**: Discord は、Go で書かれていたサービスのうち、GC による遅延のスパイクが問題になったものを Rust に書き換えています（2020年、"Why Discord is switching from Go to Rust"）。
「GC の一時停止が許されるかどうか」は、言語を選ぶときの大事な判断基準です。

## 2. 借用ルールの本当の目的

> `&T` はいくつでも作れる。`&mut T` は同時に1つだけで、しかも `&T` と共存できない。

これは「**共有するなら書き換えない、書き換えるなら共有しない**」というルールです（aliasing XOR mutability）。このルールで、2種類のバグを防いでいます。

**(a) イテレータ無効化** — 他の言語でもよく起きるバグです。

```rust
let mut v = vec![1, 2, 3];
for x in &v {
    v.push(*x); // コンパイルエラー: v を読んでいる最中に書き換えようとしている
}
```

C++ では、`push` によって Vec のメモリが別の場所に移されると、ループが指しているメモリが無効になります（未定義動作）。Java では実行時に `ConcurrentModificationException` が発生します。Rust では**コンパイルの時点**で止まります。

**(b) データ競合**: 複数のスレッドが同じデータを同時に書き換える問題です。これも同じルールで、コンパイル時に防げます（Stage 10）。

## 3. 引数は「最も一般的な型」を受け取る

```rust
fn f(s: &String)   // △ String しか渡せない
fn f(s: &str)      // ◎ String も、リテラルも、部分文字列も渡せる

fn g(v: &Vec<i32>) // △
fn g(v: &[i32])    // ◎ Vec も、配列も、スライスも渡せる
```

`&String` を `&str` に、`&Vec<T>` を `&[T]` に変換するのは自動で行われますが、逆方向の変換はできません。受け取る側の型をゆるくしておくと、呼び出す側が楽になります。
clippy の `ptr_arg` という lint がこれをチェックしています（未実装の状態のときに一度見たはずです）。

## 4. `Copy` と `Clone`: コストを見えるようにする

- `i32` や `bool` は `Copy` 型です。代入すると勝手にコピーされます。コピーは安価で、固定サイズのビット列を写すだけです。
- `String` や `Vec` は `Copy` ではありません。コピーするには `.clone()` と**明示的に**書く必要があります。

Python で `b = a` と書いても、それが参照のコピーなのか値のコピーなのかはコードからは分かりません。Rust では重い処理（ヒープのコピー）はコードに `.clone()` として現れます。
レビューで `.clone()` を見かけたら「本当に必要か？」と確認するのは、これが理由です。
