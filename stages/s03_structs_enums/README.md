# Stage 03: 構造体・列挙型 — 解説と設計判断

この Stage のテーマは「型で設計する」ことです。

---

## 1. Rust の enum は「または」を表す型

C や Java の enum は、名前の付いた定数の集まりにすぎません。Rust の enum は、**バリアントごとに別々のデータを持てます**（代数的データ型 / ADT）。

```rust
enum Shape {
    Circle { radius: f64 },              // 円 なら 半径
    Rectangle { width: f64, height: f64 }, // または 長方形 なら 幅と高さ
}
```

- `struct` は「A **かつ** B」（積の型）
- `enum` は「A **または** B」（和の型）

多くの言語は「かつ」しか素直に書けません。そのため「または」を表したいときに null やフラグ、継承で代用してきました。

### null がない理由

Rust に null はありません。値がないかもしれないときは `Option<T>` を使います。
null を発明した Tony Hoare 自身が、null を「10億ドルの誤り」と呼んでいます。`Option` を使うと、「値がないかもしれない」ことが型に現れ、処理を書き忘れるとコンパイルエラーになります。

## 2. 網羅性チェックがリファクタリングを安全にする

`Shape` に `Hexagon` を追加すると、`match` で `Shape` を処理している**全ての場所**がコンパイルエラーになります。
これは迷惑なことではなく、修正すべき場所の一覧をコンパイラが作ってくれるということです。大規模なコードで Rust が「変更に強い」と言われる大きな理由です。

ただし `_ => ...` を使うとこのチェックは効かなくなります。ワイルドカードは「将来バリアントが増えても、ここは同じ処理でいい」と言い切れる場合にだけ使いましょう。

## 3. ⭐ enum か trait か（Expression Problem）

「いろいろな図形」を表す方法は2つあります。

| | enum + match | trait + 各型に impl |
|---|---|---|
| **新しい操作**（例: 周の長さ）を追加 | 簡単（関数を1つ足すだけ） | 大変（全ての型に実装を足す） |
| **新しい種類**（例: 六角形）を追加 | 大変（全ての match を修正） | 簡単（型を1つ足すだけ） |
| 種類が閉じているか | 閉じている（自分で全部把握している） | 開いている（ライブラリの利用者が追加できる） |

これは Expression Problem と呼ばれる、昔からある設計上のトレードオフです。**どちらが正解ということはなく、「将来何が増えるか」で選びます。**

- 種類が決まっていて、操作が増えていく → enum（例: AST、コマンド、状態）
- 種類が増えていき、操作は決まっている → trait（例: プラグイン、出力形式）

## 4. カプセル化と不変条件

`Account` のフィールドは非公開になっています。その理由は「**残高はマイナスにならない**」という不変条件（invariant）を守るためです。

- `balance` を `pub` にすると、誰でも好きな値を書き込めてしまいます。
- メソッドを通してしか触れないようにすれば、不変条件を守るコードは `impl Account` の中だけで済みます。
- `u64` という型そのものも、マイナスを表現できないようにしています。型とカプセル化の二重の守りです。

## 5. 不正な状態を表現できなくする

自販機を次のように作ったとします。

```rust
struct Vending { money: u32, dispensed: bool, change: u32 }
```

この形だと「お金が0なのにお釣りがある」といった不正な組み合わせが作れてしまいます。
enum で状態を分ければ、`Dispensed` の状態にだけ `change` を持たせることができます。**ありえない状態は、そもそも型として作れない**ようにするわけです。
これを発展させたものが typestate パターンで、「接続前のソケットには send できない」といった制約をコンパイル時に保証できます。

## 6. `derive` がオプトインである理由

`Debug`, `Clone`, `PartialEq` が自動で付かないのは、「その型をコピーしてよいか」「等しいとは何か」が、型を設計する人の判断だからです。
例えば、パスワードを持つ型が勝手に `Debug` を実装すると、ログに中身が出力されてしまいます。
