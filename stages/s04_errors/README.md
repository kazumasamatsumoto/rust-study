# Stage 04: エラー処理 — 解説と設計判断

---

## 1. エラー処理の3つの流派

| 方式 | 代表的な言語 | 長所 | 短所 |
|---|---|---|---|
| 例外 | Java, Python, JS, C# | 正常系のコードがすっきり書ける | どの関数が失敗するのか、シグネチャから分からない。処理を忘れても気付けない |
| 戻り値で返す | Go (`if err != nil`), C | 失敗する箇所が見える | 書くのが冗長。エラーを無視できてしまう |
| **型で返す + `?`** | **Rust**, Swift, Kotlin の一部 | 失敗の可能性が型に現れる。無視するとコンパイラが警告する。`?` で簡潔に書ける | エラー型の設計を考える必要がある |

Rust は「Go のようにエラーが見える」ことと「例外のように簡潔に書ける」ことの両方を、`Result` と `?` で実現しています。

## 2. `panic!` と `Result` の使い分け

これは実務でよく問われる判断です。

- **`Result`**: **想定できる失敗**に使います。ユーザーの入力が間違っている、ファイルが存在しない、ネットワークが切れた、など。呼び出し側に処理を任せます。
- **`panic!`**: **バグ**、つまりプログラマの誤りに使います。「ここに来るはずがない」状態になったときで、続行するとかえって危険な場合です。

`unwrap()` / `expect()` を使ってよい場面:

- テストのコード
- プロトタイプや使い捨てのスクリプト
- 論理的に失敗しないことが分かっている場合。そのときは `expect("理由")` と書いて、なぜ失敗しないのかを残します

本番コードで `unwrap()` を見つけたら「なぜここは失敗しないと言えるのか？」と問う習慣を付けましょう。

## 3. ⭐ エラー型をどう設計するか

| 方式 | 例 | 向いている用途 |
|---|---|---|
| `String` | `Err("bad input".into())` | プロトタイプ。呼び出し側がエラーの種類で処理を分けられない |
| 独自の enum | `ConfigError::MissingEquals { line }` | **ライブラリ**。呼び出し側が `match` で種類ごとに処理できる |
| `Box<dyn Error>` / `anyhow::Error` | `anyhow::bail!("...")` | **アプリケーション**。最終的にはログに出したりユーザーに見せたりするだけの場合 |

実務でよく使われる組み合わせ:

- ライブラリでは `thiserror`（独自 enum を簡潔に書けるようにする derive マクロ）
- アプリケーションでは `anyhow`（何でも入るエラー型と、エラーに文脈を付け足す `.context()`）

**なぜライブラリとアプリケーションで分けるのか**: ライブラリは、使う人がエラーをどう扱いたいか分からないので、情報を落とさずに型で渡すべきです。アプリケーションは最終的な利用者なので、大半のエラーはまとめて報告するだけで済みます。

課題でまず手で `Display` を実装しているのは、`thiserror` が裏で何を生成しているのかを理解するためです。

## 4. エラーを捨てない

`eval_division` で `ParseIntError` を `String` に変換すると、元のエラー情報（どこで、なぜ失敗したか）が失われます。
`std::error::Error::source()` を使うと、エラーの原因を鎖のように辿れるようになります。`anyhow` が表示する "Caused by:" はこの仕組みを使っています。
