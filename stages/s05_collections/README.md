## 1. ハッシュテーブルの仕組み

`HashMap` を正しく使い分けるには、中で何が起きているかを知っておく必要があります。

### ハッシュ関数

**ハッシュ関数**とは、任意のデータを、決まった大きさの数（ハッシュ値）に変換する関数です。

```
"apple"  → hash → 0x8f3a...  → 8 で割った余り = 2
"banana" → hash → 0x1c07...  → 8 で割った余り = 7
"cherry" → hash → 0x5ab2...  → 8 で割った余り = 2   ← apple と同じ場所（衝突）
```

ハッシュテーブルは、**バケット**と呼ばれる配列を持っています。
1. キーのハッシュ値を計算する
2. それをバケットの数で割った余りを、配列のインデックスにする
3. そこに値を置く

配列のインデックスでアクセスするので O(1) です。これが「キーで検索すると平均 O(1)」の正体です。

### 衝突と「平均」O(1)

違うキーが同じバケットに入ることを**衝突**と呼びます。衝突したら、近くの空いている場所を探すなどして対処します。
衝突が少なければ O(1) ですが、**全てのキーが同じバケットに入ると、検索は O(n) まで遅くなります**。計算量の表に「平均」と書いてあるのは、このためです。

要素が増えると衝突が増えるので、ある程度埋まったところで**バケットを増やして全ての要素を入れ直します**（リハッシュ）。`Vec` の容量が2倍になるのと同じ考え方で、push と同じく償却 O(1) になります。

### ⭐ Rust の HashMap が反復順序を決めていない理由

Rust の標準の `HashMap` は、**プログラムを起動するたびに、ランダムな種（シード）を使ってハッシュ関数を初期化**します（`RandomState`）。
そのため、同じデータを入れても、実行するたびに `for (k, v) in &map` の順序が変わります。

**なぜわざわざそうしているのか**: **HashDoS 攻撃**を防ぐためです。
ハッシュ関数が固定されていると、攻撃者は「全て同じバケットに入るキー」を計算して作れます。それを Web サーバのリクエストのパラメータとして大量に送りつけると、検索が O(n) に、全体で O(n²) になり、サーバの CPU を使い切らせることができます。2011年に、多くの言語の Web フレームワークで実際にこの問題が報告されました。

Rust は、デフォルトで HashDoS に強いハッシュ関数（SipHash-1-3）とランダムなシードを使っています。**安全なほうをデフォルトにする**という方針です。
- 代わりに払うもの: 単純なハッシュ関数より少し遅くなります。信頼できる入力だけを扱い、速度が重要な場合は、`rustc-hash` クレートの `FxHashMap` などに切り替えることができます
- **教訓**: `HashMap` の順序に依存したコードやテストを書いてはいけません。課題の `top_n` で「回数が同じなら辞書順」と決めているのは、このためです

### キーに必要な条件

`HashMap<K, V>` のキーには `Hash + Eq` が必要です。
- `Hash`: ハッシュ値を計算できる
- `Eq`: 等しいかどうかを、確実に判定できる。`a == b` なら、`hash(a) == hash(b)` でなければなりません

`f64` がキーになれないのは、`NaN != NaN` のために `Eq` を実装していないからです（[CS基礎 02](../../docs/fundamentals/02_floats.md)）。

## 2. コレクションの選び方

| 型 | 中身 | 向いている用途 |
|---|---|---|
| `Vec<T>` | 連続した配列 | **迷ったらこれ**。順番に並べる、インデックスで取り出す |
| `VecDeque<T>` | リングバッファ | キュー（先頭からも末尾からも出し入れする） |
| `HashMap<K, V>` | ハッシュテーブル | キーで検索する。順序はいらない |
| `BTreeMap<K, V>` | B木（ソート済みの木） | **キーの順序で**取り出したい、範囲で検索したい（`range(10..20)`） |
| `HashSet<T>` / `BTreeSet<T>` | 値を持たない Map | 重複の除去、「含まれているか」の判定 |
| `BinaryHeap<T>` | 二分ヒープ | 優先度付きキュー（常に最大値を取り出す） |

`HashSet<T>` は、内部的には `HashMap<T, ()>` です。値の部分が何もない Map だと考えれば、性質は全て同じです。

**BTreeMap を選ぶ理由**は、速さよりも**順序が決まっていること**です。
- 出力を毎回同じ順番にしたい（テスト、設定ファイルの書き出し、差分を見やすくしたい場合）
- 「10以上20未満のキー」のような範囲での検索がしたい

## 3. ⭐ イテレータは遅延評価で、ゼロコスト

```rust
let total: i32 = v.iter().filter(|x| *x % 2 != 0).map(|x| x * x).sum();
```

### 遅延評価

`filter` や `map` は、呼んだ時点では**何も計算しません**。「こういう処理をする」という計画（イテレータ）を返すだけです。
`sum` や `collect` のような、最後に値を取り出すメソッド（消費メソッド）を呼んだときに初めて、1要素ずつ全ての処理が流れます。

```
JavaScript の配列メソッド（即時評価）:
  v.filter(...)  → 新しい配列を作る
   .map(...)     → また新しい配列を作る
   .reduce(...)  → 合計

Rust のイテレータ（遅延評価）:
  要素1 → filter → map → 足す
  要素2 → filter → (捨てる)
  要素3 → filter → map → 足す       ← 途中の配列は1つも作らない
```

途中の配列を作らないので、メモリの確保がなく、速くなります。`take(10)` と組み合わせれば、無限に続くイテレータも扱えます（Stage 06 で作ります）。

### ゼロコスト抽象化

Rust のイテレータは、コンパイルされると、**手で書いた `for` ループとほぼ同じ機械語**になります。`filter` や `map` に渡したクロージャは、インライン化されて消えます（[CS基礎 07](../../docs/fundamentals/07_dispatch.md) の静的ディスパッチ）。
「抽象化して読みやすく書いても、実行時のコストは増えない」。これが Rust の言う**ゼロコスト抽象化**です。

**他の言語との比較**

| 言語 | 仕組み | 評価 | 備考 |
|---|---|---|---|
| JavaScript | 配列のメソッド | 即時 | メソッドごとに配列を作る |
| Python | ジェネレータ、内包表記 | 遅延（ジェネレータ） | インタプリタなので、1要素ごとに一定のコストがかかる |
| Java | Stream API | 遅延 | 仮想メソッドの呼び出しやオブジェクトの生成がある（JIT がある程度最適化する） |
| **Rust** | Iterator トレイト | 遅延 | コンパイル時に全てインライン化され、ループと同じになる |

### for ループとどちらで書くか

イテレータを使うと常に読みやすくなるわけではありません。
- データを**変換して集める**処理（filter → map → collect）は、イテレータのほうが意図が明確になります
- 途中で `break` したり、複数の変数を同時に更新したりする**複雑な制御**は、`for` ループのほうが読みやすいことが多いです

チームのメンバーが読みやすいほうを選びましょう。

## 4. クロージャの正体

```rust
let k = 5;
let add_k = move |x| x + k;
```

クロージャは、コンパイラが作る**名前のない構造体**です。捕まえた変数を、フィールドとして持っています。

```rust
// コンパイラが裏で作っているもの（イメージ）
struct AddKClosure { k: i32 }
impl Fn(i32) -> i32 for AddKClosure {
    fn call(&self, x: i32) -> i32 { x + self.k }
}
```

ここから、いくつかのことが分かります。

- **クロージャは1つ1つが別の型になります**。同じ書き方のクロージャでも型は別です。そのため、戻り値の型を書くことができず、`impl Fn(i32) -> i32`（「Fn を実装した何かの型」）と書きます
- 捕まえた変数がフィールドになるので、**捕まえる変数が多いほど、クロージャのサイズは大きくなります**
- `move` は「フィールドに、参照ではなく値そのものをムーブして入れる」という意味です。クロージャを関数の外に返す場合や、別のスレッドに渡す場合に必要です（Stage 10）

### Fn / FnMut / FnOnce の違いは、self の受け取り方の違い

| トレイト | 呼び出しのメソッド | 捕まえた変数に対してできること |
|---|---|---|
| `Fn` | `call(&self)` | 読むだけ |
| `FnMut` | `call_mut(&mut self)` | 書き換える |
| `FnOnce` | `call_once(self)` | 消費する（self ごとムーブするので、1回しか呼べない） |

Stage 02 の `&T` / `&mut T` / `T`（所有権）の区別が、そのまま現れています。

### ⭐ 受け取る側は、最もゆるい制約を選ぶ

全ての `Fn` は `FnMut` としても使え、全ての `FnMut` は `FnOnce` としても使えます。

```
FnOnce ⊇ FnMut ⊇ Fn   （左ほど受け取れるクロージャが多い）
```

関数の引数にクロージャを受け取るときは、**必要な最低限の制約**にします。
- 1回しか呼ばない → `FnOnce`（どんなクロージャでも受け取れる）
- 何回も呼ぶし、呼び出し側の状態を変えてもよい → `FnMut`
- 何回も呼び、しかも同時に呼ぶ可能性がある（並列処理など） → `Fn`

Stage 02 で「`&String` ではなく `&str` を受け取る」と学んだのと同じで、**受け取る側がゆるいほど、使う側が楽になります**。
標準ライブラリの `Option::unwrap_or_else` が `FnOnce` を、`Iterator::map` が `FnMut` を受け取っているのも、この理由です。
