# Stage 08: スマートポインタ — 解説と設計判断

## 1. スマートポインタとは

**スマートポインタ**とは「ポインタとして振る舞いつつ、追加の機能を持つ型」です。実は `String` や `Vec` もスマートポインタの一種です（ヒープを指していて、容量の管理と自動解放という機能を持っています）。

スマートポインタを支えているのは、2つのトレイトです。

- **`Deref`**: `*p` や `p.method()` で、中身にアクセスできるようにする。`Box<Expr>` に対して `Expr` のメソッドをそのまま呼べるのはこのおかげです
- **`Drop`**: スコープを抜けたときに実行する後片付けを書く。ヒープの解放や、参照カウントを減らす処理がここで行われます

実際のサイズ（64bit 環境で実行した結果）:

```
Box<i32>        : 8    ← ポインタ1個
Rc<i32>         : 8    ← ポインタ1個（カウンタはヒープ側にある）
Weak<i32>       : 8
RefCell<i32>    : 16   ← 中身の i32 + 借用状態を記録するカウンタ
Box<dyn Fn()>   : 16   ← ポインタ + vtable へのポインタ（ファットポインタ）
```

## 2. `Box<T>`: ヒープに置く

`Box::new(x)` は、`x` をヒープに置き、そこを指すポインタをスタックに持ちます。所有者は1人のままで、スコープを抜けると解放されます。

### なぜ再帰型に `Box` が必要なのか

```rust
enum Expr {
    Num(i64),
    Add(Expr, Expr),   // エラー: サイズが無限になる
}
```

`enum` のサイズは「一番大きいバリアントのサイズ」で決まります（[CS基礎 03](../../docs/fundamentals/03_memory.md)）。`Add` のサイズは `Expr` 2つ分で、その `Expr` の中にまた `Add` があるかもしれない……と、**サイズが決まりません**。スタックには、サイズが決まった値しか置けません。

```rust
enum Expr {
    Num(i64),
    Add(Box<Expr>, Box<Expr>),   // OK: Box は常に 8 バイト
}
```

`Box` にすると、子の式はヒープに置かれ、`Add` の中身は「ポインタ 8 バイト × 2」になります。木やリストなど、再帰的なデータ構造を作るときの基本の形です。

`Box` を使う他の場面:
- 大きな値を、コピーせずにムーブしたい（ムーブで動くのが 8 バイトだけになる）
- `Box<dyn Trait>` で、異なる型をまとめて扱いたい（Stage 06 のトレイトオブジェクト）

## 3. `Rc<T>`: 所有者を複数にする（参照カウント）

普通は所有者は1人です。しかし「複数の場所から同じデータを使い、全員が使い終わったら解放したい」場面があります（例: 複数のウィンドウが同じ設定を共有する）。

`Rc`（Reference Counted）は、ヒープ上に**データと一緒に「所有者の数」を記録**します。

```
   スタック            ヒープ
  ┌────────┐     ┌─────────────────┐
a │ ptr ───┼──┬─→│ strong = 2      │
  └────────┘  │  │ weak   = 0      │
  ┌────────┐  │  │ data: "shared"  │
b │ ptr ───┼──┘  └─────────────────┘
  └────────┘
```

- `Rc::clone(&a)`: データはコピーせず、**カウントを1増やすだけ**
- 所有者の1人が消える（drop）: カウントを1減らす
- カウントが 0 になったら、データを解放する

実験の結果:

```
  作成直後 strong = 1
  clone 後 strong = 2
  ブロック内 strong = 3
  ブロック後 strong = 2
  a を drop: strong = 1
  drop: shared                       ← 最後の所有者が消えた瞬間に解放された
  b を drop した（ここで drop: shared が出る）
```

**`Rc::clone` と `.clone()` の書き分け**: `a.clone()` と書いても動きますが、`Rc::clone(&a)` と書くと「これは安いカウントの増加で、データのコピーではない」ことが読む人に伝わります。

### `Rc` はスレッドをまたげない

カウントの増減は、普通の足し算と引き算です。2つのスレッドが同時に増やすと、カウントが壊れてしまいます。そのため `Rc` は**スレッド間で共有できない**型になっていて、共有しようとするとコンパイルエラーになります。
スレッド間で共有したい場合は `Arc`（Atomic Rc）を使います。CPU のアトミック命令でカウントを増減するので安全ですが、少し遅くなります（Stage 10）。
「**必要なときだけ、コストを払う**」という Rust の設計がここにも現れています。

## 4. `RefCell<T>`: 借用チェックを実行時に行う

`Rc` で共有したデータは `&T` でしか触れません（複数の所有者が書き換えたら危ないからです）。それでも書き換えたい場合に使うのが `RefCell` です。

`RefCell` は、借用のルール（「`&mut` は1つだけ、かつ `&` と共存しない」）を**コンパイル時ではなく実行時に**チェックします。中にカウンタを持っていて、「今いくつ読み取り中か」「書き込み中か」を記録しています（だから `RefCell<i32>` は 16 バイトでした）。

```
  読み取り中に try_borrow_mut: Err(BorrowMutError)
  読み取り終了後 try_borrow_mut: Ok(())
```

`try_` の付かない `borrow_mut()` でルールを破ると、**panic** します。

```
thread 'main' panicked at examples/rc.rs:54:19:
RefCell already borrowed
```

このように、`&self` から中身を書き換えられることを**内部可変性**（interior mutability）と呼びます。

| | 普通の借用 | `RefCell` |
|---|---|---|
| チェックするタイミング | コンパイル時 | 実行時 |
| ルールを破ったとき | コンパイルエラー | **panic** |
| 実行時のコスト | なし | カウンタの確認と更新 |

**コンパイル時の保証を、実行時のチェックと引き換えに手放している**、という点を覚えておいてください。`RefCell` を多用したコードは、「コンパイルが通れば借用の問題はない」という Rust の一番の強みを失います。

似たものとして `Cell<T>` があります。中身を `get` / `set` でコピーして出し入れするだけなので、借用状態の管理が要りません。`Copy` な小さな値（カウンタなど）に使います。

## 5. 循環参照とメモリリーク

`Rc` には弱点があります。**お互いを `Rc` で指し合うと、カウントが 0 にならず、永遠に解放されません。**

```rust
// x → y → x と指し合う
let x = Rc::new(Node { name: "x", next: RefCell::new(None) });
let y = Rc::new(Node { name: "y", next: RefCell::new(Some(Rc::clone(&x))) });
*x.next.borrow_mut() = Some(Rc::clone(&y));
```

```
  x strong = 2, y strong = 2
  スコープを抜けた（drop Node が出ていない = リーク）
```

スコープを抜けると変数 `x` と `y` は消えて、カウントは1ずつ減ります。しかしお互いが相手を指しているので、カウントは 1 のまま残ります。`Drop` が呼ばれていないこと（"drop Node" が表示されないこと）が、リークしている証拠です。

Rust は**メモリリークを「安全でない」とはみなしていません**。リークしても、消えたメモリを読むようなことは起きないからです（[CS基礎 04](../../docs/fundamentals/04_pointers.md) の表を参照）。そのため、コンパイラはこれを止めてくれません。設計で防ぐ必要があります。

ちなみに Java や Go の GC は、循環参照も回収できます。参照カウント方式は「どこからも辿れないか」を調べないので、循環を検出できないのです。Python は参照カウントを基本にしつつ、循環を見つけるための GC を別に持っています。

## 6. `Weak<T>`: 所有しない参照

循環を断ち切るのが `Weak` です。`Weak` は**カウント（strong）を増やさない**参照です。

- `Rc::downgrade(&rc)` で、`Rc` から `Weak` を作る
- `weak.upgrade()` で、`Option<Rc<T>>` を得る。データがもう解放されていれば `None`

```
strong=1 weak=1
生きている間の upgrade: Some("parent")
drop 後の upgrade      : None
```

**設計の原則**: 「所有する方向」を1つに決めて、逆向きは `Weak` にします。
- 木: 親 → 子 は `Rc`、子 → 親 は `Weak`（課題 03）
- GUI: ウィンドウ → ボタン は `Rc`、ボタン → ウィンドウ は `Weak`
- キャッシュ: キャッシュが `Weak` で持てば、他に誰も使っていないデータは自然に消える

## 7. `Cow<'a, T>`: 借りるか所有するかを実行時に選ぶ

`Cow`（Clone on Write）は「借りている」か「所有している」かのどちらかを持つ enum です。

```rust
enum Cow<'a, B> { Borrowed(&'a B), Owned(B の所有版) }
```

課題 01 の `escape_html` のように、「**ほとんどの場合は変更が要らないが、たまに変更が必要**」な処理で使います。変更が要らないときはコピーせずに借りたまま返し、必要なときだけ新しい `String` を作ります。

## 8. ⭐ 選球眼: なぜ Rust ではグラフや双方向リストが難しいのか

双方向リストでは、各ノードが「前」と「次」の両方を指します。つまり、**1つのノードを2つのノードが指している**ことになります。

```
  A ⇄ B ⇄ C      B は A からも C からも指されている
```

Rust の「所有者は1人」というルールでは、これを素直に書けません。B の所有者は A でしょうか、C でしょうか？ 一般的なグラフでも同じ問題が起きます。

GC のある言語では、ただ参照を持たせれば済みます。C では生ポインタで指せば済みます（そして解放のタイミングを間違えるとバグになります）。Rust では、次のどれかを選ぶ必要があります。

### 案A: `Rc<RefCell<Node>>` + `Weak`

```rust
struct Node {
    value: i32,
    next: Option<Rc<RefCell<Node>>>,   // 次は所有する
    prev: Option<Weak<RefCell<Node>>>, // 前は所有しない（循環を避ける）
}
```

- 長所: 他の言語で書く場合と構造が近く、直感的に書ける
- 短所: `borrow_mut()` と `upgrade()` だらけになり、読みにくい。借用のミスが**実行時の panic** になる。カウンタの操作とヒープの確保のぶん遅い。`Weak` の向きを間違えると**リーク**する

### 案B: arena（インデックスで繋ぐ）

ノードを全部1つの `Vec` に入れ、ポインタの代わりに**`Vec` のインデックス**で繋ぎます。

```rust
struct Node { value: i32, prev: Option<usize>, next: Option<usize> }
struct List { nodes: Vec<Node>, head: Option<usize>, tail: Option<usize> }

fn push_back(&mut self, value: i32) -> usize {
    let id = self.nodes.len();
    self.nodes.push(Node { value, prev: self.tail, next: None });
    match self.tail {
        Some(t) => self.nodes[t].next = Some(id),
        None => self.head = Some(id),
    }
    self.tail = Some(id);
    id
}
```

```
後ろから: [3, 2, 1]
```

- 長所: 所有者は `List` だけなので、借用チェッカーと素直に付き合える。`RefCell` が要らない。ノードがメモリ上に連続して並ぶので、キャッシュが効いて速い（[CS基礎 06](../../docs/fundamentals/06_complexity.md)）。リストを丸ごと捨てるのも一瞬
- 短所: ノードを削除すると、そのインデックスが「空き」になる。それを再利用すると、古いインデックスが別のノードを指してしまう（**インデックス版のダングリング参照**）。対策として、世代番号を付けたインデックス（`slotmap`, `generational-arena` クレートなど）を使う
- 実例: Rust のコンパイラ自身、ゲームエンジンの ECS（`bevy` など）、グラフライブラリの `petgraph` が、この方式を使っています

### 案C: `unsafe` と生ポインタ

C と同じように生ポインタで繋ぎ、安全性はプログラマが保証します。

- 長所: 一番速く、メモリの使い方も C と同じにできる
- 短所: 借用チェッカーの保護がなくなる。正しく書くのは**専門家でも難しい**
- 実例: 標準ライブラリの `LinkedList` や `Vec` の内部。`unsafe` を小さく閉じ込め、外側には安全な API だけを見せています（[CS基礎 04](../../docs/fundamentals/04_pointers.md)）

### 案D: そもそも作らない

本当に双方向リストが必要か、考え直します。[CS基礎 06](../../docs/fundamentals/06_complexity.md) で見たように、ほとんどの場合は `Vec` や `VecDeque` のほうが速いです。グラフが必要なら、`petgraph` のような実績のあるクレートを使えば済みます。

### どう選ぶか

| 状況 | 選ぶもの |
|---|---|
| まず検討すべきこと | **案D**: `Vec` / `VecDeque` / 既存のクレートで済まないか |
| ノードの数が少なく、構造がよく変わる。GUI の部品の木など | 案A |
| ノードが多い、性能が大事、削除が少ないか世代番号で管理できる | **案B**（実務で一番よく使われる） |
| 汎用のライブラリを作っていて、性能を突き詰める必要がある | 案C（十分なテストと `miri` での検証を前提に） |

「Rust では双方向リストが書きにくい」というのは、欠点であると同時に、**「その構造は本当に必要か？ 所有関係はどうなっているのか？」と設計を問い直させている**とも言えます。
