# Stage 09: モジュール設計とテスト — 解説と設計判断

> **前提知識**: [10 コンパイルとリンク](../../docs/fundamentals/10_compilation.md)（クレート単位のコンパイル、`cargo test` が何をビルドしているか）

この Stage では「動くコード」から「**チームで育てられるコード**」へ進みます。
コードは書く時間より、読まれ、変更される時間のほうがずっと長いものです。その変更を安全にするのが、モジュールによる**境界**と、テストによる**安全網**です。

---

## 1. クレートとモジュール

| 単位 | 何か | 例 |
|---|---|---|
| **パッケージ** | `Cargo.toml` を持つ単位。1つ以上のクレートを含む | `stages/s09_modules_testing/` |
| **クレート** | コンパイルの単位。ライブラリ（`lib.rs`）か実行ファイル（`main.rs`） | `s09_modules_testing` |
| **モジュール** | クレートの中の名前空間。`mod` で作る | `ex01_visibility::temperature` |

モジュールは、ファイルの分け方とも対応しています。

```
src/lib.rs                 →  crate（ルート）
src/ex01_visibility.rs     →  crate::ex01_visibility
  └ pub mod temperature {} →  crate::ex01_visibility::temperature （ファイル内に書いたモジュール）
```

`lib.rs` に `pub mod ex01_visibility;` と書くと、コンパイラは `ex01_visibility.rs` を探して読み込みます。**書かなければ、ファイルがあってもコンパイルされません**。

## 2. ⭐ 可視性: なぜ「デフォルト非公開」なのか

Rust では、何も付けなければ**全て非公開**です。

| 書き方 | 見える範囲 |
|---|---|
| (なし) | 同じモジュールと、その子モジュール |
| `pub(super)` | 親モジュールまで |
| `pub(crate)` | 同じクレートの中 |
| `pub` | どこからでも（クレートの外からも） |

**公開したものは「約束」になります。** `pub` な関数を利用者が使い始めると、引数を変えたり削除したりするだけで、利用者のコードが壊れます。
非公開のものは、クレートの中を直すだけで自由に変えられます。だから、

- **最初は全部非公開にして、必要になったものだけを公開する**のが基本です
- 公開する API は小さければ小さいほど、後から変更しやすくなります

Java では、何も付けないと package-private（同じパッケージから見える）になり、`public` を付ける習慣も強いので、意図せず公開範囲が広がりがちです。Python には言語としての非公開がなく、`_` で始める名前は「慣習」にすぎません。
Rust は「**安全な方を短く書けるようにする**」（Stage 01 の `let` と `let mut`）という方針を、ここでも貫いています。

### フィールドを非公開にして、不変条件を守る

```rust
pub struct Celsius(f64);   // 型は公開、フィールドは非公開
```

フィールドが非公開なので、クレートの外では `Celsius(-500.0)` と書けません。必ず `Celsius::new` を通るので、「**絶対零度未満の `Celsius` は存在しない**」ことを保証できます。
Stage 03 の `Account` と同じ考え方です。型を受け取った関数は、値が正しいかどうかを毎回チェックしなくて済みます（"Parse, don't validate" と呼ばれる考え方です）。

## 3. `use` と再エクスポート

```rust
// lib.rs
pub use ex01_visibility::temperature::Celsius;
```

`pub use` を使うと、深い場所にあるものを、浅い場所からも公開できます（**再エクスポート**）。

- 利用者は `s09_modules_testing::Celsius` と短く書ける
- **内部のモジュール構成を変えても、公開しているパスは変わらない**。内部の整理と、外への約束を切り離せる

標準ライブラリもこれを多用しています。例えば `std::collections::HashMap` の実装は、別の場所（`hashbrown` クレート）にあります。

## 4. 3種類のテスト

| 種類 | 置き場所 | 見えるもの | 目的 |
|---|---|---|---|
| **ユニットテスト** | 同じファイルの `#[cfg(test)] mod tests` | 非公開のものも含めて全部 | 内部の部品が正しく動くか |
| **統合テスト** | `tests/*.rs` | `pub` なものだけ | 利用者から見て、API が使いやすく正しいか |
| **doc テスト** | doc コメント (`///`) の中のコード例 | `pub` なものだけ | ドキュメントの例が、実際に動くか |

### `#[cfg(test)]` とは

`#[cfg(test)]` は「テストのときだけコンパイルする」という指定です。`cargo build` で作る本番の実行ファイルには、テストのコードは含まれません。

### 統合テストは別のクレート

`tests/public_api.rs` は、`cargo test` のときに**独立した別のクレート**としてコンパイルされ、あなたのライブラリを外部の依存として使います（[CS基礎 10](../../docs/fundamentals/10_compilation.md) のリンクの話です）。そのため、`pub` なものしか使えません。
「外から使ってみると、意外と使いにくい」ことに気づける場所です。

### doc テスト: 腐らないドキュメント

```rust
/// ```
/// use s09_modules_testing::Celsius;
/// assert!(Celsius::new(-300.0).is_none());
/// ```
```

doc コメントに書いたコード例は、`cargo test` で**実際にコンパイルして実行されます**。
他の言語では、ドキュメントの例は実装が変わると古くなりがちです。Rust では、例が古くなるとテストが失敗するので、**ドキュメントが嘘をつかなくなります**。docs.rs に公開されるクレートのドキュメントの例が信用できるのは、このためです。

## 5. ⭐ テストしやすい設計: 依存の注入

次の関数はテストが困難です。

```rust
fn greeting() -> &'static str {
    let hour = SystemClock.hour(); // 現在時刻に直接依存している
    // ...
}
```

朝の挙動を確かめたくても、テストを実行するのが夜なら確かめられません。
外の世界（時刻・ファイル・DB・ネットワーク・乱数）に**直接**触る関数は、結果が毎回変わったり、準備が大変だったりして、テストしにくくなります。

そこで、外の世界に触る部分をトレイトにして、**引数で受け取る**ようにします。

```rust
fn greeting(clock: &impl Clock) -> &'static str { ... }

greeting(&SystemClock);   // 本番: 本物の時計
greeting(&FixedClock(7)); // テスト: いつでも朝7時
```

これを**依存の注入**（dependency injection）と呼びます。テスト用の偽物の実装は**フェイク**や**モック**と呼ばれます。

### 他の言語との比較

- Java の Spring や C# の .NET では、DI コンテナという仕組みが、実行時に依存を自動で組み立てます
- Rust では DI コンテナはほとんど使われません。**トレイトとジェネリクスで、コンパイル時に組み立てます**。`impl Clock` は単相化されるので（[CS基礎 10](../../docs/fundamentals/10_compilation.md)）、本番のコードに抽象化のコストは残りません

### やりすぎに注意

何でもトレイトにすると、コードが読みにくくなります。トレイトにするのは**外の世界との境界**だけにしましょう。
`fn add(a: u32, b: u32)` のような純粋な計算は、そのままテストできます。

**理想の形**: 外の世界に触るコードは薄く外側に置き、判断のロジックは純粋な関数として内側に置く（"functional core, imperative shell"）。内側は簡単にテストでき、外側はテストすることが少なくなります。

## 6. テストを書くということ

ex03 では、実装がすでにあり、あなたがテストを書きます。実務ではこちらのほうが多いはずです。

良いテストのための観点:

- **仕様の例**をそのまま確かめる
- **境界値**: 0、空、1つだけ、最大値、範囲のちょうど端（`greeting` の 11時と 12時のように）
- **異常系**: エラーになるべき入力が、正しいエラーになるか
- **1つのテストでは、1つのことを確かめる**。失敗したときに、何が壊れたかがすぐ分かるように
- テストの名前で、何を確かめているかが分かるようにする

> テストは、バグがあることを示すことはできても、バグがないことを示すことはできない。— Edsger Dijkstra
