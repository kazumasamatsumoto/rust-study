# Stage 10: 並行処理 — 解説と設計判断

> **前提知識**: [08 プロセス・スレッド・データ競合](../../docs/fundamentals/08_concurrency.md)（**必読**）/ [03 スタックとヒープ](../../docs/fundamentals/03_memory.md)
> データ競合と競合状態の違い、Mutex とアトミックの違いが分かっていないと、この Stage の「なぜ」が理解できません。

Rust の売り文句の1つが「**恐れのない並行性**」（fearless concurrency）です。
C++ や Java で並行処理のバグに苦しんだ人ほど、この Stage で Rust の価値を実感するはずです。

---

## 1. スレッドを作る: `spawn` と `join`

```rust
let handle = thread::spawn(|| 1 + 1); // 新しいスレッドで実行する
let result = handle.join().unwrap();   // 終わるまで待って、戻り値を受け取る
```

- `spawn` は、すぐに `JoinHandle` を返します。スレッドは裏で動き続けます
- `join` は、そのスレッドが終わるまで待ちます。スレッドの中で panic が起きていれば `Err` が返ります
- **join しないまま main が終わると、他のスレッドは途中でも強制終了されます**

## 2. ⭐ なぜ `move` が必要なのか

次のコードはコンパイルエラーになります。

```rust
let v = vec![1, 2, 3];
let h = thread::spawn(|| println!("{:?}", v));
```

```
error[E0373]: closure may outlive the current function, but it borrows `v`, which is owned by the current function
  |
4 |     let h = thread::spawn(|| println!("{:?}", v));
  |                           ^^                  - `v` is borrowed here
  |                           |
  |                           may outlive borrowed value `v`
  |
note: function requires argument type to outlive `'static`
help: to force the closure to take ownership of `v` (and any other referenced variables), use the `move` keyword
```

新しいスレッドは、**呼び出し元の関数が終わった後も動き続けるかもしれません**。そうなると、`v`（呼び出し元のスタックにある）はもう消えているのに、スレッドがそれを読もうとすることになります。[CS基礎 04](../../docs/fundamentals/04_pointers.md) の**ダングリングポインタ**そのものです。

そのため `spawn` は、クロージャが `'static`（借用を含まない、いつまでも生きていられる）であることを要求します。解決策は2つです。

**(a) `move` で所有権ごと渡す**

```rust
let h = thread::spawn(move || println!("{:?}", v)); // v の所有権はスレッドへ
```

**(b) scoped threads（`thread::scope`）で、終わるタイミングを保証する**

```rust
thread::scope(|s| {
    s.spawn(|| println!("{:?}", v)); // 借用できる!
}); // ← ここで、scope の中で作ったスレッドが全て join されることが保証される
println!("{:?}", v); // v はまだ使える
```

`scope` を抜ける前に全てのスレッドが終わることが保証されるので、コンパイラは「`v` より長く生きるスレッドはない」と分かり、借用を許します。
ex01 の `parallel_map` は (b) を、`parallel_sum` は (a) を使う課題です。

## 3. チャネル: メッセージを送る

```rust
let (tx, rx) = mpsc::channel();
thread::spawn(move || tx.send(42).unwrap());
let v = rx.recv().unwrap(); // 42
```

チャネルは、スレッド間の「パイプ」です。`send` した値の**所有権は受信側に移ります**。送った側はもう触れないので、2つのスレッドが同じデータを同時に触ることが、そもそも起こりません。

- `mpsc` = multiple producer, single consumer。`tx.clone()` で送信側を増やせます
- 全ての送信側が drop されると、受信側の `recv()` は `Err` を返し、`for v in rx` のループが終わります
- **元の `tx` を drop し忘れると、受信側は永遠に待ち続けます**。ex02 で一度はハマるはずです

## 4. 共有状態: `Arc<Mutex<T>>`

複数のスレッドから同じデータを読み書きしたいときは、`Arc` と `Mutex` を組み合わせます。

| 型 | 役割 |
|---|---|
| `Arc<T>` | **所有の共有**。最後の1つが drop されたときに、中身が解放される |
| `Mutex<T>` | **書き換えの排他制御**。鍵を取ったスレッドだけが中身を触れる |

```rust
let counter = Arc::new(Mutex::new(0));
let c = Arc::clone(&counter);         // 参照カウントを1増やす（中身はコピーしない）
thread::spawn(move || *c.lock().unwrap() += 1);
```

### `Rc` ではなく `Arc` を使う理由

`Rc`（Stage 08）も所有を共有するポインタですが、スレッドに渡そうとするとコンパイルエラーになります。

```
error[E0277]: `Rc<Vec<i32>>` cannot be sent between threads safely
  = help: within `{closure@rc.rs:6:19: 6:26}`, the trait `Send` is not implemented for `Rc<Vec<i32>>`
```

`Rc` は、参照カウントを**普通の整数**で数えています。2つのスレッドが同時に `clone` すると、[CS基礎 08](../../docs/fundamentals/08_concurrency.md) のカウンタと同じように、カウントが壊れます。カウントが実際より少なくなると、まだ使っているのに解放されてしまいます（解放後の使用）。
`Arc` は、カウントを**アトミック**（Atomically Reference Counted）に数えます。安全ですが、アトミックな操作の分だけ少し遅くなります。

そのため、Rust では次のように使い分けます。
- 1つのスレッドの中だけで使う → `Rc`（速い）
- スレッドをまたぐ → `Arc`（安全）

**間違えて `Rc` をスレッドに渡すと、コンパイラが止めてくれます**。他の言語では「1スレッド用の速い版」と「スレッド安全な版」を間違えて使っても、実行時にたまに壊れるだけで、気づくのが難しいバグになります。

## 5. ⭐ `Send` と `Sync`: データ競合をコンパイル時に防ぐ仕組み

上のエラーに出てきた `Send` が、Rust の並行処理の安全性の核心です。

| トレイト | 意味 | 実装していない代表例 |
|---|---|---|
| `Send` | その値の**所有権を、別のスレッドに移してよい** | `Rc<T>` |
| `Sync` | その値への**参照 `&T` を、複数のスレッドで共有してよい** | `Cell<T>`, `RefCell<T>` |

- この2つは**マーカートレイト**で、メソッドを持ちません。「この型はこういう性質を持つ」という印です
- 中身が全て `Send` の構造体は、**自動的に** `Send` になります。`Sync` も同じです。自分で実装を書く必要はほとんどありません
- `thread::spawn` は「クロージャが `Send` であること」を要求します。そのため、`Send` でない値をスレッドに渡すコードは、コンパイルが通りません

つまり、**データ競合を起こしうる型は、そもそもスレッドの間で受け渡せない**ようになっています。
`Mutex<T>` は、中身が `Send` であれば `Sync` になります。鍵で守っているので、`&Mutex<T>` を共有しても安全だからです。

ex03 のテストには、次のような関数があります。

```rust
fn assert_send_sync<T: Send + Sync>() {}
assert_send_sync::<Bank>();
```

これは実行時には何もしません。`Bank` が `Send + Sync` でなければ、**コンパイルエラーになる**ことでテストしています。型の性質をテストする、Rust ならではの書き方です。

### 防げないもの

[CS基礎 08](../../docs/fundamentals/08_concurrency.md) で学んだとおり、Rust が防ぐのは**データ競合**だけです。次のものは防げません。

- **競合状態**: 「残高を確認してから引き出す」を、別々の鍵の取得で行うと、その間に他のスレッドに割り込まれる
- **デッドロック**: ex03 の `Bank::transfer` で体験します。テストが終わらなくなったら、それがデッドロックです

## 6. 並列計算のライブラリ: rayon（紹介のみ）

ex01 の `parallel_sum` を、実務ではこう書きます。

```rust
use rayon::prelude::*;
let sum: u64 = data.par_iter().sum(); // iter() を par_iter() に変えるだけ
```

[rayon](https://docs.rs/rayon) は、**スレッドプール**と**ワークスティーリング**（暇なスレッドが、忙しいスレッドの仕事を奪って手伝う仕組み）を使って、自動で処理を分担します。
`par_iter` に渡すクロージャにも `Send` / `Sync` が要求されるので、ここでもデータ競合はコンパイル時に防がれます。
この Stage で手書きしているのは、rayon が裏で何をしているのかを理解するためです。

## 7. ⭐ 選球眼: 並行処理の3つのスタイル

| スタイル | 考え方 | 長所 | 短所 | 向いている場面 |
|---|---|---|---|---|
| **共有しない**（分割して最後に合算） | データを分けて、各スレッドに独立して処理させる | 最速、最も安全 | 分割できる問題にしか使えない | 集計、画像処理、バッチ処理 |
| **メッセージパッシング**（チャネル） | データを「送る」。同時に触るのは常に1つのスレッドだけ | 流れが追いやすい。所有権と相性が良い | 送るたびにコストがかかる。全体の状態を見るのが難しい | パイプライン、ワーカープール、イベント処理 |
| **共有メモリ**（Arc + Mutex） | 同じデータを、鍵を取って順番に触る | 共有状態を直接扱える | ロック競合で遅くなる。デッドロックの危険 | キャッシュ、カウンタ、接続プール |

[CS基礎 08](../../docs/fundamentals/08_concurrency.md) の実験で、「共有しない」が Mutex より約600倍速かったことを思い出してください。
**判断の順番**: まず共有しない設計ができないかを考える → 次にメッセージパッシング → どうしても必要な場合に共有メモリ。

### Go の goroutine との比較

Go には有名な言葉があります。

> Don't communicate by sharing memory; share memory by communicating.
> （メモリを共有して通信するな。通信によってメモリを共有せよ）

これはメッセージパッシングを勧めるもので、Rust のチャネルの考え方とも共通しています。違うのは、**守らなかったときに何が起きるか**です。

| | Go | Rust |
|---|---|---|
| 並行処理の単位 | goroutine（軽量。最初のスタックは数KB。ランタイムが OS スレッドの上で多数を切り替える） | OS スレッド（`std::thread`）。軽量なものが欲しければ async（Stage 11） |
| 1万個作れるか | 簡単に作れる | OS スレッドでは重い。async を使う |
| チャネルで送った値を、送った後も触れるか | **触れてしまう**（ポインタを送れば、両方から同時に触れる） | **触れない**（所有権が移る） |
| データ競合の検出 | **実行時**。`go run -race` で、実際にその経路を通ったときだけ見つかる | **コンパイル時**。safe Rust では書けない |
| 書きやすさ | `go f()` だけで始められる。とても簡単 | 所有権、`Send`、`'static` を考える必要がある |

**判断の目安**
- 大量の並行接続を、チームの誰でもすぐに書けるようにしたい → Go の手軽さは大きな武器です
- 並行処理のバグが致命的で、コンパイル時に保証が欲しい → Rust
- Rust で大量の並行接続を扱いたい → スレッドではなく async（tokio）を使います。これが次の Stage 11 のテーマです
