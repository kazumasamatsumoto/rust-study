## 1. async fn と `.await`

```rust
async fn fetch_price(item: &str) -> u32 { ... }

let price = fetch_price("apple").await;
```

- `async fn` を呼ぶと、**すぐに値が返る**わけではありません。返ってくるのは「将来 `u32` になるもの」= `Future<Output = u32>` です
- `.await` して初めて実行され、結果の `u32` が手に入ります
- `.await` は `async` の中でしか書けません

### 順番に await すると、待ち時間は足し算になる

```rust
let a = fetch_price("apple").await; // 100ms 待つ
let b = fetch_price("milk").await;  // さらに 100ms 待つ → 合計 200ms
```

async で書いただけでは、速くなりません。これは async を学び始めた人がよく誤解するポイントです。
**同時に進めたいものは、同時に進めるように書く**必要があります。

### 同時に進める方法

| 方法 | 動き方 | 使う場面 |
|---|---|---|
| `tokio::join!(a, b)` | 同じタスクの中で、a と b を交互に poll する | 数が決まっている少数の Future |
| `tokio::spawn(fut)` | 新しい**タスク**を作ってランタイムに渡す。マルチスレッドのランタイムなら、別のスレッドで並列に動くこともある | 独立した仕事。数が実行時に決まる |
| `JoinSet` | spawn したタスクをまとめて管理する | 多数のタスクの結果を集める |

### なぜ `tokio::spawn` には `'static` が必要なのか

```rust
pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
where
    F: Future + Send + 'static,
```

spawn したタスクは、**spawn した関数より長く生き続ける**可能性があります。spawn した側が先に return してしまうかもしれません。
そのため、タスクの中で借用（`&str` など）を使うと、借用元が先に消えてダングリング参照になる恐れがあります。
`'static` は「借用を含まない（または、プログラムが終わるまで生きる借用しか含まない）」という意味です。
だから課題の `total_concurrent` は、`&[&str]` ではなく、所有権ごと渡せる `Vec<String>` を受け取ります。

`Send` は「別のスレッドに送ってよい」という意味です（Stage 10 / CS基礎 08）。マルチスレッドのランタイムでは、タスクが途中で別のスレッドに移ることがあるので必要になります。

## 2. select! とキャンセル

```rust
tokio::select! {
    v = fetch() => Some(v),
    _ = sleep(Duration::from_secs(1)) => None,
}
```

`select!` は、複数の Future を同時に進め、**最初に終わったものの分岐だけ**を実行します。**負けた方の Future は drop されます**。

Rust の Future は poll されなければ何もしないので、drop すれば、その処理は**その場で止まります**。これが Rust の async の**キャンセル**です。
タイムアウトやユーザーによる中断を簡単に書けるのは長所です。一方で、「処理の途中でキャンセルされても、データが壊れないか」を考える必要が出てきます（**キャンセル安全性**）。
例えば、ファイルの半分だけを書いたところでキャンセルされたら、どうなるでしょうか。tokio のドキュメントには、メソッドごとに cancel safe かどうかが書かれています。

## 3. チャネル

タスク同士でデータを受け渡すには、**チャネル**を使います。

| チャネル | 送る側 → 受ける側 | 使う場面 |
|---|---|---|
| `mpsc` | 多 → 1 | 仕事の受け渡し（キュー） |
| `oneshot` | 1 → 1、1回だけ | 1つの結果を返す |
| `broadcast` | 1 → 多 | 全員への通知 |
| `watch` | 1 → 多、最新の値だけ | 設定値の変更の通知 |

`mpsc::channel(16)` の `16` は**バッファの大きさ**です。バッファがいっぱいになると、送る側の `send().await` は空きができるまで待ちます。
これを**背圧**（バックプレッシャー）と呼びます。消費者が遅いときに、生産者が勝手にメモリを食いつぶさないようにするための仕組みです。
（`unbounded_channel` を使うと上限がなくなりますが、その分メモリを使い切る危険があります。）

## 4. ⭐ ブロッキング処理を async の中でやってはいけない理由

`blocking_demo` の結果（手元の Mac での実行結果）:

```
== B: std::thread::sleep (async の中でやってはいけない) ==
  [B] tick at    0ms
  [B] tick at  501ms   ← 100ms ごとに動くはずが、止まっている
  [B] tick at  604ms

== C: spawn_blocking に逃がす ==
  [C] tick at    0ms
  [C] tick at  101ms   ← 止まらない
  [C] tick at  212ms
```

async のタスクは協調的マルチタスクで動いています（CS基礎 09）。`.await` しない処理は、**そのスレッドで動いている他のタスクを全部止めてしまいます**。
マルチスレッドのランタイムでも、ワーカースレッドの数は CPU のコア数くらいしかありません。ブロッキング処理がいくつか重なると、サーバ全体が止まります。

| 処理 | async の中でどうするか |
|---|---|
| ファイルやネットワークの I/O | `tokio::fs`, `tokio::net` の async 版を使う |
| 待つこと | `std::thread::sleep` ではなく `tokio::time::sleep(...).await` |
| 重い計算（画像処理、ハッシュ、圧縮など） | `tokio::task::spawn_blocking` で別のスレッドに逃がす。大量の並列計算なら `rayon` |
| 同期版しかないライブラリ（一部の DB ドライバなど） | `spawn_blocking` に包む |

目安として、**`.await` と `.await` の間が 10〜100µs を超える**ようなら、ブロッキングを疑いましょう。

## 5. Future を自分で実装する

課題 03 の `Countdown` で、`async fn` が裏でやっていることを手で書きます。ポイントは2つです。

1. `poll` は「状態を1歩進めて、終わったなら `Ready`、まだなら `Pending`」を返す
2. `Pending` を返すなら、**必ず誰かが後で Waker を呼ぶようにしておく**

`Countdown` は、すぐに `wake_by_ref()` を呼んで「すぐにまた poll して」と頼んでいます。
本物の I/O の Future では、Waker を OS の通知（epoll や kqueue）に登録して、データが届いたときに呼ばれるようにします。tokio の中身は、この仕組みを大規模にしたものです。

## 6. ⭐ 選球眼: async とスレッド、どちらを選ぶか

**async は「速くなる魔法」ではありません。** 解決するのは「**大量の待ち**」だけです。

| 状況 | 向いている方式 | 理由 |
|---|---|---|
| 数万の同時接続を持つ Web サーバ、プロキシ、チャット | **async** | ほとんどの時間が待ち。スレッドではメモリとコンテキストスイッチのコストが大きい |
| 外部 API を大量に同時に叩くクローラ | **async** | 同上 |
| CPU を使い切る計算（画像処理、数値計算、圧縮） | **スレッド / rayon** | 待ちがないので async にする意味がない。協調的マルチタスクでは、むしろ他のタスクを止めてしまう |
| ファイルを順番に処理する CLI ツール | **普通の同期コード** | 並行性が要らないなら、一番シンプルなもので十分 |
| 同時接続が数十程度の社内ツール | **どちらでもよい**。スレッドの方が簡単なことが多い | スレッド数十本のコストは問題にならない |

**async を使うことのコスト**
- 学ぶことが増える（`Send` / `'static` / `Pin` / キャンセル安全性）
- コンパイルエラーが分かりにくくなりがち
- ランタイム（tokio）への依存が増える
- 関数の色の問題（下で説明します）

Rust のエコシステムでは、Web 系のライブラリ（axum, reqwest, sqlx）の多くが async を前提にしています。そのため実務では「選ぶ」というより「乗る」ことも多いです。それでも、**CLI やバッチ処理に async を持ち込む必要があるかどうか**は、毎回考える価値があります。

### なぜ Rust には標準のランタイムがないのか

Go や JavaScript では、言語にランタイムが組み込まれています。Rust の標準ライブラリにあるのは、`Future` トレイトと `async`/`await` の構文だけです。それを動かすランタイムは、外部のクレートから選びます。

理由は、Rust が想定している動作環境の幅が広いからです。

- **サーバ**: マルチスレッドで、work-stealing（暇なスレッドが他のスレッドの仕事を取ってくる）方式のランタイムが欲しい → `tokio`
- **組み込み機器**: OS もヒープもない環境で、割り込みと組み合わせて動くランタイムが欲しい → `embassy`
- **WASM（ブラウザ）**: ブラウザのイベントループの上で動かしたい → `wasm-bindgen-futures`

1つのランタイムを標準にすると、これらの用途のどれかが犠牲になります。そこで Rust は「インターフェース（`Future`）だけを標準にし、実装は選べるようにする」という方針を取りました（`docs/judgment/02_choosing_crates.md` の「標準ライブラリが小さい理由」と同じ考え方です）。

**その代わりに払うもの**: ライブラリが特定のランタイム（ほとんどの場合 tokio）に依存してしまう、という問題があります。tokio 用のライブラリは、別のランタイムの上では動かないことがあります。

### ランタイムの選択肢

| ランタイム | 特徴 | 選ぶ場面 |
|---|---|---|
| `tokio` | 事実上の標準。機能が多く、エコシステムが最大 | 迷ったらこれ。サーバ用途ではほぼこれ一択 |
| `smol` | 小さくシンプル | 依存を小さくしたいツール |
| `embassy` | 組み込み向け。ヒープが不要 | マイコン |
| `glommio` / `monoio` | スレッドごとに独立したランタイム（thread-per-core）。`io_uring` を使う | 極限まで性能を求めるストレージやプロキシ。Linux 専用 |

### 他の言語の async との比較

| | Rust | Go | JavaScript (Node) | Python (asyncio) |
|---|---|---|---|---|
| 仕組み | ステートマシン + 外部のランタイム | **goroutine**（ランタイムが管理する軽量なスレッド） | 単一スレッドのイベントループ + Promise | 単一スレッドのイベントループ + コルーチン |
| `await` を書くか | 書く | **書かない**（普通の関数呼び出しに見える） | 書く | 書く |
| 実行の開始 | `.await` / `spawn` するまで動かない（遅延） | `go f()` ですぐ動く | Promise を作った時点で動く（先行） | `await` / `create_task` するまで動かない |
| マルチコア | 使える | 使える | 使えない（Worker を除く） | 使えない（GIL がある。最近の版では外せる選択肢もある） |
| CPU を使い続けるタスク | 他のタスクを止める | ランタイムが横取りして切り替える（Go 1.14 から） | イベントループ全体が止まる | イベントループ全体が止まる |
| タスクのサイズ | 必要な変数の分だけ | 小さなスタック（数KB から伸びる） | Promise とクロージャ | コルーチンのオブジェクト |

**Go は「関数に色を付けない」道を選びました。** goroutine はランタイムが管理するので、普通の関数を書くだけで、ブロッキングする処理も自動的に他の goroutine に譲ります。分かりやすい反面、ランタイム（GC やスケジューラ）が必ず付いてくるので、組み込み機器などには向きません。

**Rust は「ゼロコストで、どこでも動く」ことを優先しました。** その代わり、`.await` を書く手間や、`Pin` などの複雑さを利用者が引き受けています。

### 関数の色の問題

2015年に Bob Nystrom が "What Color is Your Function?" という記事で指摘した問題です。

- 関数には「赤（async）」と「青（普通）」の2色がある
- **赤い関数は、赤い関数の中からしか呼べない**（`.await` は async の中でしか書けない）
- 一番下の関数を1つ async にすると、それを呼んでいる関数を全部 async にしなければならなくなる。色が上へ上へと伝染していく
- 同じ機能のライブラリに、async 版と同期版の2種類が必要になる（`reqwest` と `reqwest::blocking`、`tokio::fs` と `std::fs`）

Rust、JavaScript、Python、C# はこの問題を抱えています。Go は goroutine で回避しています。
Rust では、プログラムの入口で `#[tokio::main]` を使うか、`Runtime::block_on` で、同期の世界から async の世界に入ります。逆に async の中から同期の重い処理を呼ぶときは、`spawn_blocking` を使います。
**どこを async の境界にするか**を決めるのは、設計上の大事な判断です。
