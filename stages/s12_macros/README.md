# Stage 12: マクロ — 解説と設計判断

> **前提知識**: [10 コンパイルとリンク](../../docs/fundamentals/10_compilation.md)（マクロがコンパイルのどの段階で展開されるか）/ [07 ディスパッチ](../../docs/fundamentals/07_dispatch.md)（ジェネリクスとの比較）

`println!`、`vec!`、`assert_eq!`、`#[derive(Debug)]`、`#[tokio::main]`。ここまでの Stage で、すでに何十回もマクロを使ってきました。
この Stage では、マクロを**自分で書けるようになる**ことと、**マクロを書くべきかどうかを判断できるようになる**ことを目指します。
大事なのは後者です。マクロは強力ですが、使いすぎるとコードが読めなくなります。

---

## 1. マクロとは何か: コードを生成するコード

関数は**実行時**に呼ばれて、値を受け取り値を返します。
マクロは**コンパイル時**に展開されて、**コードの断片を受け取り、コードの断片を返します**。

```
ソースコード
   ↓ 字句解析（文字列を「トークン」に分ける）
トークン列
   ↓ 構文解析 + ★ マクロ展開（マクロ呼び出しを、生成したコードに置き換える）
構文木 (AST)
   ↓ 名前解決・型検査・借用検査
   ↓ LLVM で機械語に
実行ファイル
```

マクロの展開は**型検査より前**に行われます。つまりマクロは「型」を知りません。知っているのは「どんなトークンが、どんな形で並んでいるか」だけです。
これが、マクロにできることとできないことを決めています。

### なぜ `println!` は関数ではないのか

```rust
println!("{} + {} = {}", a, b, a + b);
```

- Rust の関数は**引数の数が固定**です（C の `printf` のような可変長引数はありません）。マクロなら、任意の数の引数を受け取れます
- フォーマット文字列の `{}` の数と引数の数が合っているかを、**コンパイル時に検査**しています。`println!("{} {}", a)` はコンパイルエラーになります。C の `printf("%d %d", a)` は、コンパイルが通って実行時に壊れたデータを表示します

「関数では書けないこと」をするためにマクロがある、というのが基本の考え方です。

## 2. C のマクロとの違い: テキスト置換ではなく、構文の単位で置き換える

C のマクロ（プリプロセッサ）は、**ただの文字列置換**です。

```c
#define SQUARE(x) x * x
SQUARE(1 + 2)   // → 1 + 2 * 1 + 2 → 5（9 ではない！）
```

Rust で同じものを素直に書いて、実験してみました。

```rust
macro_rules! square_naive {
    ($x:expr) => { $x * $x };
}
```

実行結果:

```
square_naive!(1 + 2) = 9
square_naive!(next()) = 2
next() が呼ばれた回数 = 2
```

- **`1 + 2` は正しく 9 になりました。** `$x:expr` は「式」という**構文の単位**で受け取るので、展開しても `(1 + 2) * (1 + 2)` として扱われます。C のように、かっこを付け忘れて演算の優先順位が崩れることはありません
- **しかし `next()` は 2 回呼ばれました。** 展開結果は `next() * next()` なので、副作用のある式は 2 回評価されます。ここは C と同じ落とし穴です

課題の `square!` では、この 2 つ目の問題を解決してもらいます。

## 3. `macro_rules!` の書き方

```rust
macro_rules! 名前 {
    (パターン1) => { 展開結果1 };
    (パターン2) => { 展開結果2 };   // 上から順に試され、最初に一致したものが使われる
}
```

### フラグメント指定子

パターンの中の `$名前:種類` は、「この位置にこの種類の構文が来る」という意味です。

| 指定子 | 一致するもの | 例 |
|---|---|---|
| `expr` | 式 | `1 + 2`, `foo()`, `v[0]` |
| `ident` | 識別子 | `x`, `Color`, `my_func` |
| `ty` | 型 | `i32`, `Vec<String>` |
| `literal` | リテラル | `42`, `"abc"`, `true` |
| `pat` | パターン | `Some(x)`, `1..=5` |
| `vis` | 可視性（空でもよい） | `pub`, `pub(crate)`, (なし) |
| `meta` | 属性の中身 | `derive(Debug)`, `doc = "..."` |
| `tt` | トークン木 1 つ | 何でも。かっこで囲まれた部分は全体で 1 つ |

### 繰り返し

```rust
$( $k:expr => $v:expr ),*    // 「キー => 値」がカンマ区切りで 0 回以上
$( $x:expr ),+               // 1 回以上
$(,)?                        // 末尾のカンマがあってもなくてもよい（0 回か 1 回）
```

展開側でも同じ書き方で繰り返せます。パターン側で `$k` が 3 回一致したなら、展開側の `$( map.insert($k, $v); )*` も 3 回繰り返されます。

### 再帰

マクロは自分自身を呼び出せます。`max_of!(3, 9, 2)` は、次のように展開されていきます。

```
max_of!(3, 9, 2)
→ max(3, max_of!(9, 2))
→ max(3, max(9, max_of!(2)))
→ max(3, max(9, 2))
```

ただし、再帰の深さには上限があります。`count!` を 150 個のトークンに対して使ってみると、次のエラーになりました。

```
error: recursion limit reached while expanding `count!`
```

上限のデフォルトは 128 です。クレートの先頭に `#![recursion_limit = "256"]` と書けば引き上げられますが、コンパイルが遅くなります。再帰の深さがトークンの数に比例するマクロは、大きな入力には向きません。

## 4. ⭐ 衛生性 (hygiene)

マクロの中で作った変数は、**呼び出し側の変数とは別物**として扱われます。これを**衛生性**と呼びます。

実験:

```rust
macro_rules! make_x {
    () => { let x = 1; };
}
macro_rules! make_var {
    ($name:ident) => { let $name = 1; };
}

let x = 10;
make_x!();          // マクロの中で x = 1 を作る
println!("{x}");
make_var!(y);       // 呼び出し側から渡した名前 y で変数を作る
println!("{y}");
```

実行結果:

```
make_x!() の後の x = 10
make_var!(y) の後の y = 1
```

- `make_x!` の中の `x` は、呼び出し側の `x` を上書き**しませんでした**。マクロの中の `x` と外の `x` は、名前が同じでも別の変数です。コンパイラも「マクロの中の `x` が使われていない」と警告を出しました
- `make_var!(y)` のように、**呼び出し側が名前を渡した場合**は、その名前で変数が作られ、外から使えます

C のマクロには衛生性がないので、マクロの中で `tmp` という変数を使うと、呼び出し側の `tmp` と衝突してバグになります。そのため C では、`__my_macro_tmp_42` のような、衝突しにくい奇妙な名前を付けるのが習慣になっています。
（衛生的なマクロという考え方は、Lisp 系の言語 Scheme で生まれたものです。）

### ただし、パスは呼び出し側で解決される

`macro_rules!` の衛生性が守ってくれるのは、**ローカル変数とラベルだけ**です。関数名や型名のようなパスは、**呼び出した場所**で解決されます。

```rust
macro_rules! hashmap {
    () => { HashMap::new() };   // ✗ 呼び出し側で HashMap が use されていないとエラー
}
macro_rules! hashmap {
    () => { ::std::collections::HashMap::new() };   // ◎ どこから呼んでも同じものを指す
}
```

- 標準ライブラリのものは `::std::...` とフルパスで書く
- 自分のクレートのものは `$crate::...` と書く。`$crate` は、マクロを定義したクレートを指す特別な変数です。他のクレートから使われても正しく解決されます

課題のマクロが、全て `::std::` や `$crate::` を使って書かれているのはこのためです。

### 空の入力に気を付ける

`hashmap!` を 1 つのパターンだけで書くと、`hashmap! {}` のときに次の展開になります。

```rust
let mut map = HashMap::new();
map   // 何も insert していないのに mut
```

これは「`mut` が不要」という警告になります（実際に模範解答で引っかかりました）。マクロは**入力によって展開結果が変わる**ので、空の場合や要素が 1 つの場合など、**端のケースでの展開結果**を想像する必要があります。

## 5. ⭐ `#[derive]` もマクロである

`#[derive(PartialEq)]` は、**手続き型マクロ (procedural macro)** の一種です。
nightly コンパイラの `-Zunpretty=expanded` というオプションで、展開した結果を見てみました。

```rust
#[derive(Debug, PartialEq)]
struct Point { x: i32, y: i32 }
```

展開結果（PartialEq の部分）:

```rust
#[automatically_derived]
impl ::core::cmp::PartialEq for Point {
    #[inline]
    fn eq(&self, other: &Self) -> bool {
        self.x == other.x && self.y == other.y
    }
}
```

**自分で書いた場合と全く同じコードが生成されている**だけです。derive に魔法はありません。
（展開結果を見るには、`cargo install cargo-expand` で入るコマンド `cargo expand` を使うのが普通です。nightly が必要です。）

### 手続き型マクロの3種類

| 種類 | 書き方 | 例 |
|---|---|---|
| derive マクロ | `#[derive(Serialize)]` | `serde::Serialize`, `thiserror::Error`, `clap::Parser` |
| 属性マクロ | `#[tokio::main]` | `tokio::main`, `axum::debug_handler`, `tracing::instrument` |
| 関数風マクロ | `sqlx::query!("...")` | `sqlx::query!`（コンパイル時に DB に接続して SQL を検査する） |

`macro_rules!` との違い:

- **普通の Rust のコードで書く**。トークン列を受け取ってトークン列を返す関数を書き、その中では何でもできます（ファイルを読む、DB に接続する、など）
- **専用のクレート**（`Cargo.toml` に `proc-macro = true`）に分ける必要があります
- 構文を解析するために `syn`、コードを組み立てるために `quote` というクレートを使うのが定番です

**その代わりに払うもの**: `syn` は大きなクレートなので、**コンパイル時間が延びます**。serde の derive を使うと、プロジェクトのビルド時間のかなりの割合を `syn` のコンパイルが占めることもあります。

この Stage では手続き型マクロは書きません。「derive の正体は、コードを生成する普通のプログラム」と分かっていれば十分です。

## 6. 他の言語では

| 言語 | 仕組み | 特徴 |
|---|---|---|
| C / C++ | プリプロセッサ（`#define`） | 文字列置換。衛生性がなく、演算の優先順位や二重評価の問題が起きる |
| C++ | テンプレート、`constexpr` | 型に応じたコード生成と、コンパイル時計算 |
| Lisp / Scheme | マクロ | コードがそのままデータ（リスト）なので、マクロが非常に強力。衛生的なマクロの元祖 |
| Go | `go generate` | 言語の外の、コード生成ツール。生成したファイルをリポジトリに入れる |
| Java | アノテーションプロセッサ（Lombok など） | コンパイル時にコードを生成する。Rust の derive に近い |
| TypeScript / Python | デコレータ | **実行時**に関数やクラスを書き換える。コンパイル時の検査はない |

Rust のマクロは、「C のマクロの危険さ（文字列置換・衛生性の欠如）を取り除き、Lisp のように構文単位で扱えるようにしたもの」と言えます。

## 7. ⭐ 選球眼: 関数か、ジェネリクスか、マクロか

**原則: まず関数で書く。それで書けなければジェネリクスやトレイト。それでも書けないときだけマクロ。**

| 手段 | 向いている場面 | コスト |
|---|---|---|
| 関数 | ほとんど全て | ほぼなし |
| ジェネリクス + トレイト | 型だけが違う同じ処理 | 単相化によるコンパイル時間とバイナリサイズ |
| `macro_rules!` | 可変長の引数、型や impl の量産、式のテキストが欲しい（`stringify!`） | 読みにくい、エラーメッセージが分かりにくい、IDE の補完が効きにくい |
| 手続き型マクロ | derive、属性、コンパイル時の外部検査 | 上に加えて、専用クレートとコンパイル時間 |

**マクロにしかできないこと**

- **可変長の引数**: `vec![1, 2, 3]`, `max_of!(a, b, c)`
- **型・impl・関数の定義を生成する**: `enum_str!`, `newtype!`
- **書かれたコードのテキストを使う**: `assert_eq!` は、失敗したときに `left` と `right` の式を表示します
- **呼び出し元の制御フローを変える**: `?` 演算子ができる前は、`try!` というマクロで `return` を埋め込んでいました
- **コンパイル時の検査**: `println!` のフォーマット文字列、`sqlx::query!` の SQL

**マクロを使うときに払うもの**

- **読む人の負担**: マクロの呼び出しを見ても、何が生成されるのか分かりません。展開結果を想像する必要があります
- **エラーメッセージ**: マクロの中でエラーが起きると、「マクロのどこで、何が悪かったのか」が分かりにくくなります
- **ツールの支援**: rust-analyzer の補完や、rustfmt による整形が、マクロの中では効きにくくなります
- **デバッグ**: 展開されたコードにはブレークポイントを置きにくい

`square!` は、実は関数で十分です。

```rust
fn square<T: std::ops::Mul<Output = T> + Copy>(x: T) -> T { x * x }
```

関数なら、引数が 1 回しか評価されないことが**言語のルールとして**保証されます。課題で `square!` をマクロとして書いたのは、練習のためです。実務では、このようなマクロは書かないでください。
