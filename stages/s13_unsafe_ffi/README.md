# Stage 13: unsafe と FFI — 解説と設計判断

ここまでの Stage では、「コンパイラが安全性を保証してくれる」世界で書いてきました。

## 1. `unsafe` は「チェックを切る」という意味ではない

よくある誤解は、「`unsafe` ブロックの中では、Rust のチェックが全部止まる」というものです。実際には違います。

- 借用チェッカーも型チェックも、`unsafe` の中で**普通に動いています**
- `unsafe` で使えるようになるのは、**5つの操作**だけです
- そして `unsafe` と書くことは、「**コンパイラには検証できない約束を、私が代わりに守ります**」という宣言です

### unsafe で解禁される5つの操作

| 操作 | 例 | なぜコンパイラが検証できないのか |
|---|---|---|
| 生ポインタの参照外し | `*ptr` | ポインタの指す先が有効かどうかは、実行時にしか分からない |
| unsafe な関数の呼び出し | `slice::from_raw_parts(p, n)`、C の関数 | 関数ごとに、守るべき前提条件がある |
| 可変な static 変数へのアクセス | `static mut COUNTER` | 複数のスレッドから同時に触れるとデータ競合になる |
| unsafe なトレイトの実装 | `unsafe impl Send for MyType` | 「この型はスレッド間で渡しても安全」とコンパイラは判断できない |
| union のフィールドの読み出し | `u.as_float` | どのフィールドの値が入っているか、コンパイラには分からない |

それ以外のことは、`unsafe` と書いても、何も変わりません。

## 2. ⭐ 未定義動作 (UB) とは何か

unsafe を理解するうえで最も重要な概念が、**未定義動作**（Undefined Behavior、UB）です。

> **未定義動作**: 言語の規則を破ったとき、その後に「何が起きても仕様違反ではない」状態。

UB は「クラッシュする」という意味では**ありません**。「どうなるか分からない」という意味です。

- クラッシュするかもしれない
- **たまたま正しく動くかもしれない**（これが一番厄介です）
- 間違った値を黙って返すかもしれない
- コンパイラの最適化によって、**書いたはずのコードが消える**かもしれない

### なぜコードが消えるのか

コンパイラは「**プログラムに UB は存在しない**」という前提で最適化します。例えば、

```rust
fn is_null(r: &i32) -> bool {
    let p: *const i32 = r;
    p.is_null()
}
```

参照 `&i32` は決してヌルにならない、というのが Rust の規則です。そのためコンパイラは、この関数を「常に `false` を返す」と最適化してよいことになっています。

実際に release ビルドのアセンブリを出力して確かめると（`#[inline(never)]` を付け、引数は `std::hint::black_box` で隠しました）、`is_null` の呼び出しは跡形もなく消え、結果の場所に `false`（ゼロ）を直接書き込む命令 `strb wzr, [sp, #15]` だけが残っていました。**ヌルかどうかを調べるコード自体が、存在しなくなった**のです。
もし unsafe なコードでヌルの参照を作ってしまったら、この判定は機能しません。**規則を破ったコードは、それより後の、一見無関係なコードまで壊してしまう**のです。

C 言語のコンパイラも同じ前提で最適化します。例えば「符号付き整数はオーバーフローしない」と仮定して、オーバーフローをチェックするための `if` 文を消してしまうことがあり、実際にセキュリティ上の問題を引き起こしてきました。

### Rust の主な UB

- ダングリングポインタや、ヌルポインタの参照外し
- アラインメントが合っていないポインタからの読み書き（後述）
- データ競合
- 不正な値を作ること（`bool` に 0 と 1 以外の値、範囲外の `char`、初期化されていないメモリの読み出し）
- `&mut T` が存在している間に、同じ場所への別の参照を使うこと（エイリアシングの規則の違反）

**safe な Rust だけで書かれたコードは、UB を起こさない**ことが保証されています。これが Rust の安全性の正確な意味です。
逆に言えば、unsafe を書いた瞬間から、UB を起こさない責任はプログラマに移ります。

## 3. 生ポインタ

| | 参照 `&T` / `&mut T` | 生ポインタ `*const T` / `*mut T` |
|---|---|---|
| ヌルになりうる | ならない | なりうる |
| 指す先が有効か | 常に有効（借用チェッカーが保証） | 分からない |
| アラインメント | 常に正しい | 保証なし |
| ライフタイム | ある | ない |
| `&mut` の排他性 | 保証される | 保証されない（同じ場所を指す `*mut` を何個でも作れる） |
| 作るのは | 安全 | **安全** |
| 参照外しは | 安全 | **unsafe** |

生ポインタを**作るだけ**なら安全です。危険なのは、それを**使う**ときだけです。そのため `unsafe` は、参照外しの部分にだけ必要になります。

## 4. ⭐ 借用チェッカーの限界: `split_at_mut`

次のコードは、コンパイルできません。

```rust
fn split(s: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    (&mut s[..mid], &mut s[mid..]) // エラー: s を同時に 2 回、可変で借用している
}
```

人間が見れば、`[0, mid)` と `[mid, len)` が**重ならない**ことは明らかです。重ならない 2 つの領域を同時に書き換えても、何の問題もありません。
しかし借用チェッカーは、「スライス `s` の可変な借用が 2 つある」としか判断できません。**インデックスの計算の結果が重ならないことまでは、証明できない**のです。

このような「人間には安全だと分かるが、コンパイラには証明できない」コードを書くために unsafe があります。
標準ライブラリの `split_at_mut` は、課題 01 で書くのとほぼ同じ方法で、内部的に unsafe を使って実装されています。

借用チェッカーは、**安全なプログラムを全て受け入れる**わけではありません。**受け入れたプログラムは安全**である、ということを保証しているだけです。安全なのに拒否されるプログラムも存在します。

## 5. アラインメント

CS基礎 03 で見たように、CPU は `u32` を 4 の倍数のアドレスから読むことを前提にしています。Rust では、**アラインメントが合っていないポインタから `*p` で読むことは UB** です。

実験:

```
align_of::<u8>()  = 1
align_of::<u32>() = 4
align_of::<u64>() = 8
&buf[0..] のアドレス = 0x16dba9b08  (4 で割った余り = 0)
&buf[1..] のアドレス = 0x16dba9b09  (4 で割った余り = 1)
&buf[2..] のアドレス = 0x16dba9b0a  (4 で割った余り = 2)
&buf[3..] のアドレス = 0x16dba9b0b  (4 で割った余り = 3)
```

バイト列 `[u8]` は、どの位置からでも切り出せます。`&buf[1..]` の先頭は、4 の倍数のアドレスにありません。
これを `*(ptr as *const u32)` で読むと UB です。x86 の CPU ではたまたま動くことが多いので、この種のバグは**ある環境では動き、別の環境では壊れる**という形で見つかります。

`ptr::read_unaligned` は、アラインメントを仮定せずに読みます。課題 01 の `read_u32_le` はこれを使います。
（実務では `u32::from_le_bytes` を使えば、unsafe なしで同じことができます。）

## 6. ⭐ unsafe を安全な API で包む

unsafe なコードを書くときの基本形は、次の 3 つを組み合わせることです。

1. **不変条件**（invariant）を決める。課題 02 では「`buf[0..len]` は全て初期化済み」
2. 不変条件を壊せないように、**フィールドを非公開**にする
3. **全ての公開メソッドが不変条件を守る**ことを確かめる

これができていれば、**どんな使い方をしても safe なコードからは UB を起こせない**、という API になります。この性質を**健全性**（soundness）と呼びます。

> **健全な API**: safe なコードからどう呼び出しても、UB が起きない API。
> 1 つでも UB を起こす呼び出し方があれば、その API は**不健全**（unsound）であり、バグです。

### unsafe の影響範囲は、モジュール全体

課題 02 の `pop` は、次のようになっています。

```rust
self.len -= 1;
unsafe { self.buf[self.len].assume_init_read() }  // 不変条件により初期化済み
```

この unsafe が正しいかどうかは、`len` が正しい値であることに依存しています。
ということは、**unsafe を一切含まない別のメソッド**が `self.len += 1` と書いてしまうだけで、この unsafe は UB になります。
unsafe ブロックの正しさは、そのブロックの中だけでは決まらず、**同じ不変条件に触れる全てのコード**に依存します。
そのため、unsafe を使う型は小さなモジュールに閉じ込め、フィールドに触れるコードを最小限にします。

### `MaybeUninit`

`[T; N]` のような配列は、作った瞬間に N 個の値が必要です。`MaybeUninit<T>` を使えば、「あとで値を入れる箱」だけを用意できます。

実験:

```
size_of::<String>()                   = 24
size_of::<MaybeUninit<String>>()      = 24
size_of::<Option<String>>()           = 24
size_of::<[MaybeUninit<String>; 4]>() = 96
```

`MaybeUninit` は、**「初期化済みかどうか」の情報を持たない**ので、サイズが増えません。その情報は、プログラマが（課題 02 では `len` で）管理します。
（`Option<String>` も 24 バイトのままなのは、ニッチ最適化のおかげです。CS基礎 03 を参照。）

`MaybeUninit` は、中身が初期化されているかどうかを知らないので、**中身を自動では drop しません**。課題 02 で `Drop` を自分で実装するのはこのためです。

## 7. SAFETY コメントの書き方

unsafe には、2 種類のドキュメントを書きます。

```rust
/// スライスの i 番目を、範囲チェックなしで返す。
///
/// # Safety                         ← unsafe fn には「呼び出す側が守るべき条件」を書く
///
/// 呼び出す側は `i < s.len()` を保証しなければならない。
pub unsafe fn get_unchecked_copy(s: &[i32], i: usize) -> i32 {
    // SAFETY: 呼び出し側が i < s.len() を保証している   ← unsafe ブロックには「なぜ条件を満たしているか」を書く
    unsafe { *s.as_ptr().add(i) }
}

// 呼び出す側
// SAFETY: 0 は v.len() == 3 より小さい
let x = unsafe { get_unchecked_copy(&v, 0) };
```

- `# Safety`: **呼び出す人への約束事**。clippy の `missing_safety_doc` がチェックします
- `// SAFETY:`: **その約束をなぜ守れているか**の説明。clippy の `undocumented_unsafe_blocks` がチェックします（この Stage では有効にしてあります）

SAFETY コメントが書けないなら、そのコードはまだ安全だと言えない、ということです。
レビューで unsafe を見つけたら、まず SAFETY コメントを読み、その主張が本当に正しいかを確かめます。

### Rust 2024 の変更

- `unsafe fn` の中でも、unsafe な操作は `unsafe { }` で囲むことが求められます（囲まないと `unsafe_op_in_unsafe_fn` という警告が出ます）。関数全体が unsafe だと、どこが危険な操作なのかが分からなくなるためです
- `extern` ブロックは `unsafe extern "C" { ... }` と書きます。「この宣言が本物の C の関数と一致している」ことを、書いた人が保証するという意味です

## 8. Miri: UB を検出するツール

**Miri** は、Rust のプログラムを 1 命令ずつ解釈しながら実行し、UB を検出するツールです。
範囲外アクセス、解放後の使用、アラインメント違反、初期化されていないメモリの読み出し、エイリアシングの規則の違反などを見つけてくれます。

```bash
rustup +nightly component add miri
cargo +nightly miri test -p s13_unsafe_ffi
```

- 1 命令ずつ検査しながら実行するので非常に遅く、本番で使うものではなく、テストを動かすための道具です
- C の関数の呼び出しなど、FFI を含むコードへの対応は限られています。FFI を含むテストは、`#[cfg_attr(miri, ignore)]` で Miri の実行から外すことがあります
- 「Miri で何も出なかった」ことは、「テストで通った経路では UB が見つからなかった」という意味です。UB がないことの証明ではありません

unsafe を含むクレートの多くは、CI で Miri を実行しています。

## 9. FFI: 他の言語と話す

**FFI**（Foreign Function Interface）は、他の言語で書かれた関数を呼び出したり、他の言語から呼び出されたりする仕組みです。

### なぜ必要か

- 既存の C のライブラリを使いたい（SQLite、OpenSSL、画像処理のライブラリ、OS の API など）
- Rust の標準ライブラリ自体も、ファイルやネットワークの操作のために、OS の C の関数（libc）を呼んでいます
- 逆に、既存の C / C++ / Python のプロジェクトの一部を Rust で書き換えたい

### ABI: 関数の呼び出し方の約束

関数を呼ぶときに、引数をどのレジスタやスタックに置き、戻り値をどこで受け取るか、という約束を **ABI**（Application Binary Interface）と呼びます。
Rust の普通の関数の ABI は**決まっていません**（コンパイラが自由に最適化してよい）。`extern "C"` と書くと、その関数は **C の ABI** で呼ばれるようになり、C との間で呼び合えるようになります。

Rust と C は同じ ABI を使えるので、FFI の呼び出しは**普通の関数呼び出しと同じコスト**です。
Go の cgo や Java の JNI は、ランタイムの事情により、C の関数を呼ぶたびに追加の処理が必要になります。この点は Rust の大きな強みです。

### 文字列: 最大の違い

| | Rust の `&str` / `String` | C の `char *` |
|---|---|---|
| 長さの管理 | ポインタと一緒に長さを持つ | **NUL バイト (`\0`) が来たら終わり** |
| 途中の NUL | 含められる | 含められない（そこで終わりになる） |
| 文字コード | UTF-8 が保証される | 保証なし（ただのバイト列） |

そのため、境界で変換が必要になります。

| 型 | 意味 | 対応する Rust の型 |
|---|---|---|
| `CString` | Rust から C に渡すための、末尾に NUL を付けた所有する文字列 | `String` |
| `&CStr` | C から受け取った、NUL で終わる文字列を借りて見るもの | `&str` |

実験:

```
CString::new("hi") のバイト列 = [104, 105, 0]
CString::new("a\0b") = Err(NulError(1, [97, 0, 98]))
strlen("hi") = 2
strlen("こんにちは") = 15
```

- `CString` は、末尾に `0` を付け足しています
- 途中に NUL がある文字列は、C の文字列にできないので `Err` になります（1 バイト目に NUL がある、と教えてくれます）
- `strlen` が返すのは**バイト数**です（CS基礎 05）

### C の関数の前提条件を、Rust の型で守る

C の `abs(INT_MIN)` は、C の規格で**未定義動作**です。なぜなら、

```
i32::MIN               = -2147483648
i32::MIN.checked_abs() = None
i32::MIN.wrapping_abs()= -2147483648
i32::MIN.unsigned_abs()= 2147483648
```

`i32` の最大値は 2147483647 なので、2147483648 は `i32` で表せないからです（CS基礎 01 の2の補数）。
課題 03 の `c_abs` では、C の関数を呼ぶ**前に**この入力を弾き、`Option` で返します。
**C の関数の「やってはいけない入力」を、Rust の関数のシグネチャと事前チェックで防ぐ**のが、FFI のラッパーを書くときの基本です。

### 所有権は境界を越えない

- C の `malloc` で確保したメモリは、C の `free` で解放する。Rust で drop してはいけない
- Rust で確保したメモリを C に渡したら、C 側にそれを解放させてはいけない。解放用の関数を Rust 側で用意して、C から呼んでもらう

アロケータが別物なので、混ぜると壊れます。

### panic は境界を越えられない

C には、Rust の panic（スタックを巻き戻しながら drop を実行する仕組み）を受け止める方法がありません。そのため `extern "C"` の関数の中で panic すると、**プロセス全体が強制終了**します。実験:

```rust
extern "C" fn callback() {
    panic!("extern \"C\" の中で panic");
}
fn main() {
    let r = std::panic::catch_unwind(|| callback()); // panic を受け止めようとしても…
}
```

```
thread 'main' panicked at examples/panic_ffi.rs:2:5:
extern "C" の中で panic

thread 'main' panicked at .../core/src/panicking.rs:225:5:
panic in a function that cannot unwind
...
thread caused non-unwinding panic. aborting.
```

終了コードは 134（SIGABRT）で、`catch_unwind` でも受け止められませんでした。
課題 03 の `compare_i32` だけが `todo!()` ではなく仮に `0` を返すスタブになっているのは、このためです。C から呼ばれる関数では、`unwrap` やオーバーフローする計算など、**panic しうる処理を書かない**ようにします。

### C から Rust を呼ぶ（解説のみ）

```rust
#[unsafe(no_mangle)]          // 関数名を変えずに出力する（Rust は普通、名前を内部的に変える）
pub extern "C" fn add(a: i32, b: i32) -> i32 { a + b }
```

`Cargo.toml` で `crate-type = ["cdylib"]`（共有ライブラリ）や `["staticlib"]`（静的ライブラリ）を指定してビルドすると、C から呼べるライブラリができます。
ヘッダファイル（`.h`）は `cbindgen` で自動生成できます。逆に、C のヘッダから Rust の `extern` 宣言を自動生成するのが `bindgen` です。
C のライブラリを包むクレートは、`openssl-sys` や `libsqlite3-sys` のように、**`-sys` という名前で生の宣言だけを提供し、別のクレート（`openssl`, `rusqlite`）が安全な API を提供する**、という 2 層構造にするのが慣習です。課題 03 で書いたラッパー関数は、この「安全な API の層」にあたります。

## 10. 他の言語では

| 言語 | 安全でない操作の扱い |
|---|---|
| C / C++ | **全てのコードが unsafe**。どこに危険があるか、コードからは分からない |
| Java | 基本的に安全。`sun.misc.Unsafe` や JNI で外に出られる |
| C# | `unsafe` キーワードがあり、ポインタを使えるのはその中だけ。Rust に近い考え方 |
| Go | `unsafe` パッケージと cgo。import しているかで危険な箇所が分かる |
| Python | 言語としては安全。C 拡張や `ctypes` で FFI を行い、その中では何でも起こりうる |

Rust の特徴は、**危険な箇所が `unsafe` というキーワードで目に見えて、検索できる**ことです。
C++ のプロジェクトでメモリ安全性のバグを探すときは、コード全体を疑う必要があります。Rust なら、`unsafe` を grep すれば、調べるべき場所が分かります。

## 11. ⭐ 選球眼: unsafe を使うべき時、使うべきでない時

### 使ってよい場面

- **FFI**: C のライブラリや OS の API を呼ぶ。避けようがありません
- **基本的なデータ構造を作る**: `Vec`, `HashMap`, 固定長スタック、ロックフリーのキューなど。ただし、ほとんどの場合は既存のものがあります
- **計測した結果、本当に必要な最適化**: safe なコードで書いた版と比べて、ベンチマークで差が出たときだけ

### 使うべきでない場面

- **「借用チェッカーがうるさいから」**: ほぼ確実に設計を見直すべきサインです。Stage 08 のインデックスや `Rc<RefCell>` で解決できないかを考えましょう
- **計測していない最適化**: 例えば `get_unchecked` で範囲チェックを省いても、速くならないことが多くあります。イテレータを使ったり、ループの前に長さを確認したりすると、オプティマイザが範囲チェックを自動で消してくれるからです
- **既存のクレートで済む場合**: `arrayvec` / `heapless`（固定長コレクション）、`bytemuck` / `zerocopy`（バイト列と構造体の変換）など、unsafe を正しく閉じ込めた、広く検証されたクレートがあります

自分のクレートの先頭に `#![forbid(unsafe_code)]` と書けば、そのクレートでは unsafe を一切使えなくなります。アプリケーションのクレートでは、これを方針にすることも多いです。

### unsafe を使っているクレートをどう評価するか

[docs/judgment/02_choosing_crates.md](../../docs/judgment/02_choosing_crates.md) のチェックリストの「`unsafe` の量」を、もう一段詳しく見ます。
**unsafe があること自体は問題ではありません**（標準ライブラリにも大量にあります）。問題は、**それが正しく閉じ込められ、検証されているか**です。

| 確認すること | 方法 |
|---|---|
| どれくらい使っているか | `cargo geiger` で、依存を含めた unsafe の数を数える |
| SAFETY コメントがあるか | ソースで `unsafe` を検索して、理由が書かれているかを読む |
| 検証しているか | CI で Miri やファジング（`cargo fuzz`）を実行しているか |
| 健全性のバグの履歴 | GitHub の Issue で `unsound` というラベルや単語を検索する。RustSec のアドバイザリを確認する |
| なぜ unsafe が必要なのか | README やドキュメントで説明されているか。safe な代替手段はないのか |

2020年には、人気の Web フレームワーク actix-web で、不要かつ不健全な unsafe が多数指摘され、コミュニティで大きな議論になりました。
**人気があることは、unsafe が正しいことを保証しない**、という例です。
