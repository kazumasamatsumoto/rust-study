# Stage 14: 型による設計 — 解説と設計判断

> **前提知識**: Stage 03 の「不正な状態を表現できなくする」（**必読**） / Stage 06 のトレイト / [02 浮動小数点数](../../docs/fundamentals/02_floats.md)（お金を f64 で持たない理由） / [03 スタックとヒープ](../../docs/fundamentals/03_memory.md)（型のサイズ）

この Stage のテーマは、「**間違った使い方をすると、コンパイルが通らない API**」を設計することです。
Stage 03 で触れた考え方を、実務で使われている道具を使って本格的に実践します。

---

## 1. 間違いをいつ見つけるか

ある関数に「この引数は 0 より大きくなければならない」という決まりがあるとします。この決まりを守らせる方法は、いくつかあります。

| 方法 | 間違いに気付くタイミング | 例 |
|---|---|---|
| ドキュメントに書く | 誰かがバグに気付いたとき（気付かないこともある） | 「※ 0 を渡さないでください」 |
| 実行時にチェックして panic する | テストや本番で、その行が実行されたとき | `assert!(n > 0)` |
| 実行時にチェックして `Result` を返す | 同上。ただし呼び出し側に処理を強制できる | `NonZeroU32::new(n)` が `Option` を返す |
| **型で表す** | **コンパイルしたとき** | 引数の型を `NonZeroU32` にする |

下に行くほど、間違いに**早く**気付けます。テストを書き忘れていても、そもそもそのコードが実行されなくても、コンパイラが必ず見つけてくれます。
Rust は、型で表すための道具が特に豊富な言語です。この Stage ではそれを1つずつ見ていきます。

**ただし、タダではありません。** 型が増え、コードは長くなり、エラーメッセージは難しくなります。どこまで型で守るのかは、毎回判断が必要です（最後の節で扱います）。

## 2. newtype: 同じ「数」でも、意味が違えば別の型にする

### 単位の取り違え

1999 年、NASA の火星探査機マーズ・クライメイト・オービターは、火星の大気に突入して失われました。
原因の一つは、地上のソフトウェアが推力のデータを**ヤード・ポンド法**（ポンド重・秒）で出力していたのに、受け取る側のソフトウェアは**メートル法**（ニュートン・秒）だと思って計算していたことでした。どちらもただの浮動小数点数だったので、プログラムは何の疑問も持たずに計算を続けました。

newtype（1 つのフィールドだけを持つ構造体）で包むと、コンパイラが区別してくれます。

```rust
pub struct Meters(pub f64);
pub struct Feet(pub f64);

let total = Meters(1.0) + Feet(3.0);                 // コンパイルエラー
let total = Meters(1.0) + Meters::from(Feet(3.0));   // 変換を明示すれば OK
```

ID も同じです。`fn orders_of(orders: &[Order], user: UserId)` に `OrderId` を渡すと、コンパイルエラーになります。ただの `u64` だったら、気付かないまま間違ったデータを返していたでしょう。

### コストはゼロ

実際に測ってみると、包んでもサイズは変わりません。

```
f64: 8, Meters: 8
u64: 8, UserId: 8
i64: 8, Money<Usd>: 8
```

newtype は**コンパイル時にだけ存在する区別**で、実行時には中身の値そのものとして扱われます。ゼロコスト抽象化の典型例です。
（レイアウトが中身と同じであることを言語として保証したい場合は、`#[repr(transparent)]` を付けます。C の関数に渡すときなどに必要になります。）

### 他の言語では

| 言語 | 同じことをするには | 手軽さ |
|---|---|---|
| Rust | `struct UserId(u64);` | ◎ 1 行。コストゼロ |
| Haskell | `newtype UserId = UserId Int` | ◎（「newtype」という名前はここから来ている） |
| Go | `type UserId int64` | ○ ただし定数は暗黙に変換されてしまう |
| TypeScript | `type UserId = number & { __brand: "UserId" }`（branded type） | △ 小技が必要。実行時には区別がない |
| Java | `record UserId(long value) {}` | △ オブジェクトになるので、ヒープ確保やポインタのコストがかかる |

Java で `long` を `UserId` で包むと、`List<UserId>` の各要素はヒープ上の別々のオブジェクトになります（[12 メモリ階層](../../docs/fundamentals/12_memory_hierarchy.md) の「散らばったデータは遅い」）。そのため Java では、性能が気になる場面では newtype を避けがちです。
Rust では、コストを気にせずに使えます。**「安全のための道具が、速さを犠牲にしない」**ことが、Rust で型による設計が広く使われている理由です。

### もう 1 つの使い道: 孤児ルールの回避

Stage 06 で、「トレイトか型のどちらかが自分のものでなければ impl を書けない」という孤児ルールを学びました。
`Vec<String>` に `Display` を実装したいときは、`struct Lines(Vec<String>);` という newtype を作れば、自分の型になるので実装できます。

## 3. "Parse, don't validate"（検証するな、パースせよ）

`Email` 型を見てください。

```rust
pub struct Email(String);  // フィールドは非公開

impl Email {
    pub fn parse(s: &str) -> Result<Email, EmailError> { ... }  // 唯一の作り方
}
```

フィールドが非公開なので、`Email` を作る方法は `parse` しかありません。つまり、**`Email` 型の値が存在するなら、それは必ず検証を通っています**。

これの何が嬉しいのでしょうか。2 つの設計を比べてみましょう。

```rust
// (A) 検証する (validate): 文字列のまま持ち回る
fn is_valid_email(s: &str) -> bool { ... }
fn send_welcome(email: &str) { /* ここで渡された email は検証済み？ 分からない */ }

// (B) パースする (parse): 検証の結果を型に変える
fn send_welcome(email: &Email) { /* 必ず検証済み */ }
```

(A) では、`send_welcome` を書く人は「誰かが検証してくれたはず」と信じるしかありません。心配な人は関数ごとに検証を書き、そのうちどこかで書き忘れます。
(B) では、**検証は入口で 1 回だけ**行われ、その結果が型として持ち運ばれます。内側の関数は、型を見るだけで安心できます。

この考え方は、Alexis King のブログ記事 "Parse, don't validate"（2019 年）で有名になりました。

`NonEmptyVec` も同じ考え方です。

```rust
let v: Vec<i32> = ...;
v.first()          // Option<&i32> — 空かもしれないので
let v: NonEmptyVec<i32> = ...;
v.first()          // &i32 — 空でないことが型で保証されているので
```

「空かもしれない」というケースを、**型を作った時点で 1 回だけ処理**しています。後のコードには `unwrap()` も `if let` も要りません。

> **選球眼**: 外から入ってくるデータ（HTTP リクエスト、設定ファイル、DB の値）は、**境界でパースして型に変え、内側では検証済みの型だけを使う**。これは Rust に限らず、どの言語でも使える設計の原則です。Rust では `serde` と組み合わせると、デシリアライズの時点でパースまで済ませられます。

## 4. typestate パターン: 状態を型で表す

### Stage 03 との違い

Stage 03 の自販機では、状態を enum で表しました。

```rust
enum Vending { Idle, HasMoney(u32), Dispensed { change: u32 } }
fn handle(self, event: Event) -> Vending
```

この方式では、「Idle のときにボタンを押す」という意味のない操作も、`handle` に渡すことができてしまいます。仕方がないので、実行時に「何もしない」として処理しました。

typestate パターンでは、**状態ごとに別の型**を用意し、その状態でできる操作だけをメソッドとして定義します。

```rust
impl Door<Closed> { fn open(self) -> Door<Open>; fn lock(self) -> Door<Locked>; }
impl Door<Open>   { fn close(self) -> Door<Closed>; }
impl Door<Locked> { fn unlock(self, code: u32) -> Result<Door<Closed>, Door<Locked>>; }
```

鍵のかかったドアには `open` メソッドが**存在しない**ので、開けようとするとコンパイルエラーになります。

```
error[E0599]: no method named `open` found for struct `Door<Locked>` in the current scope
```

### PhantomData: 「持っているふり」をする

```rust
pub struct Door<S> {
    code: u32,
    history: Vec<&'static str>,
    _state: PhantomData<S>,
}
```

`Door<S>` は、型パラメータ `S` を実際のフィールドとしては使っていません。Rust は使われていない型パラメータを許さないので、`PhantomData<S>` という「`S` を持っているふりをする、サイズ 0 のフィールド」を置きます。

```
Door<Open>: 32, Door<Locked>: 32
```

状態が違っても、サイズは同じです。状態は**コンパイル時にだけ存在**し、実行時のコストはありません。

### ⭐ typestate が成り立つのは、所有権があるから

`open(self)` は `self` を値で受け取る、つまり**ムーブ**します。

```rust
let closed = Door::new(1234);
let open = closed.open();
let again = closed.open();   // コンパイルエラー: closed はムーブ済み
```

```
error[E0382]: use of moved value: `closed`
```

ここが重要です。Java で同じことを書くと、こうなります。

```java
Door<Closed> closed = new Door<>(1234);
Door<Open> open = closed.open();
closed.lock();   // コンパイルが通ってしまう。古い変数がまだ使える
```

Java では古い状態のオブジェクトへの参照が残るので、「閉まっていたときのドア」をいつまでも使えてしまいます。型で状態を表しても、**古い状態から抜け出したことを保証できない**のです。

Rust では、状態を変えると古い値はムーブされて使えなくなります。**所有権（Stage 02）があるから、typestate パターンが本当に安全になる**のです。他の言語にも typestate の考え方はありますが、Rust ほど自然に書ける言語は多くありません。

### 失敗したときに値を返す

```rust
fn unlock(self, code: u32) -> Result<Door<Closed>, Door<Locked>>
```

`Err` にもドアを入れているのには理由があります。`self` はムーブ済みなので、失敗したときに何も返さないと、**ドアそのものが消えてしまいます**。
標準ライブラリにも同じ形があります。例えば `String::from_utf8(vec)` は、失敗すると `FromUtf8Error` を返し、その中から `into_bytes()` で元の `Vec<u8>` を取り戻せます。

### 実際の使われ方

- 組み込み向けの HAL（ハードウェア抽象化レイヤ）クレートでは、マイコンのピンの「入力モード」「出力モード」を型で表します。入力モードのピンに出力しようとすると、コンパイルエラーになります
- 必須の項目があるビルダー（次の節）
- 「接続前」「認証済み」「切断済み」のような、通信プロトコルの状態

### typestate を使うべきでない場面

| | enum + match（Stage 03） | typestate |
|---|---|---|
| 不正な操作を見つけるタイミング | 実行時 | コンパイル時 |
| 状態が**実行時に**決まる（DB から読み込む、ユーザーの入力で変わる） | ◎ | × 型はコンパイル時に決まっていなければならない |
| 異なる状態のものを 1 つの `Vec` に入れる | ◎ `Vec<Vending>` | × `Door<Open>` と `Door<Locked>` は別の型 |
| 状態が多い・遷移が複雑 | ○ | △ 型と impl ブロックが爆発的に増える |
| エラーメッセージの分かりやすさ | ◎ | △ 「メソッドが見つからない」としか言われない |

「ドアの一覧を DB から読み込んで画面に表示する」なら enum が向いています。「ドアを操作するライブラリの API」なら typestate が向いています。**両方を組み合わせる**こともよくあります（内部では enum で持ち、外に見せる API は typestate にする、など）。

## 5. ビルダーパターン

### なぜ Rust ではビルダーをよく使うのか

Rust には、**デフォルト引数**も**関数のオーバーロード**もありません。

```python
# Python ならこう書ける
request(url, method="GET", headers=None, timeout=30)
```

Rust で同じことをする方法は、主に 3 つあります。

```rust
// (1) 引数を全部書く — 引数が多いと読めない。どれが何だか分からない
Request::new("https://...", "GET", vec![], 30);

// (2) 構造体 + Default — 手軽。ただし必須の項目を強制できない
Request { url: "https://...".into(), ..Default::default() };

// (3) ビルダー — 読みやすい。必須の項目は typestate で強制できる
RequestBuilder::new().url("https://...").timeout_secs(5).build();
```

課題の `RequestBuilder<U>` は (3) に typestate を組み合わせたものです。`build()` は `RequestBuilder<HasUrl>` にしか定義されていないので、URL を設定し忘れるとコンパイルエラーになります。

```
error[E0599]: no method named `build` found for struct `RequestBuilder<NoUrl>` in the current scope
```

普通のビルダーなら、`build()` が `Result` を返して「URL がありません」というエラーを実行時に出すしかありません。

### 実務では

手で書くと長くなるので、derive マクロでビルダーを自動生成するクレートがよく使われます（`typed-builder`、`bon`、`derive_builder` など）。`typed-builder` や `bon` は、必須の項目を型でチェックするビルダーを生成します。
ただし、マクロが生成するコードは見えにくく、コンパイル時間も延びます。**項目が数個なら、(2) の `Default` で十分**なことも多いです。

## 6. sealed trait: 外から実装させないトレイト

```rust
mod sealed {
    pub trait Sealed {}          // 非公開モジュールの中の、公開トレイト
}
pub trait Currency: sealed::Sealed { ... }
```

`Currency` を実装するには、先に `sealed::Sealed` を実装しなければなりません。しかし `sealed` モジュールは非公開なので、外のクレートからは名前を書くことすらできません。結果として、**このクレートの中で定義した型しか `Currency` を実装できなくなります**。

```
error[E0277]: the trait bound `Bitcoin: ex03_money::sealed::Sealed` is not satisfied
```

### なぜわざわざ閉じるのか

1. **トレイトにメソッドを後から追加できるようにするため。**
   公開トレイトに、デフォルト実装のないメソッドを追加すると、**そのトレイトを実装している全ての利用者のコードが壊れます**（実装していないメソッドがあることになるため）。これはライブラリにとって、破壊的変更（メジャーバージョンを上げる必要がある変更）です。
   sealed にしておけば、実装しているのは自分のクレートの型だけなので、自由にメソッドを追加できます。

2. **実装する型の一覧を、自分で把握しておくため。**
   `Currency` の `DECIMALS` が正しい値であることは、このクレートが保証したい性質です。利用者が `DECIMALS = 100` のような変な通貨を作れると、その保証が崩れます。

それでも、利用者は `fn double<C: Currency>(m: Money<C>)` のように、**トレイトを境界として使う**ことはできます（`tests/external_user.rs` を見てください）。「使えるが、実装はできない」という状態を作るのが sealed trait です。

## 7. `#[non_exhaustive]`: 将来の追加に備える

```rust
#[non_exhaustive]
pub enum ParseMoneyError { Empty, InvalidDigit, TooManyDecimals { max: u32 }, Overflow }
```

この属性を付けると、**外のクレートで match するときに `_` の腕が必須**になります。

```
error[E0004]: non-exhaustive patterns: `_` not covered
```

その代わり、ライブラリの作者は、後から `NegativeNotAllowed` のようなバリアントを追加しても、利用者のコードを壊さずに済みます。
標準ライブラリの `std::io::ErrorKind` にもこの属性が付いていて、Rust のバージョンが上がるたびに新しい種類のエラーが追加されています。

**注意**: この効果は、**クレートの外でしか現れません**。同じクレートの中では、`_` なしで全てのバリアントを書けます。課題で `tests/external_user.rs` を用意しているのは、統合テストが「外のクレート」としてコンパイルされるので、この効果を確認できるからです。

### ⭐ トレードオフ: 網羅性チェックを手放す

Stage 03 で、「バリアントを追加すると、修正すべき場所をコンパイラが全部教えてくれる」ことを、enum の大きな利点として学びました。
`#[non_exhaustive]` を付けると、利用者は `_` を書かされるので、**この利点を失います**。新しいバリアントが追加されても、利用者のコードは黙って `_` の処理に流れます。

| | `#[non_exhaustive]` なし | あり |
|---|---|---|
| 作者がバリアントを追加したとき | 利用者のコードが壊れる（メジャーバージョンアップが必要） | 壊れない |
| 利用者が新しいバリアントに気付けるか | ◎ コンパイラが教えてくれる | × 気付けない |

エラーの種類のように「将来増えるのが当たり前」で、利用者も全部を個別に処理するわけではないものには付ける。
`Ordering::{Less, Equal, Greater}` のように「絶対に増えない」もの、あるいは利用者に全部を処理してほしいものには付けない。**誰のために、何を約束するのか**で選びます。

## 8. `#[must_use]`: 使わないと警告する

`#[must_use]` が付いた型や関数の戻り値を使わずに捨てると、警告が出ます。標準ライブラリでもあちこちで使われています。

```rust
let v = vec![1, 2, 3];
v.iter().map(|x| x * 2);     // 何も起きない
"42".parse::<i32>();         // エラーを無視している
```

```
warning: unused `Map` that must be used
  = note: iterators are lazy and do nothing unless consumed
warning: unused `Result` that must be used
  = note: this `Result` may be an `Err` variant, which should be handled
```

- イテレータは、`collect` や `sum` などで消費するまで何もしません（遅延評価）。`map` だけ書いても計算されないので、警告が出ます
- `Result` を無視すると、エラーを握りつぶしてしまうので、警告が出ます。**Stage 04 で「Rust ではエラーを無視するとコンパイラが警告する」と書いたのは、この仕組みのことです**

自分で付けるとよい場所の例:
- `self` を受け取らず、新しい値を返すメソッド（`fn with_discount(&self, pct: u32) -> Price`）。結果を捨てたら、呼んだ意味がない
- 戻り値を捨てると危険な関数（ロックのガード、トランザクションなど）

## 9. まとめ

| 道具 | 防げる間違い | 実行時のコスト | 払うもの |
|---|---|---|---|
| newtype | 単位や ID の取り違え | なし | 変換のコードを書く手間 |
| 検証済みの型（parse） | 検証のし忘れ、二重の検証 | 入口での検証 1 回 | 型の数が増える |
| typestate | 状態に合わない操作 | なし | 型と impl ブロックの増加、状態を実行時に決められない |
| 型付きのビルダー | 必須項目の設定し忘れ | なし | 書く量が多い（マクロで減らせる） |
| sealed trait | 想定外の型による実装 | なし | 利用者が拡張できない |
| `#[non_exhaustive]` | 将来の追加による破壊的変更 | なし | 利用者の網羅性チェックがなくなる |
| `#[must_use]` | 戻り値の捨て忘れ | なし | ほぼなし |

ほとんど全ての道具で、**実行時のコストはゼロ**です。払うのは、書く手間と、コードの複雑さです。

## 10. ⭐ 選球眼: どこまで型で守るか

型による設計は強力ですが、やりすぎると次のようなことが起きます。

- 型が多すぎて、コードを読む人が全体を把握できない
- ちょっとした変更のために、何十もの型と impl を書き換える必要がある
- エラーメッセージが難しく、チームの他のメンバーが触れなくなる

判断の目安:

1. **公開 API や、境界（外部からの入力）では厚く守る。** 使う人が多く、間違えたときの被害も大きいからです
2. **内部の、数十行で完結する処理では、普通の型で十分。** 読めば分かる範囲に、型の仕掛けは要りません
3. **「間違えたときの被害」と「型を作るコスト」を比べる。** お金、権限、単位、ID の取り違えは被害が大きいので、newtype にする価値が高いです。ログに出すだけの文字列を newtype にする価値は低いです
4. **チームが理解できるか。** 最も安全な API でも、誰も使い方を理解できなければ、結局誤用されます
