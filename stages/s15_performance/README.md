# Stage 15: 性能 — 解説と設計判断

> **前提知識**: [06 計算量とデータ構造](../../docs/fundamentals/06_complexity.md) / [10 コンパイルとリンク、最適化](../../docs/fundamentals/10_compilation.md)（**必読**） / [12 メモリ階層とキャッシュ](../../docs/fundamentals/12_memory_hierarchy.md)（**必読**） / [03 スタックとヒープ](../../docs/fundamentals/03_memory.md)

「Rust は速い」とよく言われます。しかし、Rust で書けば自動的に速くなるわけではありません。
遅いアルゴリズムは Rust でも遅いですし、アロケーションを大量にすれば Rust でも遅くなります。

この Stage では、次の順番で学びます。

1. **正しく測る**（測り方を間違えると、全ての判断を間違える）
2. **効果の大きい順に直す**（計算量 → アロケーション → データの持ち方 → 細かい最適化）
3. **いつ最適化するべきか、いつやめるべきかを判断する**

```bash
cargo run -p s15_performance --example measure --release   # 測り方の実験（課題を解かなくても動く）
cargo run -p s15_performance --example compare --release   # 課題を解いた後に、遅い版と比べる
```

## 1. 正しく測る

### 鉄則 1: debug ビルドで測らない

`measure` を debug ビルドと release ビルドで実行した結果です（「結果を black_box に渡す」の行）。

| | debug | release |
|---|---|---|
| 1000 万個の `x * 3` の合計 | 59.5ms | 4.2ms |
| 標準の HashMap に 100 万回 entry | 502ms | 23.6ms |

debug ビルドは、最適化をせず、オーバーフローのチェックなども入れているので、10〜20 倍遅くなります（[10 コンパイル](../../docs/fundamentals/10_compilation.md)）。
しかも、**どこが遅くなるかの比率も release とは違います**。debug ビルドでは、イテレータを使ったほうが速くなっていました（113ms vs 76ms）が、release ビルドではほぼ同じでした（後で見ます）。debug ビルドで「こっちが速い」と判断して書き換えても、release では意味がないかもしれません。

> 余談: この実験を作っている途中、最初のバージョンでは 2 乗の合計が `u64` に収まらず、**debug ビルドでだけ** `attempt to add with overflow` で panic しました。release ビルドでは何も言われずにラップアラウンドした、間違った値を出していました（[01 整数](../../docs/fundamentals/01_integers.md)）。性能を測る前に、debug ビルドで一度は正しく動くことを確かめるのも大事です。

### 鉄則 2: 計算が消えていないか疑う

```
結果を捨てる            :     42.000ns
結果を black_box に渡す :      4.230ms
```

1 行目は、1000 万個の数を足しているはずなのに、42ns で終わっています。これは速いのではなく、**計算していません**。
結果を誰も使わないので、コンパイラが計算を丸ごと消してしまったのです。

`std::hint::black_box(x)` は、「この値は誰かが使うかもしれない」とコンパイラに思わせる関数です。ベンチマークでは、入力と結果を `black_box` に通して、計算が消されないようにします。
「信じられないくらい速くなった」ときは、まず計算が消えていないかを疑いましょう。

### 鉄則 3: 1 回目は捨てる、何回か測る

```
1 回目:   23.845ms
2 回目:    4.636ms
3 回目:    4.163ms
4 回目:    4.298ms
5 回目:    4.944ms
```

同じ処理なのに、1 回目だけ 5 倍遅くなっています。`vec![0; n]` で確保したメモリは、OS が「最初に触ったときに」物理メモリを割り当てるので、1 回目にはそのコストが含まれているのです。
他にも、CPU キャッシュが温まっていない、CPU のクロックが上がりきっていない、などの理由で、最初の数回は遅くなりがちです（**ウォームアップ**）。

```
20 回実行: 最小 170.333µs / 中央値 344.458µs / 最大 374.375µs
```

ウォームアップの後でも、毎回ばらつきます。この例では、最小と中央値で 2 倍も違いました（別の回では最小 192µs / 中央値 193µs で、ほとんどばらつきませんでした。**ばらつき方そのものも、毎回違います**）。
1 回だけ測って「1.2 倍速くなった」と言っても、それはただの誤差かもしれません。

### 実務では: criterion

これらを自分で全部やるのは大変なので、実務では [`criterion`](https://crates.io/crates/criterion)（や、より新しい `divan`）というクレートを使います。

- ウォームアップを自動で行う
- 何百回も実行して、統計的に処理する（平均、信頼区間、外れ値）
- 前回の結果と比べて、「有意に速くなった／遅くなった」を教えてくれる

Part 3 の p02（KV ストア）で実際に使います。

### この Stage のテストが「速さ」を確かめない理由

速さは毎回ばらつくので、「1ms 以内に終わること」のようなテストを書くと、PC の調子や CI のマシンの混み具合によって、**通ったり落ちたりする**テストになってしまいます（flaky test / 不安定なテスト）。不安定なテストは、そのうち誰も信用しなくなり、無視されるようになります。

そこでこの Stage では:

- **正しさ**: 遅い版と同じ結果を返すことをテストで確かめる
- **アロケーションの回数**: テストで確かめる。回数は毎回同じなので、テストにしても不安定にならない（`alloc_counter.rs` を読んでみてください）
- **速さ**: `compare` の実験で、自分の目で確かめる

という分け方をしています。

## 2. どこから直すか: 効果の大きい順

### (1) 計算量（アルゴリズム）

`compare` を、模範解答で実行した結果です（この PC での一例。あなたの PC では違う値になります）。

```
has_duplicates (2万)    遅い版  47.277ms  →  189.208µs   249.9 倍
common (2万×2万)        遅い版  21.596ms  →  636.334µs    33.9 倍
moving_average (w=1000) 遅い版  40.469ms  →  134.417µs   301.1 倍
```

O(n²) を O(n) にすると、桁違いに速くなります。しかも、**データが増えるほど差が開きます**。2 万件で 250 倍なら、20 万件では 2500 倍近くになります。

どんなに細かい最適化（アロケーションを減らす、SIMD を使う）をしても、O(n²) のアルゴリズムが O(n) に勝つことはありません。**まず計算量を疑いましょう。**

よくある O(n²) の隠れ方:
- ループの中で `Vec::contains`（それ自体が O(n)）
- ループの中で `v.remove(0)` や `v.insert(0, x)`（CS基礎 06）
- ループの中で `s.chars().nth(i)`（UTF-8 なので O(n)、CS基礎 05）
- 移動平均のように、「前回の計算結果を少し変えれば済む」のに毎回最初から計算している

### (2) アロケーション

```
join            遅い版  4.645ms (9999 allocs)    →  41.125µs (1 allocs)   112.9 倍
fields (10万行)  遅い版 12.414ms (400000 allocs) →  3.109ms  (1 allocs)     4.0 倍
most_frequent   遅い版  6.545ms (200010 allocs)  →  2.560ms  (2 allocs)     2.6 倍
```

ヒープの確保は、空き領域を探したり、管理用の情報を更新したりする必要があるので、スタック上の計算よりずっと遅い処理です（[03 スタックとヒープ](../../docs/fundamentals/03_memory.md)）。さらに、確保したメモリはヒープのあちこちに散らばるので、キャッシュも効きにくくなります（[12 メモリ階層](../../docs/fundamentals/12_memory_hierarchy.md)）。

アロケーションを減らす典型的な方法:

| 方法 | 例 | 課題 |
|---|---|---|
| 最初に必要な大きさを確保する | `String::with_capacity(n)`, `Vec::with_capacity(n)` | `join` |
| 新しい値を作らず、借りたまま返す | `String` ではなく `&str` を返す | `fields_into`, `most_frequent` |
| 必要なときだけ新しい値を作る | `Cow<str>` | `normalize_spaces` |
| バッファを使い回す | `out.clear()` してから中身を入れ直す | `fields_into` |
| 不要な `clone()` / `to_string()` をやめる | `HashMap<String, _>` を `HashMap<&str, _>` にする | `most_frequent` |

`with_capacity` の効果は `measure` の実験 6 でも確かめられます。

```
Vec::new から push      :   24.549ms  (1 個あたり 6 回確保する)
with_capacity から push :    9.911ms  (1 個あたり 1 回)
```

長さ 100 の Vec を `Vec::new()` から作ると、容量が 0 → 4 → 8 → 16 → 32 → 64 → 128 と伸びるたびに確保し直すので、6 回のアロケーションが起きます（`alloc_counter` で実際に数えた値です）。

> **計測の落とし穴**: 最初はこの実験を「長さ 1000 万の Vec を 1 個作る」形で書きましたが、結果は実行するたびに「with_capacity の方が 1.5 倍速い」「ほぼ同じ」「2 倍遅い」とばらばらでした。巨大なメモリでは、OS がページを割り当てる時間や解放する時間が支配的になり、確保し直す回数の差（たった 20 回程度）が埋もれてしまったのです。
> 「with_capacity は速いはず」という思い込みで測ると、こういう結果を見落とします。**測りたいものが本当に測れているか**を、常に疑いましょう。

### ⭐ `Cow`: 「たいていは何もしなくていい」場合の最適化

```rust
pub fn normalize_spaces(s: &str) -> Cow<'_, str>
```

`Cow`（Clone on Write）は、「借りた値」か「所有している値」のどちらかを持つ enum です（Stage 08）。

- 入力がすでに綺麗なら、`Cow::Borrowed(s)` で入力をそのまま返す。アロケーションは 0 回
- 直す必要があるときだけ、`Cow::Owned(String)` で新しい文字列を返す

```
normalize (綺麗)  遅い版 179.916µs (14 allocs)  →  66.416µs (0 allocs)   2.7 倍
```

現実のデータの大半が「すでに綺麗」なら、この最適化はよく効きます。HTML のエスケープ、パスの正規化など、標準ライブラリやクレートのあちこちで使われているパターンです（`String::from_utf8_lossy` も `Cow` を返します）。

### (3) データの持ち方

[12 メモリ階層](../../docs/fundamentals/12_memory_hierarchy.md) で見たように、データをメモリ上にどう並べるかで、10 倍以上の差が出ることがあります。

- `Vec<Box<T>>` より `Vec<T>`（要素を散らばらせない）
- 一部のフィールドだけを大量に処理するなら、SoA を検討する
- 連結リストやツリーより、`Vec` とインデックスで表現できないか考える（Stage 08 の arena）

### (4) 細かい最適化 — たいていはコンパイラに任せる

```
インデックスのループ           :    1.709ms
イテレータ (filter → map → sum):    1.650ms
```

「イテレータは関数呼び出しがたくさん入るから遅いのでは？」と心配する人がいますが、release ビルドでは**ほぼ同じ速さ**です。コンパイラがクロージャをインライン化し、最終的に同じような機械語にしてくれるからです（ゼロコスト抽象化、[10 コンパイル](../../docs/fundamentals/10_compilation.md)）。
むしろイテレータは、範囲外アクセスのチェックを省けることが多いので、インデックスのループより速くなることもあります。

**読みやすいイテレータで書いてよい**し、そうするべきです。ループの書き方を細かく変えて速くしようとするのは、計測してそこがボトルネックだと分かってからにしましょう。

## 3. HashMap とハッシュ関数

### なぜ標準のハッシュ関数は「わざと遅め」なのか: HashDoS

HashMap は、キーをハッシュ関数で数値に変え、その数値で置き場所を決めます。**違うキーが同じ置き場所になる**（衝突する）と、そこでは線形探索が必要になります。

もし攻撃者が、**全部が同じ置き場所になるキー**を大量に送りつけたらどうなるでしょうか。

```
通常:   キーがばらける → 検索は平均 O(1)
攻撃:   全部が衝突する → 検索が O(n)、n 個入れると O(n²)
```

2011 年、PHP、Java、Python、Ruby などの Web フレームワークで、これを使った攻撃が可能だと発表されました（**HashDoS**、hash flooding）。HTTP の POST パラメータを内部で HashMap に入れる処理を狙い、細工したパラメータを数万個送るだけで、サーバの CPU を何十秒も使い切らせることができました。

対策は、**攻撃者が衝突を予測できないハッシュ関数**を使うことです。Rust の標準の `HashMap` は:

- **SipHash-1-3** という、暗号学的な性質を持つハッシュ関数を使う
- プログラムを起動するたびに**ランダムな鍵**で初期化する（`RandomState`）。そのため、同じキーでもハッシュ値が毎回違い、攻撃者は衝突するキーを事前に計算できない

その代わり、単純なハッシュ関数よりは遅くなります。**安全をデフォルトにして、速さが必要な人は自分で選ぶ**、という Rust らしい判断です。

### 速いハッシュ関数を選ぶとき

`measure` と `compare` の結果です。

```
標準 (SipHash-1-3) で 100 万回 entry:   23.590ms
FNV-1a で 100 万回 entry            :   18.701ms

count (標準 vs FNV)  遅い版 7.152ms  →  4.631ms   1.5 倍
```

FNV-1a は 1.2〜1.5 倍速くなりました。思ったより差が小さいと感じたかもしれません。HashMap の処理時間には、ハッシュの計算以外にも、メモリへのアクセス（キャッシュミス）や、比較の処理が含まれているからです。**ハッシュ関数を変えるだけで 10 倍速くなる、ということは普通はありません。**

| ハッシュ関数 | 速さ | HashDoS への耐性 | 使われている場所 |
|---|---|---|---|
| SipHash-1-3（標準） | 普通 | ◎ | `std::collections::HashMap` |
| FNV-1a | 速い（短いキーで特に） | × | 課題 03 で自作 |
| FxHash（`rustc-hash` クレート） | とても速い | × | Rust のコンパイラ（rustc）自身 |
| foldhash / aHash | 速い | ○（ある程度） | `hashbrown` クレートなど |

**選ぶ基準**: キーを**外部の人が決められる**（HTTP のパラメータ、ユーザーの入力、外部から受け取ったファイル）なら、標準のままにする。キーが自分のプログラムの中で決まる値だけで（コンパイラの内部処理など）、しかも計測して HashMap がボトルネックだと分かったなら、速いハッシュ関数を検討する。

## 4. プロファイラ: どこが遅いのかを調べる

ここまでの例では、どこが遅いかが最初から分かっていました。現実のプログラムでは、**どこが遅いのかを調べるところから**始めます。推測はたいてい外れます。

プロファイラは、プログラムの実行中に「今どの関数を実行しているか」を短い間隔で記録し、**どの関数に時間がかかっているか**を集計するツールです。

| ツール | 動く環境 | 特徴 |
|---|---|---|
| [`cargo flamegraph`](https://github.com/flamegraph-rs/flamegraph) | Linux / macOS | 結果をフレームグラフ（後述）の SVG にしてくれる |
| [`samply`](https://github.com/mstange/samply) | Linux / macOS / Windows | 結果を Firefox Profiler（ブラウザ）で見られる。使いやすい |
| Instruments | macOS（Xcode に付属） | Apple 公式。Time Profiler を使う |
| `perf` | Linux | 低レベルで強力。多くのツールの土台 |

```bash
cargo install samply
cargo build --release
samply record ./target/release/your_program
```

### フレームグラフの読み方

```
┌───────────────────────────── main ─────────────────────────────┐
├──────────── parse_log ─────────────┬──── print_report ─────────┤
├─ read_line ─┬──── parse_entry ─────┤                            │
│             ├─ to_string ─┬─ split ┤                            │
```

- 横幅が「その関数で使った時間の割合」。**幅の広いものが、時間を使っているもの**
- 縦は呼び出しの関係（下が呼び出し元、上が呼び出し先。ツールによって上下が逆）
- 横の並び順には意味がない（アルファベット順などで並んでいるだけ）

上の例なら、`parse_entry` の中の `to_string` が大きな割合を占めているので、「ここで `String` を作らずに `&str` のまま扱えないか？」と考えます。

**プロファイルを取るときは release ビルドで、ただしデバッグ情報は付けておく**と、関数名が分かって読みやすくなります（`Cargo.toml` に `[profile.release] debug = true`）。

## 5. ⭐ 選球眼: いつ最適化するべきか

> この節は要点だけです。Amdahl の法則やボトルネックの見分け方など、詳しい議論は [選球眼 05: パフォーマンスの判断](../../docs/judgment/05_performance_judgment.md) にあります。

### 「早すぎる最適化は諸悪の根源」

> 小さな効率のことは、97% の場合は忘れるべきだ。早すぎる最適化は諸悪の根源である。
> しかし、残りの重要な 3% の機会を逃してはならない。
> — Donald Knuth（1974）

前半だけが有名ですが、**後半が大事**です。最適化をするなとは言っていません。「どこが重要な 3% なのかを見極めてから、そこに集中しろ」と言っているのです。

### アムダールの法則: 全体の何割か

プログラム全体の実行時間のうち、ある部分が占める割合が `p` だとします。その部分を無限に速くしても、全体は最大で `1 / (1 - p)` 倍にしかなりません。

| 速くした部分の割合 | その部分を 10 倍速くすると | 無限に速くしても |
|---|---|---|
| 10% | 全体は 1.10 倍 | 1.11 倍 |
| 50% | 1.82 倍 | 2 倍 |
| 90% | 5.26 倍 | 10 倍 |

全体の 10% しか占めていない関数を頑張って 10 倍速くしても、全体はたった 1.1 倍しか速くなりません。**だから、まずプロファイラで「どこが 90% を占めているか」を調べる**のです。

### 最適化の判断フロー

1. **そもそも遅いのか？** 「速いほうがいい」ではなく、「要件（例: 1 秒以内に応答する）を満たしていない」のかを確認する。満たしているなら、何もしない
2. **どこが遅いのか？** プロファイラで調べる。推測しない
3. **計算量の問題か？** O(n²) が隠れていないか。ここが一番効く
4. **I/O 待ちではないか？** DB や外部 API を待っているなら、CPU の最適化は意味がない（[09 I/O と非同期処理](../../docs/fundamentals/09_io_async.md)）。キャッシュ、バッチ化、並行化を考える
5. **アロケーションやデータの持ち方の問題か？**
6. **直したら、もう一度測る。** 速くなっていなければ、元に戻す

### 可読性とのトレードオフ

最適化したコードは、たいてい読みにくくなります。

```rust
// 読みやすい
fn fields(line: &str) -> Vec<String> {
    line.split(',').map(|f| f.trim().to_string()).collect()
}

// 速い（でも、呼び出し側がバッファを管理し、ライフタイムも意識する必要がある）
fn fields_into<'a>(line: &'a str, out: &mut Vec<&'a str>) {
    out.clear();
    out.extend(line.split(',').map(str::trim));
}
```

`fields_into` は 4 倍速く、アロケーションもしません。しかし、使う側は「`out` を使い回す」「`out` の中身は `line` より長く生きられない」ことを理解していなければなりません。

**判断の目安**:
- 1 秒に何百万回も呼ばれる、ホットな（よく実行される）関数なら、読みにくくなっても最適化する価値がある。**なぜこう書いたのかをコメントに残す**
- 起動時に 1 回だけ呼ばれる設定の読み込みなら、読みやすさを優先する
- ライブラリの公開 API なら、両方を用意することもある（標準ライブラリの `read_to_string` と `read_line` のように）

### Rust を選ぶ理由と、最適化の関係

[01 Rust を選ぶべき時](../../docs/judgment/01_when_to_use_rust.md) で、「性能やメモリの効率がビジネス上の価値に直結するなら、Rust は有力な候補」と書きました。
しかし、この Stage で見たとおり、**アルゴリズムを直すほうが、言語を変えるよりずっと効く**ことがよくあります。O(n²) の Rust のコードは、O(n) の Python のコードに、データが増えれば負けます。

「遅いから Rust で書き直そう」と言う前に、今の言語でプロファイラを使い、計算量とアロケーションを見直したかを確認しましょう。それでも足りないときに、初めて Rust の出番です。
