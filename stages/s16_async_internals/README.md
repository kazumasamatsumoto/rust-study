## 1. Future の契約

`Future` トレイトの定義は、驚くほど小さいものです。

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> {
    Ready(T),
    Pending,
}
```

`poll` は「**処理を進められるところまで進めて、結果を報告する**」関数です。この関数には、型だけでは表現できない**約束（契約）**があります。

| 約束 | 内容 | 破るとどうなるか |
|---|---|---|
| ① 完了したら `Ready(値)` | | |
| ② まだなら `Pending`。そのときは**後で `cx.waker()` が呼ばれるように手配しておく** | Waker を保存して、準備ができたら誰かが呼ぶ | **そのタスクは二度と起こされず、永遠に止まる** |
| ③ `poll` はすぐに戻る | 中で長く待たない（ブロックしない） | 実行器のスレッドが止まり、他のタスクも全部止まる（Stage 11 の `blocking_demo`） |
| ④ `Ready` を返した後に poll しない | これは**呼ぶ側**の約束 | 何が起きるかは Future の実装次第（panic することが多い） |

②がこの Stage の中心です。
Rust の Future は、「**準備ができたら知らせてね**」と Waker を預けて `Pending` を返し、知らせが来るまで実行器はそのタスクを放っておきます。

### `Context` と `Waker`

- `Waker`: 「このタスクをもう一度 poll してください」と実行器に頼むためのハンドル。`wake()` を呼ぶと、実行器にそのタスクが戻ります
- `Context`: `poll` に渡される引数で、今のところ中身は実質的に Waker だけです（将来の拡張のために包んであります）

`Waker` は `Clone + Send + Sync` です。**別のスレッドに渡して、そこから呼べる**必要があるからです。
課題 02 のタイマーは、まさに「別スレッドが時間を計り、終わったら Waker を呼ぶ」という形になっています。本物の I/O では、OS からの通知（epoll や kqueue）を受け取ったスレッドが Waker を呼びます。

## 2. ⭐ pull 型（Rust）と push 型（JavaScript）

Rust の Future と JavaScript の Promise は、似ているようで、**動かし方が正反対**です。

```text
JavaScript (push 型)                     Rust (pull 型)
────────────────────                     ──────────────
const p = fetch(url);                    let f = fetch(url);
  ↑ ここで通信が始まる                      ↑ まだ何も起きていない（ただの値）

  通信が終わると、Promise が自分から          実行器が f.poll() を呼ぶ
  登録されたコールバックを呼ぶ (push)           → Pending なら Waker を預かる
  p.then(cb)  /  await p                    Waker が呼ばれたら、実行器がまた poll する (pull)
```

| | JavaScript の Promise | Rust の Future |
|---|---|---|
| 動き出すタイミング | **作った瞬間** | **poll されたとき**（`.await` するか spawn するまで何も起きない） |
| 進め方 | 完了した側がコールバックを呼ぶ（push） | 実行器が poll して進める（pull） |
| 実行器 | 言語のランタイムに組み込まれている（イベントループ） | **ライブラリ**（tokio など）。自分で書くこともできる（この Stage） |
| キャンセル | 標準の方法はない（`AbortController` を別に使う） | **Future を drop するだけ**。poll されなくなれば、それ以上進まない |
| メモリ確保 | Promise ごとにヒープに確保される | 必須ではない。Future はただの値なので、スタックにも置ける |
| 合成した結果 | Promise の連鎖（それぞれ別のオブジェクト） | **1つの大きなステートマシン**（第3節） |

### pull 型を選んだ理由とコスト

**得たもの**
- **キャンセルが簡単**: Stage 11 の `select!` で、負けた側の Future は drop されて止まりました。push 型では「もう結果はいらない」と伝える仕組みを別に作る必要があります
- **ゼロコスト**: Future を組み合わせても、ヒープの確保や仮想関数の呼び出しが要りません。コンパイラが1つの型にまとめて最適化できます
- **実行器を選べる**: サーバ向け（tokio）、組み込み向け（embassy）、WASM 向けなど、用途に合った実行器を使えます

**払ったもの**
- **実行器が必要**: Future を作っただけでは動かないので、「`.await` し忘れて何も起きない」バグが起きます（コンパイラは `unused_must_use` で警告します）
- **Waker の手配が実装者の責任**: Future を手で書くときに Waker を忘れると、永遠に止まります（課題 02 で体験します）
- **Pin という難しい概念が必要**（第4節）

## 3. ⭐ async fn の正体と、Future の大きさ

CS基礎 09 で見たとおり、`async` ブロックは**ステートマシン**に変換されます。

```rust
async {
    let x: u64 = 1;
    yield_once().await;   // ← ここで中断することがある
    x + 1
}
```

は、概念的には次のような enum になります。

```rust
enum AsyncBlock {
    Start,                                    // まだ一度も poll されていない
    Suspended { x: u64, fut: YieldOnce },     // await で止まっている。x を覚えておく
    Done,
}
```

**`.await` をまたいで生きている変数は、状態の中に保存されます**。保存しておかないと、中断して戻ってきたときに `x` がなくなってしまうからです。
これは、スレッドならスタックが自動でやってくれることです。async では、**スタックの代わりに Future という値の中に、必要な変数だけを保存**しています。

### 実験: Future の大きさを測る

`cargo run -p s16_async_internals --example future_size` の結果です（この PC での実行結果。debug でも release でも同じでした）。

```
== async ブロックの Future のサイズ (バイト) ==
何もしない                         :     1
1KB の配列を使うが await しない     :     1
u64 を1つ持ったまま await           :    16
1KB の配列を持ったまま await        :  1026
1KB の配列を await の前に捨てる     :     2
512B を2つ、別々の await をまたぐ   :  1026
512B ずつ、生きている範囲を分ける   :   524
1KB を Box に入れて await           :    16
1KB を持つ async fn を await する   :  1027

比較: スレッド1本のスタック (Rust の spawn のデフォルト) = 2 MiB = 2097152 バイト
```

一つずつ読み解きます。

| 結果 | なぜそうなるか |
|---|---|
| 何もしない: **1** | 「今どの状態か」を表す番号（判別子）の 1 バイトだけ |
| 1KB 使うが await しない: **1** | 中断しないので、1KB の配列は poll の中の普通のローカル変数（スタック上）で済む。Future に保存する必要がない |
| u64 を持ったまま await: **16** | `x` の 8 バイト ＋ 判別子と `YieldOnce`（1 バイトの bool）。u64 のアラインメント（CS基礎 03）で 16 に切り上がる |
| 1KB を持ったまま await: **1026** | 配列の 1024 バイトを丸ごと Future の中に保存する必要がある |
| 1KB を await の前に捨てる: **2** | await の時点でもう生きていないので、保存しなくてよい |
| 512B を2つ: **1026** | 2つ目の await の時点で `a` も `b` も生きている（最後に両方使う）ので、両方を保存する |
| 範囲を分けた: **524** | 1つ目の await では `a` だけ、2つ目では `b` だけが生きている。**同時に生きていない変数は、同じメモリを共有できる**ので、512 バイト分で済む（enum の各バリアントが同じ場所を使うのと同じ） |
| Box に入れた: **16** | Future に保存されるのは `Box`（ポインタ 8 バイト）だけ。中身はヒープにある |
| async fn を await: **1027** | 呼んだ async fn の Future（1026 バイト）が、呼んだ側の Future の中に**丸ごと埋め込まれる** |

### ここから分かること

1. **async のタスクは小さい**: スレッドのスタック 2 MiB に対して、タスク1つは数バイト〜数 KB です。10万個のタスクを作れるのはこのためです（CS基礎 09 の C10K 問題）
2. **ただし、await をまたぐ大きな変数は、そのまま Future を大きくする**: 大きなバッファを持ったまま await すると、その分だけタスクが大きくなります。spawn するたびにそのサイズでヒープ確保が起きるので、メモリ使用量に効いてきます。大きなものは `Box` や `Vec` でヒープに逃がすか、await の前に捨てましょう
3. **Future の大きさはコンパイル時に決まる**: async fn を await すると、その Future が丸ごと埋め込まれます。だから **async fn は、そのままでは自分自身を再帰的に呼べません**（自分の中に自分を埋め込むことになり、大きさが無限になる）。再帰させたいときは `Box::pin(f()).await` のようにヒープを挟みます（設計の問い3）

## 4. ⭐ Pin: なぜ必要なのか

`poll` の引数は `&mut self` ではなく、`self: Pin<&mut Self>` です。この `Pin` が、Rust の async で最も難しい部分です。ここでは「なぜ必要なのか」から説明します。

### 問題: async ブロックは「自分自身を指す参照」を持つことがある

```rust
async {
    let data = [1u8, 2, 3, 4];
    let r = &data;          // r は data を指す
    yield_once().await;     // ← ここで中断する
    println!("{}", r[0]);   // 再開後に r を使う
}
```

await をまたいで、`data` も `r` も生きています。そのため、両方が Future の中に保存されます。

```text
  Future (アドレス 0x1000 にある)
 ┌──────────────────────────────┐
 │ data: [1, 2, 3, 4]   ← 0x1000 │
 │ r:    0x1000 ────────┘        │   r は「自分自身の中」を指している
 └──────────────────────────────┘
```

これを**自己参照構造体**と呼びます。普通の Rust のコードでは書けない（借用チェッカーが許さない）形ですが、async ブロックを変換すると、こういうものが自然にできあがります。

### ムーブすると壊れる

CS基礎 03 で見たとおり、**ムーブとは、バイト列を別の場所にコピーすること**です。この Future をムーブすると、どうなるでしょうか。

```text
  ムーブ後の Future (アドレス 0x2000)
 ┌──────────────────────────────┐
 │ data: [1, 2, 3, 4]   ← 0x2000 │
 │ r:    0x1000 ─────────────────┼──→ 古い場所（もう何もない！）
 └──────────────────────────────┘
```

`r` の値（アドレス）もそのままコピーされるので、**古い場所を指したまま**になります。CS基礎 04 のダングリングポインタです。

### 実験: 本当にずれるのか

`cargo run -p s16_async_internals --example self_ref` の結果です。自分のフィールドを指すポインタを持つ構造体を作り、ムーブしてみます（アドレスを表示するだけで、ずれたポインタの先は読まないので、unsafe は使っていません）。

```
① 作った直後 (スタック上)
  data の本当のアドレス     : 0x16fd5a020
  ptr_to_data が指すアドレス: 0x16fd5a020  → 一致
② Box に入れた (ヒープに移動した)
  data の本当のアドレス     : 0x100791cb8
  ptr_to_data が指すアドレス: 0x16fd5a020  → ずれている!
③ &mut を2つ使って mem::swap した後の x
  data の本当のアドレス     : 0x16fd5a038
  ptr_to_data が指すアドレス: 0x16fd5a048  → ずれている!
```

②: Box に入れただけで、data はヒープ（`0x100...`）に移動しましたが、ポインタはスタック（`0x16f...`）を指したままです。
③: 注目してほしいのはこちらです。`&mut` が2つあれば、`std::mem::swap` で**中身を入れ替える（= ムーブする）ことができてしまいます**。x のポインタは、入れ替える前の y の場所を指しています。

つまり、**`&mut T` を渡してしまうと、受け取った側はいつでも中身をムーブできる**のです。だから `poll(&mut self)` という設計では、自己参照する Future を安全に扱えません。

### 解決策: `Pin<&mut T>`

`Pin<&mut T>` は「**この値は、もうメモリ上で移動しない**」と約束された参照です。

- `Pin<&mut T>` からは、普通の `&mut T` を（安全なコードでは）**取り出せません**。`&mut T` がなければ `mem::swap` も `mem::replace` もできないので、ムーブできません
- 値を移動しないまま、中身を変更する（poll する）ことはできます

```text
  &mut T          … 読める・書ける・ムーブできる
  Pin<&mut T>     … 読める・書ける・ムーブできない   ← poll にはこれを渡す
```

### `Unpin`: ムーブしても壊れない型

とはいえ、ほとんどの型は自己参照を持たず、ムーブしても何も壊れません。`i32` も `String` も `Vec` も、`Box<T>`（ヒープの中身は動かないので）もそうです。
そういう型には **`Unpin`** という印（自動トレイト）が付いていて、`Pin<&mut T>` からでも `get_mut()` で普通の `&mut T` を取り出せます。

| 型 | `Unpin` か | 理由 |
|---|---|---|
| `i32`, `String`, `Vec<T>`, `Box<T>` | ○ | 自己参照を持たない |
| 課題 01 の `Ready`, `YieldN`, `Then` | ○ | 中身が全て `Unpin` だから自動で `Unpin` になる |
| **`async { ... }` で作った Future** | **×** | 自己参照を持つ**可能性がある**ので、コンパイラは常に `!Unpin` にする |
| `Pin<Box<dyn Future>>` | ○ | Box そのもの（ポインタ）は動かしても、中身は動かないから |

課題 01 で `self.get_mut()` が使えるのは、課題の Future が全て `Unpin` だからです。
一方、async ブロックを `Unpin` を要求する関数に渡すと、次のエラーになります（実際のコンパイルエラー）。

```
error[E0277]: `{async block@src/main.rs:11:19: 11:24}` cannot be unpinned
  --> src/main.rs:12:23
   |
12 |     let _ = poll_once(&mut fut);
   |             --------- ^^^^^^^^ the trait `Unpin` is not implemented for `{async block@src/main.rs:11:19: 11:24}`
   |             |
   |             required by a bound introduced by this call
   |
   = note: consider using the `pin!` macro
           consider using `Box::pin` if you need to access the pinned value outside of the current scope
```

### ピン留めする2つの方法

コンパイラも提案しているとおり、`!Unpin` な Future を poll するには、どこかに**ピン留め**します。

| 方法 | どこに置くか | 特徴 | この Stage での使いどころ |
|---|---|---|---|
| `std::pin::pin!(fut)` | 今のスタックフレーム | ヒープ確保なし。ただし、その関数の外には持ち出せない | 課題 01 の `busy_block_on`、課題 02 の `block_on` |
| `Box::pin(fut)` | ヒープ | 確保が1回必要。`Pin<Box<_>>` は自由にムーブできる（動くのはポインタだけ） | 課題 03 のタスク（キューの間を行き来させるため） |

> **Pin を完全に理解する必要はありません。** 実務で Pin を意識するのは、Future やストリームを手で実装するとき（とライブラリを書くとき）くらいです。
> 「自己参照する値をムーブから守るための型」「ほとんどの型は Unpin なので関係ない」「async ブロックは Unpin ではないので `pin!` か `Box::pin` で留める」の3点を押さえれば十分です。

## 5. Waker と block_on: 眠って待つ

課題 01 の `busy_block_on` は、`Pending` が返ってきても、すぐにまた poll します。待っている間も CPU を使い続けるので、**ビジーループ**と呼ばれます。

課題 02 の `block_on` は、`Pending` なら `thread::park()` で**眠り**、Waker が呼ばれたら（= `unpark` されたら）起きて poll します。

### 実験: どれくらい違うのか

課題 01・02 を解いた後に `cargo run -p s16_async_internals --example busy_vs_park --release` を実行した結果です（模範解答での実行例）。

```
busy_block_on: poll   16866978 回, 110.515917ms
block_on     : poll          2 回, 110.061167ms
```

同じ 100ms のタイマーを待つのに、ビジーループは **約1700万回** poll し、その間 CPU のコア1つを 100% 使っていました。`block_on` は **2 回**（最初の `Pending` と、起こされた後の `Ready`）だけです。
何度か実行すると、ビジーループの回数は 1600万〜1900万回の間でばらつきました（debug ビルドでは 270万〜340万回）。`block_on` は毎回 2 回でした。

**かかった時間はどちらも同じ**です。ビジーループは速くなるわけではなく、ただ CPU を無駄にしているだけです。
サーバで1万個のタスクがそれぞれビジーループしたら、と想像してみてください。Waker という仕組みがある理由がこれです。

### park / unpark の性質

`thread::park()` と `Thread::unpark()` には、大事な性質が2つあります。

1. **先に `unpark` されていたら、次の `park` はすぐに戻る**: 「Waker が呼ばれた後に park した」場合でも、取りこぼさずに起きられます
2. **理由なく起きることがある**（見せかけの起床 / spurious wakeup）: だから「起きたら必ず poll して確かめ、`Pending` ならまた眠る」というループにします

### ⭐ 起こし損ね（lost wakeup）

`TimerFuture::poll` では、「完了したか確認する」と「Waker を保存する」を、**同じロックの中で**行います。これを2回に分けてロックすると、何が起きるでしょうか。

```text
  poll するスレッド                     タイマーのスレッド
  ─────────────────                     ──────────────────
  lock → completed は false → unlock
                                        lock → completed = true
                                              waker は None なので、誰も起こさない
                                        unlock
  lock → waker を保存 → unlock
  Pending を返す
  park() ……… 二度と起こされない
```

タイマーのスレッドは、Waker が保存される**前に**完了してしまい、起こす相手がいませんでした。poll した側は、もう完了しているのに、それを知らないまま眠り続けます。

これは CS基礎 08 の**競合状態**（race condition）です。データ競合ではない（Mutex で守っている）ので、Rust のコンパイラは防いでくれません。
「確認」と「待つ準備」を1つのロックの中でまとめて行えば、この隙間はなくなります。これは async に限らず、`Condvar` を使った待ち合わせでも同じ鉄則です。

課題 02 のテストは、別スレッドで実行して 5 秒で打ち切るようにしてあります。Waker の保存を忘れた実装で試すと、次のように失敗します（実際の出力）。

```
5 秒たっても終わりませんでした。Pending を返すときに Waker を保存しているか、タイマーのスレッドが wake を呼んでいるか、ThreadWaker が unpark しているかを確認してください。
```

## 6. 実行器: タスク自身が Waker になる

課題 03 の実行器の要は、**`Task` に `Wake` を実装して、タスク自身を Waker にする**ことです。

```text
 ① spawn: Future を Task に包み、キューに送る
 ② run:   キューから Task を取り出して poll する
            Pending → Future を Task に戻す。キューには入れない（放っておく）
 ③ タイマーのスレッドが waker.wake() を呼ぶ
            = Task::wake が呼ばれる
            = Task が自分自身をキューに送り直す
 ④ run:   キューから取り出して、もう一度 poll する → Ready → 終わり
```

こうすると、**起こされたタスクだけ**がキューに戻ってきます。起こされていないタスクは、一度も poll されません。

課題 03 のテスト `test_tasks_run_concurrently` は、100ms のタイマーを待つタスクを3つ spawn し、次の2点を確かめています。

- 全体が **100ms 程度**で終わること（300ms ではない）: 1つのスレッドで、3つのタスクの待ち時間を重ねている
- poll の合計が**ちょうど 6 回**であること: 各タスクにつき「最初の `Pending`」と「起こされた後の `Ready`」の2回だけ。起こされていないタスクを poll していたら、6 回を超えます

### `JoinHandle` も Future

`spawn_with_handle` が返す `JoinHandle` は、「タスクの結果が入ったら Ready になる Future」です。
中身は `TimerFuture` とほぼ同じで、「結果があれば Ready、なければ Waker を保存して Pending」です。タスクが終わったら、保存された Waker を呼んで、待っている側を起こします。

**「何かを待つ」は全て、この同じ形（状態の確認 ＋ Waker の保存）で書ける**ことに注目してください。チャネル、Mutex、タイマー、ソケット、どれも同じです。

## 7. なぜ Rust は標準のランタイムを持たないのか

Stage 11 で「Rust の標準ライブラリには async のランタイムがない」と学びました。この Stage を終えると、その理由がよく分かります。

標準ライブラリ（正確には `core`）にあるのは、`Future`、`Poll`、`Context`、`Waker`、`Pin` という**インターフェースだけ**です。
実行器は、そのインターフェースを使う**ただのライブラリ**です。今まさに、あなたが数百行で書いたように。

この分け方のおかげで、

- サーバでは tokio、組み込み機器では [embassy](https://embassy.dev/)（OS もヒープもない環境向けの async フレームワーク）、ブラウザの WASM では `wasm-bindgen-futures`（JavaScript の Promise の仕組みの上で Future を動かす）、というように、**環境に合った実行器を選べます**
- `async fn` で書いたライブラリのコードは、`Future` トレイトにしか依存していなければ、どの実行器の上でも動きます

**その代わりに払っているもの**: 実行器ごとに、タイマーや I/O、チャネルの API が違います。tokio 向けに書かれたライブラリ（`tokio::time::sleep` を中で使っているもの）は、他の実行器ではそのまま動きません。
「どのランタイムを使うか」がエコシステムの分断を生んでいる、という批判もあります。現在は事実上 tokio が標準になっていて、多くのクレートが tokio を前提にしています（選球眼 02）。

## 8. ⭐ 自作版と tokio の比較

自作した実行器と、tokio（このリポジトリで使っている 1.54.1）の実際の仕組みを比べます。tokio の欄は、tokio 1.54.1 のソースで確認した内容です。

| | 自作版（この Stage） | tokio（マルチスレッドランタイム） |
|---|---|---|
| 実行するスレッド | 1本 | 複数のワーカースレッド。デフォルトは CPU のコア数（`std::thread::available_parallelism`） |
| 実行待ちキュー | `mpsc` チャネル1本 | **ワーカーごとのローカルキュー**（容量 256。`src/runtime/scheduler/multi_thread/queue.rs` の `LOCAL_QUEUE_CAPACITY`）＋ 全体で共有するキュー |
| 負荷の偏り | 考えない（スレッドが1本なので） | **ワークスティーリング**: 自分のキューが空になったワーカーは、他のワーカーのキューからタスクを盗む（`steal_into`） |
| タスクの持ち方 | `Arc<Task>` ＋ `Mutex<Option<Pin<Box<dyn Future>>>>` | タスクごとに1回だけ確保する領域に、ヘッダと Future を並べて置く。ヘッダには状態・キューの次へのポインタ・vtable がある（`src/runtime/task/core.rs` の `Header`） |
| タスクの状態管理 | Mutex でロックする | ロックを使わず、**アトミックな整数（`AtomicUsize`）のビット**で「実行中」「通知済み」「完了」などを管理する（`src/runtime/task/state.rs`） |
| Waker | `Wake` トレイト（`Arc` の参照カウントを使う） | `RawWaker` と自前の vtable。タスクのヘッダにある参照カウントを使い、Waker を作るたびの確保をなくしている |
| タイマー | **タイマーごとにスレッドを1本作る**（重い！） | **階層型タイミングホイール**: 64 スロット × 6 段で、1ms の精度で約2年先までを管理する（`src/runtime/time/wheel/mod.rs`）。スレッドは作らない |
| I/O | なし | **I/O ドライバ**: `mio` クレートを通して、Linux では epoll、macOS では kqueue、Windows では IOCP を使い、ソケットの準備ができたら Waker を呼ぶ |
| 1つのタスクが居座る問題 | 考えない | **協調スケジューリングの予算**: 1回の実行で使える操作の回数に上限（128。`src/task/coop/mod.rs` の `Budget::initial`）があり、使い切ると tokio のリソースはわざと `Pending` を返して、他のタスクに順番を譲らせる |
| ブロッキング処理 | 考えない（実行器ごと止まる） | `spawn_blocking` 用の別のスレッドプール |

**考え方は全く同じ**です。「Future を poll する」「Pending なら Waker を預けて放っておく」「Waker が呼ばれたらキューに戻す」。
tokio は、その各部分を「ロックを減らす」「確保を減らす」「スレッドを減らす」「CPU のコアを全部使う」方向に、徹底的に最適化したものです。

自作版のタイマーは「1つのタイマーにスレッド1本」なので、1万個のタイマーを作ると1万本のスレッドができてしまいます。これでは async にした意味がありません（CS基礎 09）。
tokio のタイミングホイールは、たくさんのタイマーを1つのデータ構造でまとめて管理し、「次に起こすべき時刻」までまとめて眠ります。

## 9. ⭐ 選球眼: 実行器を自作するべき場面

この Stage で実行器を作ったのは、**仕組みを理解するため**です。実務で自作する場面は、ほとんどありません。

| 場面 | 選ぶもの | 理由 |
|---|---|---|
| Web サーバ、API クライアント、一般的なネットワークのプログラム | **tokio** | エコシステムの大半が tokio を前提にしている。性能も十分に最適化されている |
| 組み込み機器（マイコン、OS なし、ヒープなし） | **embassy** などの組み込み向け | tokio は OS の機能（スレッド、epoll）を前提にしているので使えない。Future がただの値でスタックに置けるおかげで、ヒープなしでも async が使える |
| ブラウザで動く WASM | **wasm-bindgen-futures** | ブラウザでは自分でスレッドやイベントループを作れないので、JavaScript のイベントループの上に乗る |
| テストで「時間」や「実行順」を制御したい | tokio の `start_paused`（Stage 11）など、既存の仕組み | 自作しなくても、たいてい用意されている |
| ゲームエンジンや GUI のように、独自のイベントループを既に持っている | 自作、または既存の小さな実行器 | 既存のループの1フレームごとに、タスクを少し進める、という統合が必要になることがある |
| 学習 | 自作 | まさにこの Stage |

**判断の基準**: 「既存の実行器が前提にしている環境（OS、スレッド、ヒープ）が使えるか」と「エコシステムのライブラリを使いたいか」。ほとんどの場合、答えは tokio です。

ただし、**中身を知っていること**には、実務でも大きな価値があります。

- 「async の中で重い計算をすると、なぜ他のリクエストまで遅くなるのか」を説明できる（実行器のスレッドを占有するから）
- 「大きなバッファを持ったまま await するとメモリを食う」理由が分かる（第3節）
- 自分で Future やストリームを実装する必要が出たときに、Waker の扱いを間違えない
- tokio のドキュメントに出てくる「ワークスティーリング」「協調スケジューリング」「タイマーホイール」という言葉の意味が分かる
